# Path-MTU discovery для UDP в TUN

Документ описывает, как UDP-движок TUN в `outline-ws-rust` (`crates/outline-tun`) обрабатывает датаграммы, которые upstream-транспорт отвергает как слишком большие: когда он шлёт отправителю ICMP-сигнал «пакет слишком велик», какой MTU объявляет и когда молчит, чтобы QUIC-клиенты не уходили на TCP. Документ для операторов TUN-клиента и разработчиков UDP-пути.

*English version: [TUN-PMTUD.md](TUN-PMTUD.md)*

## Когда срабатывает PMTUD-путь

Для каждого UDP-потока, прочитанного из TUN-устройства и направленного в туннельный аплинк, движок оборачивает payload в UDP-кадрирование SOCKS5 и передаёт в `send_packet` транспорта. Часть транспортов отвергает payload больше жёсткого предела:

| Транспорт | Предел | Ошибка |
|---|---|---|
| VLESS-UDP | 65 536 байт payload (`MAX_VLESS_UDP_PAYLOAD`) | `OversizedUdpDatagram { transport: "vless-udp", payload_len, limit }` |
| Shadowsocks UDP через обычный UDP-сокет (`UdpWsTransport::from_socket`) | 65 507 байт (`MAX_UDP_SOCKET_PACKET_SIZE`) | `Ss2022Error::OversizedUdpUplink` (предел не передаётся) |

Движок распознаёт обе ошибки через `is_dropped_oversized_udp_error` и отправляет отказ в PMTUD-путь, а не считает его сбоем аплинка.

UDP поверх HTTP/3-датаграмм в этот путь не попадает: пакет, который не помещается в текущий размер датаграммы, уходит в стрим и считается в `outline_ws_udp_h3_datagram_fallback_total{reason="too_large"}`.

## Зачем движок шлёт ICMP-сигнал

Отказ транспорта отправителю не виден: он повторяет тот же слишком большой payload по каждому таймеру потерь и так и не узнаёт реальный MTU туннеля. В продакшене это ломало VoWiFi: IKE_AUTH с клиентскими сертификатами через туннельный аплинк повторялся, пока обмен сертификатами не истекал по таймауту и звонок не обрывался.

Поэтому движок синтезирует ICMP-ошибку исходному отправителю, чтобы сработал его собственный PMTUD:

- IPv4: `Destination Unreachable / Fragmentation Needed` (Type 3 / Code 4) с Next-Hop MTU во втором слове ICMP-заголовка (RFC 1191).
- IPv6: `Packet Too Big` (Type 2 / Code 0) с MTU во втором слове (RFC 4443 §3.2).

Ответ цитирует исходный IP-заголовок и 8-байтный UDP-заголовок, чтобы стек отправителя сопоставил его с сокетом (RFC 1812 §4.3.2.3, RFC 4443 §3.2). Цитируемый заголовок собирается заново из ключа потока (`build_ipv4_udp_packet` / `build_ipv6_udp_packet` с пустым payload).

## Объявляемый MTU

`limit` транспорта (сколько байт SOCKS5-обёрнутого payload он принимает) становится объявляемым MTU, поднятым до протокольного минимума семейства:

| Семейство | Минимум | Константа |
|---|---|---|
| IPv4 | 576 (RFC 791) | `IPV4_MIN_PATH_MTU` |
| IPv6 | 1280 (RFC 8200) | `IPV6_MIN_PATH_MTU` |

Если ошибка не несёт предела (`Ss2022Error::OversizedUdpUplink`), объявляется минимум семейства. Предел, не помещающийся в поле заголовка (например, 65 536 от VLESS-UDP в 16-битном поле IPv4), обрезается до максимума поля.

Payload ICMPv6 Packet Too Big обрезается так, чтобы пакет целиком не превышал минимальный MTU канала IPv6 (RFC 4443 §2.4(c)).

## Ограничение частоты

Каждому потоку разрешён не больше чем один PTB в секунду (`PTB_THROTTLE`, как значение Linux `net.ipv4.icmp_ratelimit` по умолчанию — 1000 мс). RFC 4443 §2.4(f) требует ограничения частоты для ICMPv6; RFC 1812 §4.3.2.8 рекомендует его для IPv4. Пачка повторов слишком больших датаграмм даёт поэтому один PTB в секунду на поток, и некорректный отправитель не может устроить ICMP-шторм из TUN-интерфейса.

Состояние ограничения — метка времени `last_ptb_sent` потока, поэтому оно сбрасывается при вытеснении потока из таблицы. Если к моменту отправки PTB потока в таблице уже нет (он закрывается), PTB не отправляется.

## Порог QUIC: когда движок молчит

PTB с path MTU ниже минимума Initial-датаграммы QUIC делает только хуже. RFC 9000 §14.1 требует от конечных точек QUIC v1 отправлять Initial-пакеты в UDP-датаграммах с UDP payload не меньше 1200 байт (конечные точки IPv6 соблюдают ещё и минимальный MTU канала 1280 байт). Стек по спецификации, получив ICMP-ошибку с меньшим path MTU, решает, что адресат QUIC не пропускает, отключает для него QUIC и уходит на TCP.

Регрессия, из-за которой появилась проверка: YouTube-клиенты Samsung Smart TV отправляли через TUN на googlevideo Initial-датаграммы QUIC по 1200 байт. Носитель SS-over-QUIC с датаграммами (с тех пор удалён) сообщал `OversizedUdpDatagram { limit ≈ 1180 }` для обрамлённого payload, движок отправлял PTB с MTU 1180 байт, и QUIC-стек телевизора отключал HTTP/3 для googlevideo. Сессии оставались на TCP, UDP-трафик с аплинка пропадал.

Поэтому движок не шлёт PTB, если предел транспорта ниже порога QUIC для семейства (`should_emit_ptb_for_limit`):

| Семейство IP | Порог (байт) | Константа | Источник |
|---|---|---|---|
| IPv4 | 1200 | `QUIC_MIN_INITIAL_PAYLOAD_V4` | RFC 9000 §14.1, минимальный UDP payload Initial |
| IPv6 | 1280 | `QUIC_MIN_INITIAL_PAYLOAD_V6` | RFC 9000 §14.1 + минимальный MTU канала RFC 8200 |

Ниже порога датаграмма отбрасывается молча, как до появления PMTUD: отправитель повторяет или истекает по своему расписанию и сохраняет состояние QUIC. На пороге и выше (включая диапазон ~1300–1450 байт, где обычно и бывают проблемы с path MTU) PTB отправляется.

Ошибка без предела (`limit == None`) всегда получает PTB: без сообщённого размера движок не может показать, что порог нарушен, а подавление скрыло бы сигналы PMTUD на транспортах, которые размер не сообщают. Объявляемый MTU в этом случае — минимум семейства (576 / 1280).

Из текущих транспортов предел сообщает только VLESS-UDP (65 536 байт, выше обоих порогов), поэтому на текущих носителях проверка порога ничего не подавляет; она действует для любого транспорта, который сообщит меньший предел.

## Диагностика

- `outline_ws_udp_oversized_dropped_total{direction, cause}` считает каждое отбрасывание слишком большой датаграммы. Значения `cause`: `vless_udp`, `ss_socket`, `xhttp_records`, `socks_client`, `socks_relay`, `socks_direct`, `socks_in_tcp`. В PMTUD-путь TUN попадают причины `vless_udp` и `ss_socket`.
- `outline_ws_udp_h3_datagram_fallback_total{reason="too_large"}` считает HTTP/3-датаграммы, которые не поместились и ушли в стрим.
- Счётчика отправленных PTB нет: `write_pmtud_packet` пишет ICMP-пакет в TUN-устройство без метрики. Неудачная запись PTB логируется на уровне `DEBUG` (`failed to emit ICMP PTB after TUN UDP oversize drop`).

QUIC-стек, принявший PTB и снизивший path MTU, обычно повторяет Initial-датаграммы нового размера. Если они всё равно велики для транспорта, цикл ограничен одним PTB в секунду на поток и виден как ровный редкий ряд отбрасываний.

## Конфигурация

Минимум Initial-датаграммы QUIC зафиксирован в RFC 9000. Настройка одна: разрешено ли движку слать PTB с path MTU ниже этого минимума:

```toml
[tun]
# Default: false. PTBs whose advertised path MTU would sit below QUIC
# v1's Initial-datagram minimum (1200 v4 / 1280 v6) are suppressed,
# keeping compliant QUIC clients on UDP.
pmtud_emit_below_quic_initial = false
```

| Ключ | По умолчанию | Что делает | Когда менять |
|---|---|---|---|
| `pmtud_emit_below_quic_initial` | `false` | `true` шлёт PTB на каждое отбрасывание с известным пределом, в том числе ниже порога QUIC. Ошибки без предела получают PTB при обоих значениях | `true` на хостах без QUIC-клиентов, где сигнал PMTUD важнее, например VoWiFi / IKEv2 с IKE_AUTH, несущим сертификаты, через узкий туннельный аплинк: PTB даёт IKE узнать MTU туннеля до таймаута звонка |

Влияние настройки на отбрасывания ниже порога:

| Значение | Отбрасывания ниже порога | VoWiFi / IKE на узких аплинках |
|---|---|---|
| `false` | Молча; отправитель повторяет по своему таймеру | Медленнее: подсказки MTU нет |
| `true` | Один PTB в секунду на поток | PMTUD реагирует на первый PTB |

Ограничение частоты, построители ICMP и подъём до протокольного минимума (576 / 1280 в ICMP-заголовке) работают одинаково при обоих значениях.

Настройки, полностью отключающей синтез PTB (поведение до коммита `bcaf86d`), нет. Транспорт, который не выдаёт `OversizedUdpDatagram` или `Ss2022Error::OversizedUdpUplink`, в PMTUD-путь не попадает.
