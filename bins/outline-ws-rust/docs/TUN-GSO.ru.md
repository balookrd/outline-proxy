# TUN GSO / GRO / USO offload (`[tun] gso`, `[tun] gro`, `[tun] uso`)

Документ описывает три настройки TUN offload в `outline-ws-rust` на Linux: что каждая меняет на путях чтения и записи, как проверить, что она работает, и как её откатить. Документ для операторов, запускающих TUN-клиент на Linux.

*English version: [TUN-GSO.md](TUN-GSO.md)*

## Цена обработки по пакету без offload

TUN-клиент терминирует TCP в userspace. Без offload каждый downlink-сегмент пишется в TUN-устройство отдельным `write(2)`, а каждый uplink-сегмент приходит отдельным `read(2)`. На нагруженном канале это тысячи вызовов в секунду, и каждый пакет проходит весь сетевой путь ядра (маршрутизация, `nftables`, `conntrack` и пакетное шифрование WireGuard, если клиент за WireGuard), прежде чем попасть на NIC или в наш стек. Профиль живого клиента на ~40–60 Мбит/с показал, что CPU уходит в основном на эту работу ядра по каждому пакету (`nft_do_chain`, `nf_conntrack_*`, `fib_*`, `tun_get_user`, `wg_xmit`), а не на шифрование и не на userspace-стек; самый частый syscall — `write(2)`.

Offload собирает пакеты в пачки, чтобы путь ядра и наш стек выполнялись раз на суперпакет, а не раз на MSS:

| Ключ | Направление | Механизм |
|---|---|---|
| `gso` | downlink, запись (TSO) | Отдаём ядру один TCP-суперсегмент до 61 440 байт вместо N пакетов по MSS; ядро режет его по MSS после того, как маршрутизация / `nftables` / `conntrack` / WireGuard отработали один раз |
| `gro` | uplink, чтение (GRO) | Ядро сливает несколько входящих MSS-сегментов одного потока в один суперпакет (до 64 КиБ) и отдаёт его целиком, так что чтение / разбор / TCP-обработка выполняются один раз |
| `uso` | downlink UDP, запись (USO) | Отдаём ядру один суперсегмент `GSO_UDP_L4` из датаграмм одного размера; ядро режет его по датаграммам |

## Что делает `gso = true`

- Открывает TUN-устройство с `IFF_VNET_HDR`, поэтому каждый `read(2)` / `write(2)` несёт 10-байтный префикс `virtio_net_hdr`.
- Downlink (запись): `flush` собирает очередь данных server→client в один TCP-суперсегмент (до 61 440 байт, `GSO_MAX_SUPER_SEGMENT_PAYLOAD`) с `virtio_net_hdr`, задающим MSS (`gso_size`) и частичную (pseudo-header) контрольную сумму. Ядро режет его на MSS-сегменты, проставляет каждому sequence number и досчитывает L4-checksum. Отсюда экономия CPU на downlink.
- Повторные передачи остаются по MSS: scoreboard отправки отслеживает каждый MSS-сегмент отдельно, поэтому потеря внутри суперсегмента восстанавливается повтором одного MSS-пакета, как и без GSO.
- Один `gso` не вызывает `TUNSETOFFLOAD`, поэтому путь чтения не меняется; uplink покрывает `gro`.

## Что делает `gro = true`

Требует `gso`; `gro = true` при `gso = false` — ошибка конфига (`tun.gro requires tun.gso`).

- Вызывает `TUNSETOFFLOAD` с `TUN_F_CSUM | TUN_F_TSO4 | TUN_F_TSO6`, разрешая ядру сливать входящий TCP в GRO-суперпакеты (до 64 КиБ, `gso_type` TCPV4/6) вместо нарезки до ≤ MSS.
- Uplink (чтение): цикл чтения передаёт большой TCP-сегмент прямо в userspace TCP-движок. Его приёмный путь уже принимает сегменты больше одного MSS: размер берётся из IP total length, данные буферизуются как `Bytes` и обрезаются по окну приёма. `TUN_F_CSUM` включает и RX checksum offload, поэтому ядро может оставить L4-checksum недосчитанной; цикл чтения пересчитывает её по payload.
- UDP при одном `gro` остаётся по датаграммам: `TUN_F_USO4/6` не запрашивается, поэтому без `NETIF_F_GSO_UDP_L4` ядро разбивает UDP GRO обратно на датаграммы до нашего чтения. Если UDP-суперпакет всё же придёт, цикл чтения разобьёт его на датаграммы.
- Слияние происходит только на всплесках: GRO объединяет сегменты, только когда источник шлёт пачкой (bulk-загрузка или путь форвардинга с `generic-receive-offload` на входном NIC). Uplink из одних ACK и интерактивный трафик остаются по пакету.
- Если ядро отвергает `TUNSETOFFLOAD`, клиент пишет `WARN` (`TUNSETOFFLOAD failed; TUN offload state may be stale`) и работает без GRO; TSO на записи продолжает работать.

## Что делает `uso = true`

Требует `gso`; `uso = true` при `gso = false` — ошибка конфига (`tun.uso requires tun.gso`).

- Вызывает `TUNSETOFFLOAD` с `TUN_F_CSUM | TUN_F_USO4 | TUN_F_USO6`, так что writer может отдать ядру один суперсегмент `GSO_UDP_L4` (не больше 64 датаграмм, `UDP_MAX_SEGMENTS`, и не больше 61 440 байт payload), который ядро режет на датаграммы размера `gso_size`. Это UDP-аналог TCP TSO из `gso` на пути записи.
- Downlink (запись): per-flow reader сливает подряд идущие датаграммы одного размера одного потока (4-tuple фиксирован, поэтому все идут одному адресату) в один суперсегмент с частичной (pseudo-header) контрольной суммой, которую ядро досчитывает на каждую датаграмму. Датаграмма другого размера завершает пачку и начинает следующую; датаграммы не теряются. Экономия больше всего на bulk QUIC-видео, где downlink — тяжёлое UDP-направление.
- `TUN_F_USO` включает и RX UDP GRO: ядро может отдать нам слитые UDP-суперпакеты при чтении, и цикл чтения разбивает их обратно на датаграммы (`resegment_udp_gso`).
- `TUN_F_CSUM` (обязателен для USO) включает RX checksum offload; цикл чтения пересчитывает недосчитанные контрольные суммы.
- Если ядро отвергает USO (ядро < 6.2), клиент пишет `TUNSETOFFLOAD rejected USO; UDP GSO disabled, TCP offload kept` и оставляет TCP offload.

## Включение

Все три включены по умолчанию: `gso` по умолчанию `true`, `gro` и `uso` по умолчанию равны `gso`.

```toml
[tun]
gso = true   # downlink TSO (по умолчанию)
gro = true   # uplink GRO (по умолчанию: следует за gso)
uso = true   # downlink UDP USO (по умолчанию: следует за gso)
```

Только Linux; на других платформах игнорируется. Требования:

- `gso` требует ядро с `IFF_VNET_HDR`. Если `TUNSETIFF` с `IFF_VNET_HDR` не прошёл, клиент подключается без него, пишет `TUNSETIFF with IFF_VNET_HDR failed; attached without it — TUN GSO/GRO/USO disabled` и работает по пакету.
- `gro` и `uso` требуют `TUNSETOFFLOAD`; `uso` требует `TUN_F_USO` (ядро ≥ 6.2). Отвергнутый offload логируется, остальное сохраняется.
- `gro` и `uso` задаются независимо друг от друга, но каждый требует `gso = true`.

## Проверка

Все три пути — в data plane, поэтому сначала проверьте целостность данных, потом CPU:

1. Задайте ключи и перезапустите клиент.
2. Downlink (`gso`): скачайте большой файл через туннель и сравните его `sha256sum` с оригиналом. Хеши должны совпасть.
3. Uplink (`gro`): загрузите большой файл через туннель и сравните его `sha256sum` на дальней стороне.
4. UDP (`uso`): проверьте, что DNS резолвится и QUIC-трафик (например, YouTube) воспроизводится, затем прогоните bulk-передачу по UDP. Рост `outline_ws_tun_packets_total{outcome="uso_supersegment"}` означает, что downlink-датаграммы сливаются.
5. Сравните CPU и частоту syscall с выключенным offload при той же скорости: `sudo timeout 5 strace -f -c -p $(pidof outline-ws-rust)`. С `gso` падает число `write`; с `gro` на bulk-загрузке — число `read`.

Строки лога при старте `TUN offload negotiated` (поля `req_gso`, `req_gro`, `req_uso`, `vnet_hdr`, `rx_gro`, `udp_gso`) и `TUN loop started` (поля `gso`, `rx_gro`, `udp_gso`) показывают, что приняло ядро.

Состояние offload в `ethtool -k <tun>`:

- `gso` (TSO на записи) в `ethtool` не виден. Он работает через `virtio_net_hdr` в каждом `read`/`write` на fd, открытом с `IFF_VNET_HDR`; это свойство очереди, а не netdevice-фича. Подтверждение — только строки лога выше.
- `gro` и `uso` видны, потому что `TUNSETOFFLOAD` выставляет настоящие netdevice-фичи. При обоих включённых должны быть `on`: `tx-checksum-ip-generic` (`TUN_F_CSUM`), `tx-tcp-segmentation` и `tx-tcp6-segmentation` (`gro`, `TUN_F_TSO4/6`), `tx-udp-segmentation` (`uso`, `TUN_F_USO4/6`). Работающий `uso` показывает `tx-udp-segmentation: on` без хвоста `[requested on]`; форма `[requested on]` — залипшее состояние из раздела [Известные проблемы](#известные-проблемы).
- `generic-segmentation-offload` и `generic-receive-offload` — собственные software GSO/GRO ядра для устройства, клиент их не выставляет; игнорируйте их.

## Откат

- `gso = false` возвращает обработку по пакету; `gro` и `uso` следуют за ним, если не заданы явно (любой из них в `true` при `gso = false` не даст загрузить конфиг). Пересборка не нужна, только перезапуск.
- `gro = false` убирает только GRO на uplink; TSO на downlink остаётся.
- **Внимание:** не ставьте `uso = false` при `gso = true`. С `IFF_VNET_HDR` ядро оформляет локальный UDP-GSO (исходящий QUIC/HTTP3 приложений на хосте) как суперпакеты `GSO_UDP_L4`, которые доходят целыми только при включённом `TUN_F_USO`. `gso` без `uso` ломает UDP через туннель. `uso = false` используйте только как диагностический шаг, а для отката — вместе с `gso = false`.

## Известные проблемы

`TUNSETOFFLOAD` выставляет feature-флаги на устройстве, и на persistent TUN-интерфейсе они переживают рестарт процесса. Клиент явно выставляет состояние offload при каждом подключении к устройству (в том числе `0`, когда offload выключен), поэтому обычно достаточно рестарта, чтобы применился новый конфиг. Если после рестарта `ethtool -k <tun>` показывает `tx-udp-segmentation: off [requested on]`, выполните настоящий переход флага командой `ethtool -K <tun> tx-udp-segmentation off` и перезапустите клиент либо пересоздайте интерфейс (`ip link del` / `ip tuntap add`).
