# Генерация access-key артефактов

Генератор клиентских конфигов для узлов `outline-ss-rust`
(`generate_keys.py`, python3, только stdlib). Читает `config.toml` узла и пишет
до четырёх файлов на юзера в тот же каталог, откуда их раздаёт nginx.

Реальные имена узлов, домены и адреса парка в этом документе заменены условными: `fleet.example` — домен парка; `relay-a`…`relay-d` — промежуточные cloud-узлы; `exit-a`…`exit-e` — выходные узлы. Соответствие — в локальном некоммитируемом `FLEET.local.md`.

Дизайн: [`docs/superpowers/specs/2026-08-11-access-keys-to-python-design.md`](../../docs/superpowers/specs/2026-08-11-access-keys-to-python-design.md),
ws-rust-конфиг — [`docs/superpowers/specs/2026-08-15-ws-rust-config-generator-design.md`](../../docs/superpowers/specs/2026-08-15-ws-rust-config-generator-design.md).

| Файл | Условие | Содержимое |
|---|---|---|
| `<user>.conf` | есть `password` и на сервере есть пара сплит-ног `ws_ss_tcp` + `ws_ss_udp` | Outline YAML |
| `<user>.json` | есть `vless_id` и непадед VLESS-эндпоинт | Xray-подписка с балансером по узлам из `--node` |
| `<user>.toml` | есть хоть один wire | конфиг `outline-ws-rust` для Android-клиента |
| `<user>.txt` | есть хоть один URL | все URL юзера, по одному в строке |

Первая строка `<user>.txt` — `ssconf://` на собственный `.conf` (ссылка для
Outline-клиента; только если `.conf` создаётся и `url_base` известен), дальше
`ss://` и `vless://` по носителям в том же порядке, в каком их генерировал
бинарь.

## Откуда это взялось

Раньше `.conf` генерировал сам `outline-ss-rust` (режим `--write-access-keys-dir`),
и на юзера приходилось до семи файлов — по одному на носитель. Правка формата
ссылок требовала пересборки бинаря и выкладки на весь парк, а совместимость с
xray-клиентами правилась много раз подряд.

При переносе URI не изменились ни на байт — поменялась только раскладка по
файлам. Генерация в бинаре с тех пор удалена, и golden-корпус в
[`golden/`](golden/) (синтетический конфиг плюс 17 артефактов) снят уже с
Python-генератора: это regression-anchor самого генератора, а не доказательство
эквивалентности с Rust. Подробности и команда пересъёмки — в
[`golden/README.md`](golden/README.md).

## Запуск

```bash
sudo /opt/outline/access-keys/generate_keys.py
```

| Флаг | Значение по умолчанию |
|---|---|
| `--config` | `/etc/outline-ss-rust/config.toml` |
| `--out-dir` | из `[access_keys] write_dir`; своего дефолта нет |
| `--file-extension` | из `[access_keys] file_extension`, иначе `.yaml` |
| `--node` | `relay-a.fleet.example`, `relay-b.fleet.example`; повторяется на каждый узел |
| `--dry-run` | всё отрендерить, ничего не писать |

Генератор падает с ошибкой, если в конфиге нет ни одного включённого юзера.

## Секция `[access_keys]`

```toml
[access_keys]
public_host = "cloud.fleet.example"
file_extension = ".conf"
write_dir = "/var/www/html/<keys-dir>/"
```

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `public_host` | нет, обязателен | хост в ссылках |
| `file_extension` | `.yaml` | расширение Outline-артефакта (`.json`, `.toml`, `.txt` от него не зависят) |
| `write_dir` | нет | куда пишутся артефакты; из него же выводится `url_base` |
| `public_scheme` | `wss` | `wss` или `ws`; задаёт схему выведенного URL (`wss` → `https`, `ws` → `http`) и наличие TLS/ALPN в ссылках |
| `url_base` | выводится | явный URL каталога раздачи; явное значение всегда побеждает |
| `print` | — | генератор не читает |

`url_base` выводится как `public_host` плюс путь `write_dir` относительно корня
nginx (`/var/www/html`, константа `NGINX_DOCUMENT_ROOT` в `config_model.py`).
Вложенный каталог сохраняет весь путь: `/var/www/html/keys/prod` → `/keys/prod`,
а не `/prod`.

Из `write_dir` вне корня nginx `url_base` не выводится: URL-путь из пути в
файловой системе там неизвестен, а угаданный путь дал бы артефакты со ссылками в
несуществующий каталог. Такой узел должен прописать `url_base` явно; явное
значение нужно и в случае, когда артефакты раздаются не с того хоста, куда
записаны.

Сервер секцию `[access_keys]` парсит и игнорирует
(`bins/outline-ss-rust/src/config/loader.rs`), она целиком принадлежит
генератору.

### Узел без раздачи

На `.102` и `.104` nginx выключен: артефакты нужны на диске, но публиковать их
некому. Там `write_dir` указывает вне вебрута — `/opt/outline/access-keys-out/`.
Из этого следует:

- `url_base` не выводится, поэтому в `<user>.txt` не попадает `ssconf://`, а в
  отчёте нет `outline_url`, `happ_url` и `ws_url`. Остаются `ss://` и
  `vless://` — они адресуют прокси-порт узла, а не HTTP-раздачу;
- файлы с паролями и `vless_id` не лежат в каталоге, который станет публичным,
  если на узле однажды поднимут nginx.

«Раздаём / не раздаём» выражено местом хранения, а не отдельным флагом, и в
генераторе нет условий про конкретные узлы.

## Каталог раздачи — секрет, и живёт он в `config.toml`

Имя каталога ничем, кроме неугадываемости, не защищено: nginx раздаёт его без
авторизации, а `<user>.conf` / `<user>.json` / `<user>.txt` / `<user>.toml`
несут пароль и `vless_id`. Кто знает путь — знает креды всех юзеров узла,
перебрав имена.

Поэтому путь задаётся на узле, ключом `[access_keys] write_dir` в
`config.toml`, и в репозиторий не попадает. Встроенного дефолта у генератора
нет намеренно: он был бы публикацией секрета в исходниках. Без `write_dir` и
без `--out-dir` генератор падает с ошибкой `no output directory`, ничего не
записав.

Тот же префикс нужен nginx-блоку подписок — там он остаётся плейсхолдером
`__KEYS_PREFIX__` (см. [`nginx-subscription-headers.conf`](nginx-subscription-headers.conf)),
как токен в [`ops/heartbeat/nginx-heartbeat.conf`](../heartbeat/nginx-heartbeat.conf).

Расширение на узлах задаёт флаг: в боевых `config.toml` ключа
`file_extension` нет, и `save-keys.sh` вызывает генератор с
`--file-extension .conf`. Без флага генератор возьмёт дефолт `.yaml`, и
клиенты, которые ходят за `<user>.conf`, получат 404. Ключ `file_extension` в
`[access_keys]` работает так же, если флаг не передан.

`--node` задаёт узлы балансера в `.json` и узлы-аплинки в `.toml`. На
cloud-узлах это пара relay-a+relay-b (дефолт). На `exit-a` / `exit-b` передаётся
собственный хост: там подписка должна вести на тот узел, который её и раздаёт,
а не на cloud-пару.

Отчёт печатается в stdout — `save-keys.sh` перенаправляет его в `users.txt`.
Блок на юзера:

```
user: <id>
written_conf: <путь>        # если создан .conf
written_json: <путь>        # если есть vless_id и непадед VLESS-эндпоинт
written_toml: <путь>        # если есть хоть один wire
written_txt: <путь>
outline_url: ssconf://…/<user>.conf    # ссылка для Outline-клиента
happ_url: https://…/<user>.json        # ссылка для Happ и прочих xray-клиентов
ws_url: https://…/<user>.toml          # ссылка для Android-клиента
warning: …                             # выключенная серверная фича, см. ниже
```

Строк, которых у юзера быть не может, нет: у SS-only нет `happ_url`, у
VLESS-only — `outline_url` и `written_conf`. В stderr генератор печатает число
юзеров и узлов балансера.

`outline_url` — тот же файл, что `written_conf`, но со схемой `ssconf://`:
Outline ходит по ней как по динамическому ключу и перечитывает конфиг при
изменении. `happ_url` всегда с расширением `.json`, `ws_url` — с `.toml`:
`file_extension` относится только к Outline-артефакту.

Отдельного `config_url` (та же ссылка, но `https://`) в отчёте нет: он
дублировал `outline_url` схемой, а сама ссылка и так лежит первой строкой в
`<user>.txt`. Старый бинарь печатал блок на артефакт, а не на юзера; отчёт
никто не парсит.

Запись атомарная (временный файл `.<имя>.tmp` + `os.replace`) — клиент не
получит полузаписанный файл. Артефакты создаются сразу с правами `0640`
(`root:www-data`: раздающая группа читает, остальные — нет), а не `0644`;
временный файл открывается тем же режимом. Новый каталог создаётся `0750`,
у существующего режим не меняется. `.tmp`-остаток после сбоя nginx не отдаёт —
dotfile-раздача закрыта (`location ~ /\.` в `nginx-subscription-headers.conf`).

Группа `www-data` выставляется явно. `0640` работает только вместе с правильной
группой: файл, оставшийся `root:root`, worker'у nginx недоступен, и каждая
подписка отвечает `403` с момента перегенерации — узнают об этом клиенты, а не
прогон. Поэтому `write_atomic` делает `fchown` на группу `www-data`, а если её
нет или прогон не от root — печатает в stderr
`WARNING: could not set group 'www-data' …` с прямым указанием на 403.

Проверить результат, не показывая креды:

```bash
sudo jq -r '.[0].outbounds[].tag' <keys-dir>/<user>.json   # <keys-dir> = [access_keys] write_dir
```

`cat` любого артефакта выводит пароль или `vless_id` — не делайте этого.

## Как разрешаются поля

Пользователи — чистые креды: `id`, `password`, `vless_id`, `method`. Своих
путей у них нет — носители задаёт глобальный список `[[endpoint]]` со строками
`{path, kind, padded}`, и юзер работает на каждом эндпоинте своего типа: с
`password` — на SS-эндпоинтах (`ws_ss*` / `xhttp_ss*`), с `vless_id` — на
VLESS-эндпоинтах (`ws_vless` / `xhttp_vless`). `method` берётся на юзера: своё
значение в `[[users]]` бьёт глобальное из `[shadowsocks]`, без обоих —
`chacha20-ietf-poly1305`. Так же это разрешает сервер.

`enabled = false` исключает юзера целиком; юзер без `password` и без
`vless_id` пропускается. Юзер без `password` не получает `.conf`, без
`vless_id` (или без непадед VLESS-эндпоинта на сервере) — `.json`. Дубликат
`id` — ошибка. Имя файла — `id`, в котором всё, кроме ASCII-букв, цифр и
`._-`, заменено на `_`.

## ALPN в ссылках

Параметр `alpn` в share-ссылках (`<user>.txt` и `link` в `<user>.toml`)
зависит от носителя и от того, поднят ли на сервере h3 (`uri.alpn_list`):

| Носитель | `[server.h3]` поднят | иначе |
|---|---|---|
| WS | `h3,h2,http/1.1` | `h2,http/1.1` |
| XHTTP `packet-up` | `h3,h2,http/1.1` | `h2,http/1.1` |
| XHTTP `stream-one` | `h3,h2` | `h2` |

`stream-one` не получает `http/1.1`: поверх h1 сервер отвечает 505 (hyper не
умеет full-duplex), и клиент, выбравший h1, отваливался бы на каждом дозвоне.
При `public_scheme = ws` параметра нет вовсе — ALPN это расширение TLS.

Признак «h3 поднят» считается как в Rust (`effective_h3_listen`): у
`[server.h3]` задан `listen` и h3 включён — есть пара сертов (своя, иначе
унаследованная от `[server]`) либо непустой массив `certs`. `[server.h3].certs`
наследует `[server].certs`, только если ключ опущен целиком; явный `certs = []`
от наследования отказывается.

В `<user>.json` у xray-клиента `alpn` выбирает ровно одну версию HTTP, а не
список предпочтений. Поэтому каждая xhttp-нога (`stream-one`) там размножена на
две outbound-записи — `h3` и `h2` — на каждый узел, а WS-ноги стоят на
`http/1.1`. Это ограничение клиента: `outline-ss-rust` умеет WebSocket поверх h2
(RFC 8441) и h3 (RFC 9220), а `wsSettings` у xray — только HTTP/1.1 Upgrade.

## Порядок outbounds в `.json`

Прокси-ноги идут первыми (при двух узлах и обоих VLESS-путях — шесть:
`xhttp-h3`, `xhttp-h2`, `ws` на каждый узел), `direct` и `block` — последними.
Балансер `leastPing` до первой пробы отправляет трафик в `outbounds[0]`; окажись
там `direct`, первые ~30 секунд трафик шёл бы мимо туннеля.

Следствие того же механизма, проверенное на живом ядре: если мертва именно
нога №1, первое соединение после старта отобьётся, а со второй попытки
балансер уже опирается на пробы. Это ожидаемое поведение.

Пробы (`burstObservatory`) идут на `https://www.gstatic.com/generate_204` с
интервалом 30 с и таймаутом 5 с через тот outbound, который измеряют.

Подписка строится по первому непадед `ws_vless` и первому непадед
`xhttp_vless` эндпоинту: Xray паддинг не умеет. Если у сервера все
VLESS-эндпоинты padded, `.json` не создаётся.

## Конфиг ws-rust для Android (`<user>.toml`)

Один `[[outline.uplinks]]` на узел из `--node`, внутри — цепочка носителей
через `[[outline.uplinks.fallbacks]]`. Все wire'ы заданы share-link'ами — теми
же, что лежат в `<user>.txt`, поэтому две формы не расходятся, а креды едут
внутри ссылки и в самом аплинке не повторяются.

Порядок цепочки при генерации: `vless-xhttp stream-one` → `vless-ws` → `ss-ws`
→ `ss-xhttp stream-one` → `vless-xhttp packet-up`. Отсутствующий эндпоинт или
кред убирает свой wire: SS-only юзер получает два, VLESS-only — три (по одному
эндпоинту каждого типа). Сплит-ноги `ws_ss_tcp` / `ws_ss_udp` в цепочку не
попадают — у них нет share-ссылки.

ALPN, в отличие от `.json`, wire'ы не размножает: ws-rust читает первый токен
как запрошенный режим и понижает носитель внутри wire'а сам
(`ws_h3 → ws_h2 → ws_h1`).

Что пишет генератор (константы в `ws_toml.py`):

| Ключ | Значение | Зачем |
|---|---|---|
| `[tun] path`, `mtu` | `"vpn"`, `1500` | дескриптор TUN приходит от `VpnService`; MTU обязан совпадать с `ServerProfile.TUN_MTU` |
| `[tun.tcp] sniffing` | `true` | exit-узел должен получить домен, а не локально резолвленный IP |
| `[tun.tcp] carrier_migration` | `true` | без Session ID на сервере ни на что не влияет |
| `[padding] enabled` | по правилу ниже | |
| `[[uplink_group]] mode`, `routing_scope` | `active_passive`, `global` | один узел несёт весь трафик, выходной IP стабилен |
| `shared_resume` | `true`, если на узле `[cluster] enabled` | мягкая смена активного узла |
| `reselect_interval` | `"6h"` | единственное, что возвращает клиента с резервного узла: `auto_failback` не пишется |
| `tun_wire_dial` | `true` | по умолчанию `false`, и тогда каждый TUN-дозвон уходит на wire 0, а цепочка fallback'ов не работает; на Android весь трафик идёт через TUN |
| `health_weighted_selection` | `true` | |
| `shuffle_wires` | `true` | цепочка перемешивается при загрузке, первичный носитель не всегда одной формы |
| `shuffle_timer` | от `30m` до `60m` | период смены активного wire'а; стабильный хеш sha256 от юзера и узла, поэтому перегенерация не меняет файл |

Профиль экономии энергии (без тёплого резерва и замера потерь, растянутые
keepalive H2/QUIC) сюда не пишется: приложение применяет его само
(`MobilePowerConfig.kt`).

### Пробы

`[outline.probe]` повторяет состав проб группы `main` на relay-a: DNS-проба и
TLS-рукопожатия через туннель к тем же пяти хостам, плюс `endpoint_check` —
bare-TCP обход всех wire'ов, который запускается только после цикла, проваленного
на всех wire'ах (выключенный exit тогда объявляется мёртвым сразу, без обхода
носителей).

| Ключ | Значение |
|---|---|
| `interval_secs` | `300` |
| `timeout_secs` | `10` |
| `min_failures` | `2` |
| `attempts` | `1` |
| `endpoint_check` / `endpoint_check_timeout_ms` | `true` / `2000` |
| `[outline.probe.dns]` | `1.1.1.1:53`, имя `google.com` |
| `[outline.probe.tls] targets` | `www.instagram.com`, `www.youtube.com`, `www.googletagmanager.com`, `www.googlevideo.com`, `api.telegram.org` |

Без проб — а именно так профиль генерировался раньше — `healthy` пишет только
data plane, и клиент, у которого разом отвалились все аплинки (смена SIM,
мёртвая сота), не может узнать, что они вернулись; интерфейсу нечего показать в
качестве латентности. Это и давало вечное «no link» на телефоне.

Осознанное отличие от relay-a — интервал: парк пробит каждые 10 с от сети и по
широкому каналу, а телефон заплатил бы за это батареей и полосой на тех
мобильных каналах, ради которых всё затевалось. Без трафика ожившие аплинки
замечаются со следующим циклом проб, то есть в пределах 300 с. `attempts = 1`
по той же причине: `min_failures = 2` уже гасит одиночный флап, а вторая
попытка удваивала бы цену каждого цикла.

Три серверные настройки меняют то, что клиент реально получит; о каждой
выключенной генератор докладывает строкой `warning:`:

| Настройка в `config.toml` узла | Что даёт клиенту | Если выключена |
|---|---|---|
| `[session_resumption] enabled` | миграцию живого флоу на смерти носителя | флоу рвётся |
| `[session_resumption] downlink_buffer_bytes` | реплей downstream-хвоста (предупреждение советует `65536`, как у клиентского кольца) | в мигрировавшем ответе остаётся дыра |
| `[cluster] enabled` | `shared_resume` — мягкую смену активного узла | смена узла рвёт сессии RST |

Паддинг — атрибут эндпоинта (`padded = true`) и решается по правилу «только
падед, если они есть». Если среди носителей цепочки есть хоть один падед,
генератор оставляет в `<user>.toml` только падед wire'ы и пишет клиентский
`[padding] enabled = true`; иначе оставляет все (плоские) и `enabled = false`.
Переключатель клиента глобальный (per-wire override нет), а паддинг не
согласуется по проводу — падед кадры на непадед пути убивают сессию, поэтому
цепочка держится одного класса. Отброшенные плоские пути генератор перечисляет
строкой `warning:`.

Формат закреплён фикстурами в [`golden/expected-ws/`](golden/expected-ws/) — это
побайтовые копии `both.toml` и `ss-only.toml` из `golden/expected/`. Что
фикстура — загружаемый конфиг, а не просто валидный TOML, проверяет Rust-тест
`generated_android_config_fixture_loads`
(`bins/outline-ws-rust/src/config/tests/mod.rs`): у схемы ws-rust
`deny_unknown_fields`, и лишний ключ ронял бы бинарь на старте.

## Раскатка

```bash
ssh sysadm@<node> 'sudo -n install -d -o root -g root -m 0755 /opt/outline/access-keys'
rsync -a --delete --exclude '__pycache__' --exclude 'test_*.py' --exclude 'golden' \
  ops/access-keys/ sysadm@<node>:/tmp/access-keys/
ssh sysadm@<node> 'sudo -n cp -a /tmp/access-keys/. /opt/outline/access-keys/ \
  && rm -rf /tmp/access-keys && sudo -n chown -R root:root /opt/outline/access-keys \
  && sudo -n chmod 0755 /opt/outline/access-keys/generate_keys.py'
```

`<node>` — FQDN узла (`relay-a.fleet.example` и т. п.). Раскатывайте по одному узлу
за раз. Рестарт сервисов не нужен: пишутся файлы, которые nginx уже раздаёт с
диска. На узле генератор вызывается из
`/opt/outline/outline-ss-rust/save-keys.sh` вместо прежнего
`outline-ss-rust --write-access-keys-dir`; при провижининге его запускает фаза
`services` в `ops/provision-node/install.sh` (`ACCESS_KEYS_REGEN=1`).

Генератор без встроенного дефолта каталога работает только на узле, где задан
путь. Один раз на узел:

```bash
# 1) прописать каталог в config.toml, в секцию [access_keys]
#    write_dir = "/var/www/html/<keys-dir>"
# 2) проверить, что генератор его видит — ничего не записывая
sudo /opt/outline/access-keys/generate_keys.py --dry-run
```

Флаги `--out-dir` и `--file-extension` перекрывают конфиг и нужны для разовой
генерации в сторону.

Раскатка 2026-08-11 (состав парка на ту дату; `exit-e` с тех пор выведен,
`exit-d` и `exit-c` недоступны из РФ):

| Узлы | `--node` | Раздача |
|---|---|---|
| `relay-a`, `relay-b` | по умолчанию, пара relay-a+relay-b | да, вход мобильных клиентов |
| `exit-a`, `exit-b`, `exit-d`, `exit-c`, `exit-e` | свой хост | да |
| `.102`, `.104` | `ss.fleet.example` | нет — nginx там выключен |

На `.102` / `.104` юзер ровно один — служебный `cloud`, через который cloud-узлы
держат обратные аплинки; его креды они берут из своих конфигов, а не из
выложенного файла. Артефакты там генерируются на диск, чтобы ссылка была под
рукой, но не публикуются: для этого пришлось бы поднять веб-сервер на домашнем
адресе. `public_host` там `ss.fleet.example`, и порт в ссылках — 443, тогда как
наружу проброшены 5443 (`.104`) и 6443 (`.102`).

На `exit-c`, `.102` и `.104` не было `rsync` — туда заливали через
`tar czf - … | ssh … tar xzf -`. На `.102` стоит `sshguard`, который банит весь
трафик с IP после серии подключений: работайте через
`ssh -o ControlMaster=auto -o ControlPath=… -o ControlPersist=10m`.

Что раскатка вскрыла на узлах:

- на `exit-b` и `exit-e` `url_base` указывал на каталог, отличный от того, куда
  писал `save-keys.sh`; раздавались устаревшие файлы, а актуальные лежали рядом.
  Приведено к одному каталогу на обоих (тому, что в `[access_keys] write_dir`);
- на `exit-a`, `exit-c`, `exit-d` артефакты не обновлялись месяцами и разошлись с
  конфигом (на `exit-e` разошлись все 62 — там ротировали пути и креды);
- в каталогах копились файлы старых схем именования (`<user>-vless.conf`) и
  удалённых юзеров. Перед чисткой они архивировались в `/var/backups/`.

## Заголовки подписки

Заголовки `profile-title` и `profile-update-interval` (`12`) добавляет nginx —
блок в [`nginx-subscription-headers.conf`](nginx-subscription-headers.conf),
вставляется в `server`-блок `sites-available/fleet.example`. Покрывает `.json`,
`.toml` и `.txt`; `.conf` намеренно вне: это одиночный Outline-конфиг, а не
подписка.

Блок вставлен только на relay-a и relay-b (вход мобильных клиентов). На
`exit-a` / `exit-b` его нет, поэтому там все формы раздаются без заголовков.

Внимание: проверяйте заголовки с `--resolve` на конкретный узел.
`cloud.fleet.example` резолвится в оба cloud-узла, и обычный `curl` может попасть
на соседний, где правка ещё не применена, и показать «заголовков нет».

```bash
curl -sS -D- -o /dev/null --resolve cloud.fleet.example:443:127.0.0.1 \
  https://cloud.fleet.example/<keys-dir>/<user>.toml | grep -i profile-
```

`ops/provision-node/collect-from-reference.sh` определяет каталог ключей из
`[access_keys] write_dir`, а если его нет — из `save-keys.sh` (`--out-dir`,
затем `--write-access-keys-dir`): все три формы встречались на узлах.

## Известная слепая зона

Пробы observatory в `.json` идут через ту же ногу, что и трафик, поэтому падение
узла и деградацию пути они ловят. Отказ вида «узел отвечает, а трафик утёк
мимо туннеля» — как 2026-08-11, когда `systemd-networkd` снёс `ip rule` на
`ws0`, — прошёл бы зелёными пробами.
