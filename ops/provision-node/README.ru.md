# provision-node — клонирование настроенного узла парка на чистый хост

Три скрипта, которые берут рабочий узел (*эталон*) и воспроизводят его на
пустом: пакеты, `/opt`, бинари, systemd-юниты, nginx, sysctl, docker-нагрузки,
root-crontab и секреты, которые всё это связывают.

Реальные имена узлов, домены и адреса парка в этом документе заменены условными: `fleet.example` — домен парка; `relay-a`…`relay-d` — промежуточные cloud-узлы; `exit-a`…`exit-e` — выходные узлы; `198.51.100.0/24` — домашняя сеть (`.102`, `.104` и т. д. — последний октет); `203.0.113.x` — публичные адреса. Соответствие — в локальном некоммитируемом `FLEET.local.md`.

Что именно составляет «узел», зависит от семейства узлов, поэтому всё это
вынесено в профиль в каталоге `profiles/`. Сами скрипты не знают ничего
про конкретное семейство, а выбранный профиль копируется в бандл — бандл
самодостаточен на целевой машине.

| Профиль | Семейство | Состав |
|---|---|---|
| `relay-a` | узел-вход | ss+ws, ocserv, unbound+dnsproxy, ddns контейнером, netplan, только IPv4 |
| `exit-a` | узел-выход | ss-rust, dumbproxy, unbound+dnsproxy, ddns контейнером, IPv6 `/64` + ndppd |

Оба сделаны по живым узлам (Ubuntu 24.04, x86_64); имена хостов нигде не
зашиты.

| Скрипт | Где запускается | Что трогает |
|---|---|---|
| `collect-from-reference.sh` | рабочая станция | читает эталон по ssh, пишет бандл локально |
| `install.sh` | новый узел, от root | всё на этом узле |
| `register-uplink-user.sh` | рабочая станция | заводит по одному юзеру на каждом соседе через его control API |

## Порядок

```bash
# 1. Снять эталон (только чтение; ничего там не перезапускается)
./collect-from-reference.sh --reference sysadm@relay-a.fleet.example \
    --profile relay-a --out ./bundle-relay-a

# 2. Объявить новый узел соседям, через которых он ходит
./register-uplink-user.sh --user relay-b --template relay-a --out ./relay-b-uplink-creds \
    --peer exit-a:sysadm@exit-a.fleet.example \
    --peer exit-c:sysadm@exit-c.fleet.example \
    --peer exit-d:sysadm@exit-d.fleet.example \
    --alias-cidr 203.0.113.50/32 \
    --alias-peer mmv@198.51.100.104:cloud \
    --alias-peer mmv@198.51.100.102:cloud

# 3. Доставить бандл и скрипты на новый узел
rsync -a --delete ./bundle-relay-a/ sysadm@relay-b.fleet.example:/tmp/provision-bundle/
rsync -a ./ sysadm@relay-b.fleet.example:/tmp/provision-node/
rsync -a ./relay-b-uplink-creds sysadm@relay-b.fleet.example:/tmp/

# 4. Сначала dry-run, потом установка
ssh sysadm@relay-b.fleet.example 'sudo /tmp/provision-node/install.sh \
    --bundle /tmp/provision-bundle --host relay-b \
    --uplink-creds /tmp/relay-b-uplink-creds \
    --shared-uplink fleet-1 --shared-uplink fleet-2 --dry-run'

ssh sysadm@relay-b.fleet.example 'sudo /tmp/provision-node/install.sh \
    --bundle /tmp/provision-bundle --host relay-b \
    --uplink-creds /tmp/relay-b-uplink-creds \
    --shared-uplink fleet-1 --shared-uplink fleet-2'
```

Список `--peer` в шаге 2 — тот, с которым регистрировался relay-b. `exit-c` и
`exit-d` из РФ больше недоступны [проверить: актуальные имена uplink'ов группы
`main` в `/etc/outline-ws-rust/config.toml` эталона, прежде чем копировать
команду].

Шаг 2 нужен только узлу-входу. Узел-выход ни к кому не дозванивается, поэтому
клонирование `exit-a` — это собрать → доставить → установить:

```bash
./collect-from-reference.sh --reference sysadm@exit-a.fleet.example \
    --profile exit-a --out ./bundle-exit-a

ssh sysadm@<new-node> 'sudo /tmp/provision-node/install.sh \
    --bundle /tmp/provision-bundle --host exit-b \
    --ipv6-prefix 2a0f:cdc6:500:XXX::/64'
```

Именно `--ipv6-prefix` делает dual-stack клон отдельным узлом: префикс
переписывает `ndppd.conf` и `[outbound] ipv6_prefix` в конфиге ss-rust
(`REHOST_IPV6_FILES` в профиле `exit-a`), которые иначе так и продолжат называть
`/64` эталона. Без флага `install.sh` берёт первый глобальный префикс из
`ip -6 route show proto kernel` (кроме `fe80`, `fc`, `fd`). Только если такого
нет, `preflight` предупреждает `no --ipv6-prefix given`, и перезапись
пропускается. Если на хосте больше одного глобального префикса, передавайте
флаг явно.

ss-rust щупает префикс на старте и пишет либо `outbound IPv6 startup probe
succeeded`, либо `… failed for all attempts; disabling random outbound IPv6
source`. Если проба падает, проверять в таком порядке:

1. `/etc/ndppd.conf` и `[outbound] ipv6_prefix` — там `/64` *этого* узла?
   Если в любом из них остался префикс эталона, ndppd отвечает на neighbour
   solicitation за чужую подсеть, и все адреса настоящего `/64` недостижимы.
   Это наиболее вероятная причина после частичного повторного прогона — см.
   «Повторный прогон» ниже.
2. И только потом подозревать площадку: некоторые провайдеры маршрутизируют
   лишь один назначенный адрес, а не весь префикс. Сервер откатывается на адрес
   по умолчанию и продолжает работать, но ротация мертва, пока провайдер не
   отдаст префикс маршрутом.

Проверка в обоих случаях одна — взять адрес из префикса и отправить с него:

```bash
ip -6 addr add <префикс-со-случайным-суффиксом>/128 dev lo
ping6 -c3 -I <этот-адрес> 2606:4700:4700::1111
ip -6 addr del <префикс-со-случайным-суффиксом>/128 dev lo
```

Одна вещь с эталона `exit-a` сознательно вынесена за рамки клона: GRE/BGP-туннели
`bgp0`/`bgp1`. Поскольку эти туннели описаны в `/etc/network/interfaces`
эталона, профиль `exit-a` не собирает сетевую конфигурацию вообще
(`NETWORK_PATHS=()`) — интерфейсы нового узла настраиваются до запуска
install.

Но два хука в этом файле относятся не к адресации, и без них клон нерабочий:

```
post-up /opt/network/ipset-init.sh            # → iptables-init.sh → весь
                                              #   firewall, включая v4/v6 MASQUERADE
up ip -6 route add local <prefix> dev lo      # принимать весь маршрутизируемый /64
```

Поэтому `install.sh` переизлагает их сгенерированным `post-up.service`
(oneshot, до `outline-ss-rust`, из `NET_BRINGUP_EXEC` профиля), подставляя
префикс этого узла; маршрут добавляется через `ip -6 route replace`, так что
повторный запуск юнита безвреден. Юнит ещё и
экспортирует `WAN_V6_PREFIX`, потому что `network-online.target` может быть
достигнут одним лишь IPv4: без этого firewall-скрипт рискует отработать раньше,
чем появится IPv6-адрес, молча пропустить правило v6-MASQUERADE и оставить его
отсутствующим до конца аптайма — ровно это и случилось на эталоне, где тот же
хук висит в ifupdown-секции `inet` и выполняется раньше секции `inet6`. На хосте с
netplan/networkd ifupdown-хуки всё равно никогда бы не сработали. Без этого
юнита узел поднимается без firewall и без NAT: узел-выход, который не
фильтрует и не форвардит.

### Чтобы policy-правило не пропадало (`NET_POLICY_RULE_GUARD=1`)

`post-up.service` отрабатывает один раз при загрузке, и на узле с клиентом его
последний шаг (`tunnel-init.sh` → `init-ws0.sh`) заводит правило, которое
отправляет помеченный клиентский трафик в туннель: `from all fwmark 0xa lookup
110`. Рестарт `systemd-networkd` это правило не переживает — networkd удаляет
все routing policy rules, которые завёл не он сам, а
`ManageForeignRoutingPolicyRules` по умолчанию `yes`. Автоматическое обновление
`systemd` перезапускает networkd среди дня, поэтому правило может исчезнуть на
узле, которого никто не касался.

Отказ при этом тихий и полный. Маршрут в таблице 110 и разметка nftables живы,
рвётся только последнее звено цепочки: каждое помеченное соединение уходит через
собственный публичный IP узла вместо туннеля. Аплинки здоровы, метрики зелёные,
в логах ни одной ошибки — узел ничего не проксирует, выглядя исправным.
На `relay-a` это стоило почти рабочего дня 2026-08-11.

Поэтому профиль, несущий туннель, ставит `NET_POLICY_RULE_GUARD=1`, а
`install.sh` пишет два слоя защиты:

- `/etc/systemd/networkd.conf.d/10-keep-foreign-rules.conf` —
  `ManageForeignRoutingPolicyRules=no`, networkd перестаёт удалять правило;
- `outline-ws0-routing.service` — `PartOf=`/`WantedBy=systemd-networkd.service`,
  так что рестарт networkd переигрывает `init-ws0.sh`, даже если правило всё же
  пропало.

`verify` засчитывает отсутствие правила хотя бы в одном семействе
(`ip rule show pref 910`, `ip -6 rule show pref 910`) как проваленную проверку
и печатает `ws0 policy rule missing`: без правила узел проходит все остальные
проверки как здоровый. Проваленные проверки суммируются в `N check(s) failed`;
ненулевым кодом скрипт по ним не выходит.

Сами firewall-скрипты переписывать не нужно: `iptables-init.sh` определяет
WAN-интерфейс, его адрес и маршрутизируемый `/64` во время выполнения, а
повторный запуск ничего не меняет (каждое правило добавляется через
`-C || -A`). Mesh-allow-лист в `iptables-update.sh` сознательно не трогается —
см. «Объявление узла в mesh» ниже. Флаги `--ipv4`, `--wan-if` и
`--ipv6-prefix` остаются для эталона, который всё ещё зашивает свою
идентичность, и чтобы поправить неверную догадку.

## Две конвенции у соседей

Парк опознаёт клиентский узел двумя разными способами, поэтому у скрипта
регистрации два режима:

- Учётка на узел (`--peer`, группа `main`: exit-a, exit-c, exit-d). Сосед держит
  по юзеру на узел. Новый узел получает собственную учётку, склонированную с
  учётки эталона: те же секретные пути и `fwmark`, свежие `vless_id`/пароль. Эти
  креды попадают в creds-файл, а `install.sh` подставляет их в соответствующий
  блок `[[outline.uplinks]]`.
- Общая учётка плюс alias (`--alias-peer`, группа `russia`: `.104`, `.102`).
  Все cloud-узлы ходят под одним юзером `cloud`, а различаются через
  `[users.aliases]` — переразметку учёта по адресу источника. Ничего не
  создаётся: `/32` нового узла добавляется в эту карту. Креды остаются общими,
  поэтому такие uplink'и объявляются флагом `--shared-uplink <name>` и
  сохраняют значения эталона.

Без `--shared-uplink` `install.sh` откажется работать, если у uplink'а нет
собственных кред, — опечатка в имени uplink'а останавливает прогон, а не
оставляет идентичность эталона. `--allow-shared-uplink-creds` сохраняет креды
uplink'ов эталона целиком; без него и без `--uplink-creds` `preflight`
останавливается на профиле с `REQUIRES_UPLINK_CREDS=1` (`relay-a`).

Ключ у `--peer` — это `name` uplink'а в конфиге ws-rust нового узла, а не имя
хоста. `--alias-peer` принимает `<ssh-target>:<общий-юзер>`, и карта алиасов
читается, сливается и записывается целиком — потому что control API заменяет её
целиком.

## Что принадлежит репозиторию, а не эталону

Почти всё, что получает новый узел, — копия того, что было на эталоне. Несколько
файлов устроены наоборот: они лежат в `assets/`, одинаковы на всех узлах
семейства, и `install.sh` кладёт их поверх того, что приехало в бандле. Профиль
перечисляет их в `ASSET_FILES`, а `%HOST%` / `%DOMAIN%` внутри ассета
раскрываются в идентичность устанавливаемого узла — так один файл несёт
пути к сертификатам, разные на каждом узле.

Сегодня это стек unbound, и попал он сюда ровно потому, что сбор с эталона —
это и есть механизм, по которому четыре боевых узла разъехались, и никто этого
не заметил (нашли и починили руками 2026-08-08):

- На `relay-a`/`relay-b` у `unbound-exporter` не было `restart: unless-stopped`,
  поэтому контейнер умирал при первой же перезагрузке узла и больше не
  поднимался. Никто не видел: сам unbound продолжал резолвить, а единственным
  симптомом была дыра в одном ряду Grafana.
- На `exit-a`/`exit-b` сервиса exporter не было вовсе, в `unbound.conf` стояло
  `control-enable: no` — которое всё равно оставило бы exporter без данных, — и
  в nginx не было location `/unbound-exporter/metrics`, так что даже рабочий
  exporter нечем было бы соскрести через 443.
- На всех четырёх была выключена `extended-statistics`, поэтому там, где
  exporter всё-таки работал, он отдавал 27 семейств метрик вместо 56, и 13 из
  21 панели дашборда Unbound оставались пустыми.

| Ассет | Куда ставится | Кем используется |
|---|---|---|
| `assets/unbound/unbound.conf` | `/opt/unbound/unbound.conf` | оба профиля |
| `assets/unbound/docker-compose.entry.yml` | `/opt/unbound/docker-compose.yml` | `relay-a` — unbound, unbound-exporter, dnsproxy |
| `assets/unbound/docker-compose.exit.yml` | `/opt/unbound/docker-compose.yml` | `exit-a` — unbound, unbound-exporter, dnsproxy |
| `assets/unbound/forward-zones.entry.conf` | `/opt/unbound/forward-zones.conf` | `relay-a` — гео-блокированные источники и зоны Google, форвард за границу |
| `assets/unbound/forward-zones.exit.conf` | `/opt/unbound/forward-zones.conf` | `exit-a` — пустой; include всё равно должен существовать |
| `assets/unbound/dnsproxy-cert-reload.sh` | `/opt/unbound/dnsproxy-cert-reload.sh` | оба — перезапускает dnsproxy, когда файл сертификата новее контейнера |
| `assets/unbound/dnsproxy-cert-reload.cron` | `/etc/cron.d/dnsproxy-cert-reload` | оба — гоняет скрипт раз в час |

Конфиг резолвера — один файл на оба семейства. По сравнению с тем, что сейчас
стоит на узлах-выходах, в нём на одну строку больше — `cache-max-negative-ttl:
60`, которая на узлах-входах уже была: без неё NXDOMAIN живёт `cache-max-ttl`,
то есть час, и имя, которое начало резолвиться, остаётся сломанным ещё долго
после того, как авторитативная сторона починена. Переустановленный узел-выход
эту строку получит.

Что *не* общее — список форвардимых зон: `unbound.conf` заканчивается строкой
`include: "/etc/unbound/forward-zones.conf"`, и каждый профиль кладёт туда свою
половину. Входная половина форвардит гео-блокированные зоны TMDB/Bunny на Quad9
и Mullvad, а `google.com` / `googleapis.com` — по DoT на dnsproxy самих
узлов-выходов, чтобы Google видел рекурсию из-за границы. Выходная половина
пустая — форвард Google на этом узле замкнулся бы сам на себя, — но unbound
отказывается стартовать без включаемого файла, поэтому ставится пустой файл, а
не никакой. До 2026-11-05 блок Google жил только на боевых cloud-узлах и успел
разъехаться: в апстримах числился выведенный из парка узел.

Этот форвард — и причина, по которой семейство выходов вообще держит dnsproxy,
и причина существования `dnsproxy-cert-reload`. dnsproxy читает
`--tls-crt`/`--tls-key` один раз при старте и больше никогда — ни SIGHUP, ни
слежения за файлом, — поэтому после продления через lego контейнер продолжает
отдавать старый сертификат на `:8853`/`:8443`, пока его не перезапустят, и
каждый DoT/DoH-клиент, проверяющий цепочку, отваливается от узла в момент
истечения старого. 2026-11-05 так лёг `google.com` для всего парка: dnsproxy на
exit-a отдавал сертификат, истёкший ещё 2026-10-14, на exit-b — истёкший тем же
утром, а продлённые файлы всё это время лежали рядом. Ежечасный cron сравнивает
mtime сертификата со временем старта контейнера и перезапускает dnsproxy, если
файл новее. Сам `/opt/fleet/update-certs.sh` он не трогает — тот остаётся
файлом эталона: отличается по семействам и несёт учётные данные DNS API.
Проверка узла снаружи:

```bash
openssl s_client -connect exit-a.fleet.example:8853 -servername exit-a.fleet.example </dev/null 2>/dev/null | openssl x509 -noout -enddate
```

Если эта дата отстаёт от даты на `:443` (ss-rust перечитывает сертификат сам),
dnsproxy после продления не перезапускался.

Две настройки в нём стоят ради дашборда, а не ради резолвера, поэтому менять их
можно только вместе с
[`ops/grafana/README.md`](../grafana/README.md#unbound): это
`extended-statistics: yes`, без которой `unbound-control stats_noreset` отдаёт
93 строки вместо 195 и 13 из 21 панели `unbound-dashboard.json` (uid
`9FQf4fEWz`) нечего рисовать, — и отсутствие `statistics-cumulative`, которая
exporter'у не нужна: он опрашивает `stats_noreset`, и дальше по цепочке
счётчики и так растут монотонно.

Exporter слушает `127.0.0.1:9167`, а скрейпится через nginx на 443 — значит, в
файле сайта нужен соответствующий `location`. Этот файл приезжает с эталона,
поэтому профиль объявляет location сам, а `install.sh` вставляет его в
последний блок `server`, если его там нет:

```
NGINX_LOCATIONS=( "/unbound-exporter/metrics:http://127.0.0.1:9167/metrics" )
```

Фаза `verify` проверяет обе половины — что exporter отвечает на 9167 и что сайт
действительно отдаёт этот location, — потому что вторая с самого узла не видна:
локально всё выглядит здоровым, а скрейп получает 404.

`assets/victoria-metrics/scrape-unbound-exporter.yaml` — четвёртая часть и
единственная, которую никто не применяет: scrape-конфиг принадлежит
VictoriaMetrics в k3s, а не устанавливаемому узлу. См. «Сознательно не
автоматизировано» ниже.

## Что лежит в бандле

```
MANIFEST            профиль, хост/ОС/архитектура/адреса/machine-id эталона, версии бинарей, каталог access-ключей
profile.conf        профиль, с которым собран этот бандл
assets/             перечисленные выше файлы репозитория, скопированы внутрь — бандл остаётся самодостаточным
SHA256SUMS          проверяется до запуска любой фазы (это не фаза, поэтому
                    --only/--skip её не обойдут); отсутствие или провал —
                    фатально (бандл распаковывается в / как root).
                    --skip-integrity отключает проверку с предупреждением
                    "INTEGRITY CHECK DISABLED"
packages.list       осознанно установленные пакеты (набор docker-ce, nginx, jq, ipset, …)
docker-images.list  образы для pull
crontab.root        root-crontab эталона
ocserv-run.sh       сгенерирован по РАБОТАЮЩЕМУ контейнеру, а не по устаревшему
                    update-ocserv.sh на диске
payload/            whitelist /opt, бинари, юниты, nginx, sysctl, docker daemon.json,
                    конфиги демонов (ndppd) и — если профиль их собирает — сетевые
                    файлы, которые только раскладываются, но не применяются
secrets/            0700: конфиги сервисов, users.txt, ACME-материал, пароли ocserv
```

Спящее содержимое эталона не собирается: `accel-ppp`, `wireguard`,
`ping-check`, `*.bak*`, `*-old.sh`, `__pycache__`, venv у ddns (пересобирается
на цели) и собственный сертификат эталона (новый узел выпускает свой).

**Внимание:** в бандле живые секреты (`secrets/`: конфиги сервисов,
ACME-материал, пароли ocserv). Не коммитьте его.

## Фазы

`install.sh` идёт по ним по порядку; `--only` / `--skip` принимают любое
подмножество, каждая фаза безопасна к повторному прогону.

| Фаза | Что делает |
|---|---|
| `preflight` | root, совпадение архитектуры, контрольные суммы бандла, указывает ли `<host>.fleet.example` сюда, есть ли uplink-креды |
| `identity` | то, что приносит клон образа и чего нет ни в одном бандле: machine-id (пересоздаётся, если он всё ещё эталонный), hostname, строка в `/etc/hosts` |
| `packages` | apt-репозиторий docker + пакеты, `daemon.json` (docker перезапускается, только если файл изменился) |
| `users` | `outline-ss-rust`, группа `certs`, каталоги состояния и логов; плюс `outline-ws` со своими каталогами — только на профилях, которые несут клиент (`INSTALL_WS_RUST=1`, это entry) |
| `files` | `/opt`, `/usr/local/{bin,sbin}`, юниты, сайт nginx, sysctl, симлинк `occtl` и сгенерированный `post-up.service`, если профиль его описывает. Затем поверх — файлы репозитория (`ASSET_FILES`, плюс бинарные/байт-точные через `RAW_ASSET_FILES`) и недостающие `NGINX_LOCATIONS` в файл сайта |
| `secrets` | конфиги сервисов с владельцами и правами, `users.txt`, пароли ocserv, ACME-материал, затем `permission-certs.sh` (ему нужен уже созданный фазой `users` юзер `outline-ss-rust`) |
| `rehost` | переписывает все упоминания эталона: пути сертификатов, ddns-крон, флаги dnsproxy, `SRV_CN` у ocserv, а если префикс задан или найден — ещё и IPv6 `/64`. Добавляет профильные `COMPOSE_REQUIRED_ARGS` и проверяет себя: предупреждает обо всём, что ещё называет эталон, и о каждом упомянутом пути к сертификату/ключу, которого на этом узле нет |
| `uplinks` | подставляет собственные `vless_id`/`password` узла в каждый блок `[[outline.uplinks]]` — в длинной форме отдельными строками, в ссылочной внутри каждого `link = "…"` (userinfo у VLESS, base64-userinfo у SS с сохранением шифра) |
| `network` | распаковывает описания интерфейсов эталона в `/root/provision-network-<host>` и останавливается. Никогда не применяет — см. ниже |
| `ddns` | пересобирает python-venv либо собирает образ контейнера — по профилю |
| `certs` | выпускает `<host>.fleet.example` через lego, повторно гоняет `permission-certs.sh`, перевешивает симлинки `/opt/ddns/certs` на сертификат нового хоста |
| `cron` | ставит root-crontab |
| `services` | пишет cgroup-drop-in'ы памяти из `memory-tuning/fleet.tsv` в бандле (см. [`ops/memory-tuning`](../memory-tuning/README.ru.md)), включает и запускает юниты, тянет образы, поднимает node-exporter / ocserv / unbound+dnsproxy, перегенерирует access-ключи через `save-keys.sh` (`ACCESS_KEYS_REGEN=1`) |
| `verify` | юниты, таймеры, `/metrics`, слушающие порты, контейнеры, `NGINX_LOCATIONS`, через которые скрейпятся экспортеры; спрашивает собственный резолвер узла о его же имени (`VERIFY_SELF_DNS`); а на dual-stack профилях — IPv6-маршрут по умолчанию, ndppd, `local`-маршрут для `/64` и правило MASQUERADE |

### Что приносит клон образа и чего нет ни в одном бандле

Скрипты рассчитаны на чистый хост. Когда «чистый хост» на деле копия диска
эталона (так сделаны `relay-b` и `exit-b`), он приезжает с идентичностью, которой
бандл не касается вовсе, — ни `files`, ни `secrets`, ни `rehost` на неё даже не
смотрят. Этим занимается фаза `identity`:

- `/etc/machine-id`. Один и тот же у двух живых хостов — это общий
  journal-id и DHCP DUID, а любая метрика с такой меткой молча сливает узлы в
  один. Пересоздаётся, если совпадает с эталонным (он записан в MANIFEST); уже
  запущенные сервисы держат старый id до перезагрузки узла.
- Hostname и `/etc/hosts`. Ubuntu-строка `127.0.1.1 <fqdn>` на клоне
  называет эталон. Помимо путаницы, локальный резолвер способен раздать эту
  строку всей сети: 2026-08-08 `dnsproxy` (hosts-файлы включены по умолчанию,
  `network_mode: host`, поэтому docker кладёт внутрь копию `/etc/hosts`) отвечал
  парку `relay-b.fleet.example → 127.0.1.1`, и каждый узел, набиравший relay-b по
  имени, попадал на собственный порт 443. Ровно это и закрывают
  `--hosts-file-enabled=false` в ассете dnsproxy и проверка `VERIFY_SELF_DNS`.

Без автоматического ответа остаётся то, что держат соседи: `shard_id`,
`[cluster] peers` и mesh-allow-list — см. ниже.

### Сознательно не автоматизировано

- Вход в `cloud.fleet.example`. Крон-строка, добавляющая узел в общую
  round-robin запись, ставится закомментированной. Именно вход в запись
  направляет сюда боевой клиентский трафик, поэтому это отдельное решение —
  флаг `--join-shared-dns`, когда он действительно нужен.
- Рестарты соседей. `register-uplink-user.sh` пишет через control API,
  который применяет юзеров на лету.
- Скрейп нового узла. Экспортеры отвечают, nginx их отдаёт — и никто их не
  собирает: scrape-конфиг принадлежит VictoriaMetrics на NAS
  (`ops/nas-monitoring`), а не устанавливаемому хосту. Его источник —
  [`ops/nas-monitoring/victoria-metrics/scrape.yaml`](../nas-monitoring/victoria-metrics/scrape.yaml).
  Добавьте блок цели в каждый job — `assets/victoria-metrics/scrape-unbound-exporter.yaml`
  показывает job `unbound-exporter`, — и выполните `./ops/nas-monitoring/deploy.sh`:
  он копирует файл на NAS, а VictoriaMetrics перечитывает его в течение минуты
  (`-promscrape.configCheckInterval=1m`), рестарт не нужен. До 2026-11-09 файл
  лежал в PVC `victoria-metrics-data` в k3s, до 2026-08-09 — в
  `/opt/victoria-metrics/data/scrape.yaml` на `.102`. Узел, которого нет в scrape-конфиге, не сломан никак, что он мог бы
  заметить сам: он не появляется в Grafana.
- Объявление узла в mesh. В `/opt/network/iptables-update.sh` список
  разрешённых пиров для QUIC-порта mesh (9443) записан литеральными адресами, и
  этот файл раскатывается одинаковым на все узлы кластера — именно так список
  остаётся везде одним и тем же, и поэтому он никогда не рехостится. Теперь эти
  правила пишет сама установка, из `MESH_PEERS` в профиле: идемпотентно (уже
  перечисленный пир не трогается) и со вставкой перед завершающим цепочку
  `DROP`, поскольку скрипт пересобирает `INPUT_EX` с нуля на каждом прогоне и
  правило, добавленное руками, дожило бы лишь до следующей загрузки.

  Две вещи по-прежнему делаются не автоматически. Добавление узла в кластер —
  это правка `MESH_PEERS` для всего семейства (список обязан совпадать у всех
  участников), и она вступает в силу только там, где после этого прогнали
  установку. И конфигу ss-rust каждого узла нужна своя секция `[cluster]`:
  `peers`, согласованные с `MESH_PEERS`, и `shard_id`, уникальный внутри этого
  кластера, — он приезжает копией эталонного, установка про это предупреждает,
  но выбрать значение не может. `cluster_psk` — секрет, и в этом репозитории его
  нет нигде.
- Применение сетевой конфигурации. Фаза `network` только распаковывает
  `interfaces`/`interfaces.d` эталона, чтобы человек слил их руками. Опустить
  интерфейс по ssh на хосте без консоли — верный способ отправить узел на
  переналивку; если всё-таки сливаете, делайте это под dead-man:
  `systemd-run --on-active=5min systemctl restart networking`.

### Проверка версии соседа в register-uplink-user.sh

`register-uplink-user.sh` отказывается писать на соседа, у которого
`outline-ss-rust` старше фикса персистентности control API (`b48525b5`): такая
сборка при создании юзера переписывает `config.toml` и теряет вместе с ним
остальных юзеров. Проверка — grep по бинарю на строку
`failed to serialize user entry as TOML`; сосед, не прошедший её,
пропускается с предупреждением, а не молча перезаписывается.

## Повторный прогон

Каждая фаза идемпотентна, но полный повтор — это *восстановление из бандла*, а
не слияние: фаза `secrets` перезаписывает `/etc/outline-{ss,ws}-rust/config.toml`
копией эталона, а `rehost` и `uplinks` затем заново накладывают идентичность
узла. Всё, что поменялось на узле после установки — юзеры, заведённые через
control API или дашборд, ручные правки, — теряется. Чтобы повторить только
часть, сузьте область: `--only rehost`, `--only uplinks`, `--skip secrets`.

`files` и `secrets` возвращают значения эталона; `rehost` — то, что делает
их значениями этого узла. Прогон первых без второго — например, `--only
files`, чтобы обновить один юнит, — молча вернёт префикс ndppd эталона,
`[outbound] ipv6_prefix`, пути сертификатов и домены выпуска. Установка
печатает `phases files/secrets ran without rehost` и готовую команду
`--only rehost`, но предупреждение — единственный признак: больше никто не жалуется, а узел в таком
состоянии выглядит здоровым, анонсируя при этом чужой `/64`.

Без `--yes` скрипт перед первой фазой спрашивает `Provision this host as
<host> from the <ref> bundle? [y/N]`; любой ответ, кроме `y`/`yes`, — включая
пустой, который читает неинтерактивный запуск по ssh, — прерывает прогон.
`--dry-run` пропускает вопрос и ничего не меняет. `--list-phases` печатает
список фаз.

## Ограничения

- `packages.list` фильтруется профильным `PACKAGES_ALLOW_RE`. Пакет,
  установленный на эталоне вне этого шаблона, не переносится — расширяйте
  шаблон, когда у семейства узлов появляется новая зависимость.
- Локально собираемый образ на узле без доступа к pypi.org. ddns-ответчик
  собирается из Dockerfile, где `pip install` идёт на pypi.org, а часть
  хостингов до него не достаёт (при этом files.pythonhosted.org может
  отвечать — из-за чего отказ выглядит странно). Такой образ переносят готовым,
  а фаза ddns пропускает сборку, если `DDNS_IMAGE` уже загружен:
  ```bash
  ssh <эталон> 'sudo docker save update_domain:latest' | ssh <новый-узел> 'sudo docker load'
  ```
- В `docker-images.list` попадают только образы *работающих* контейнеров за
  вычетом профильного `DOCKER_IMAGE_EXCLUDE_RE`, а сам pull делается по
  возможности: у локально собранного образа (ddns-ответчик на exit-a) нет
  реестра — его собирает фаза `ddns`.
- Спецификации `--peer` разбираются по `:`, поэтому ssh-target с портом не
  распарсится. Заводите алиас хоста в `~/.ssh/config`.
- Бандл фиксирует бинари эталона побайтово, но не собирает их — для обновления
  дальше используйте `ops/deploy/deploy-binary.sh`.

## Как добавить профиль

Скопируйте ближайший существующий профиль и поправьте списки. Переменные
делятся на сбор (`OPT_PATHS`, `UNIT_PATHS`, `SECRET_TARS`, `PACKAGES_ALLOW_RE`,
…) и установку (`ENABLE_UNITS`, `DOCKER_START`, `DDNS_MODE`, `VERIFY_*`, …); у
каждой есть значение по умолчанию, поэтому профиль перечисляет только то, что
у него есть.

Правила, которые стоит держать в голове:

- Всё, что содержит креды, идёт в `SECRET_TARS`, а не в payload. Смотреть
  надо, откуда сервис РЕАЛЬНО читает конфиг, а не куда его кладёт пакет: на
  этом парке живой файл регулярно оказывается тем, что в `/opt`, а не стоковым
  путём под `/etc` или `/usr/local/etc`, и ключи лежат именно в живом. Собрать
  его как обычный payload — значит положить креды в несекретную половину
  бандла.
- Файл, называющий эталон, должен попасть в `REHOST_FILES`. Каждый вызов
  `rehost_file` сообщает, сколько вхождений заменил, и предупреждает, если файл
  не упоминает ни старый, ни новый хост, — так расхождение с эталоном всплывает
  вместо того, чтобы тихо породить узел, указывающий на свой шаблон. Аудит в
  конце фазы предупреждает о каждом оставшемся упоминании и о каждом пути
  `.crt`/`.key`/`.pem`, которого на этом узле нет, и печатает итог
  `N rehost problem(s) above — fix them before the services phase starts
  anything`. Прогон он не останавливает: читайте вывод до фазы `services`.
- `ASSET_FILES` — для файла, источником которого не должен быть ни один
  эталон. Берите его, когда у всех узлов семейства содержимое обязано быть
  одинаковым и расхождение между ними — это баг, а не локальная настройка; тот
  же путь добавьте в `OPT_EXCLUDES`, чтобы бандл не тащил ещё и копию эталона,
  которую ассет тут же перезапишет. Всё по-настоящему узловое заносится как
  `%HOST%` / `%DOMAIN%`; всё секретное в ассетах не место вообще — `assets/`
  лежит в репозитории.
- `RAW_ASSET_FILES` — тот же `ASSET_FILES`, но для бинарника или файла,
  который обязан лечь байт-в-байт. Формат `<ассет>:<цель>[:режим]` тот же, но
  содержимое копируется дословно — без раскрытия `%HOST%` / `%DOMAIN%`, которое
  идёт через `sed` в подстановке команды и испортило бы PNG, — и целевой каталог
  не создаётся. Файл пишется только туда, где каталог уже есть, поэтому
  landing-страница ложится в webroot nginx (`/var/www/html`, его создаёт пакет
  nginx) на узлах с nginx и пропускается на всех остальных.
- `NGINX_LOCATIONS` — для маршрута, который обязан быть в файле сайта.
  Запись вида `<location>:<URL для proxy_pass>`, вставляется в последний блок
  `server`, если его там нет. Именно так exporter становится доступен скрейпу:
  узел, чей файл сайта старше самого exporter'а, отвечает на loopback и отдаёт
  404 на 443, и на узле этого никто не замечает.
  Соседняя правка того же рода вшита в код, а не в профиль: фаза `files`
  расширяет location подписки до `(json|toml|txt)`. Список расширений приезжает
  внутри бандла, поэтому бандл, снятый до появления `<user>.toml`, раздавал бы
  ws-rust-конфиг без заголовков `profile-*` — клиент забрал бы его один раз и
  никогда не обновил. Правка идемпотентна и молчит на уже расширенном файле.
- `COMPOSE_REQUIRED_ARGS` — для флага, которого эталон ещё не знает.
  Запись вида `<compose-файл>:<сервис>:<флаг>`, флаг вставляется в начало списка
  `command:` этого сервиса. Нужен, когда правка обязана быть на каждом клоне, а
  не только на эталоне; сервис с inline-командой (`["-d", "-c", …]`) не
  переписывается, а попадает в предупреждение.
- `VERIFY_SELF_DNS=1` — для семейства, которое держит резолвер. Проверка
  спрашивает собственный резолвер узла о его же имени и валится на петлевом
  ответе — именно так выглядит утёкшая hosts-запись.
