# Бэкап и восстановление NanoPi .104 (userdata → NFS)

Периодический бэкап боевой NanoPi-NEO3-Plus `198.18.1.104` на NFS и быстрое
восстановление на новую microSD, если старая карта умрёт.

## Почему бэкапится только `p9`

Карта `/dev/mmcblk0` — это Rockchip raw-boot раскладка (GPT, 29.84 GiB):

| Раздел | Что | Меняется? |
|--------|-----|-----------|
| `p1`–`p7` | uboot / misc / dtbo / resource / kernel / boot / recovery — **сырые** блобы, их грузит U-Boot напрямую, не из `/boot` | почти нет |
| `p8` | `rootfs` ext4 — стоковый образ FriendlyElec (overlay **lower**) | почти нет |
| `p9` | `userdata` ext4 — overlay **upper** (`/data/root`): **весь ваш стейт** — configs, systemd drop-in'ы, `zram-swap`, sysctl, всё что правилось руками | **да** |

`p1`–`p8` восстанавливаются перезаливкой **оригинального образа FriendlyElec**.
Уникальное — только `p9`, поэтому бэкапим его. Наивный `tar` корня бесполезен:
он не заберёт raw-загрузчик `p1`–`p7`, и новая карта не стартует.

Важные факты платы (учтены в скриптах):
- В рабочем namespace `p8`/`p9` **не смонтированы** — initramfs собирает overlay и
  делает `switch_root`. Поэтому образ снимается прямо с блочного устройства
  `/dev/mmcblk0p9`.
- 1 ГБ RAM, склонность к memory-livelock → бэкап-джоб идёт под `Nice=19`,
  `ionice idle` и жёстким cgroup-лимитом `MemoryMax=256M`, ночью.
- Реально занято в `p9` ~1 ГБ из 28 ГБ. Режим `e2image -ra` читает только занятые
  блоки (не весь раздел) и щадит и карту, и плату.

## Как это работает

- **Модель push:** скрипт крутится на самой .104, сам монтирует NFS и стримит
  туда сжатый образ. Расписание — `systemd`-таймер (еженедельно, Вс 04:00).
- **Формат образа (по умолчанию `MODE=e2image`):** `e2image -ra` отдаёт обычный
  разреженный ext4-образ размером с ФС (номинально ~28 ГБ), но читает лишь ~1 ГБ
  занятых блоков; свободное — нули → `gzip` ужимает до ~0.3–0.6 ГБ.
  Восстановление переносимо: образ — простой ext4, разворачивается `gunzip | dd`
  на macOS **или** Linux, без спец-тулинга.
- **Файлы на NFS:** `nanopi104-p9-<TS>.e2image.img.gz` + `.sha256` + `.meta`
  (uuid, размеры, sha, минимальный размер целевого раздела). Ротация — `KEEP=6`.

## Установка (на .104)

```bash
# с мака скопировать каталог на плату
scp -r ops/nanopi104-backup mmv@198.18.1.104:/tmp/

ssh mmv@198.18.1.104
cd /tmp/nanopi104-backup
sudo ./install-on-104.sh          # поставит nfs-common, разложит скрипт+юниты

sudoedit /etc/default/nanopi104-backup   # ВПИСАТЬ NFS_HOST и NFS_EXPORT

# первый прогон вручную + лог
sudo systemctl start nanopi104-backup.service
journalctl -u nanopi104-backup.service -n 60 --no-pager

# включить еженедельно
sudo systemctl enable --now nanopi104-backup.timer
systemctl list-timers nanopi104-backup.timer
```

Конфиг живёт в `/etc/default/nanopi104-backup` (а не в скрипте), поэтому
обновление скрипта не затирает настройки. Ключи: `NFS_HOST`, `NFS_EXPORT`,
`NFS_OPTS`, `NFS_SUBDIR`, `KEEP`, `MODE` (`e2image`|`dd`), `STOP_SERVICES`.

`STOP_SERVICES=1` останавливает `outline-ws-rust` на время снятия образа (меньше
записей в `p9`), затем сразу поднимает. По умолчанию `0` — снимок
crash-consistent (как выдёргивание питания; ext4-журнал доигрывается при
восстановлении). Конфиги статичны, так что дефолт безопасен.

## Восстановление (умерла карта → новая)

Восстановление делается **не на .104** (она мертва), а на маке или любом Linux с
картридером. Две фазы:

### Фаза 1 — залить оригинальный образ FriendlyElec (baseline)

Берётся **ваш** оригинальный образ платы (тот, которым заливали изначально). Он
воссоздаёт GPT, raw-загрузчик `p1`–`p7`, стоковый `p8` и `p9`.

```bash
# macOS (карта = diskN из `diskutil list external physical`)
diskutil unmountDisk /dev/diskN
xzcat friendlyelec-nanopi.img.xz | sudo dd of=/dev/rdiskN bs=4m      # или gunzip -c

# Linux
xzcat friendlyelec-nanopi.img.xz | sudo dd of=/dev/sdX bs=4M conv=fsync status=progress
```

Требование: **новая карта ≥ старой** (тот же 32 ГБ-класс). После заливки `p9`
должен быть ≥ размера ФС из `.meta` (`restore_min_target_bytes`, ~28 ГБ).
Стоковые образы FriendlyElec обычно авто-расширяют `userdata` до конца диска при
первом старте; если ваш образ этого не делает — расширьте `p9` через `parted`
перед фазой 2 (restore-скрипт проверит размер и не даст перезаписать в меньший
раздел).

### Фаза 2 — наложить последний бэкап `p9`

```bash
./restore-p9.sh /path/to/nanopi104-p9-YYYYMMDD-HHMMSS.e2image.img.gz
# спросит устройство карты, покажет что затрёт, потребует ввести имя + YES
```

Скрипт проверяет `gzip`/`sha256`, отказывается писать на внутренний/системный
диск, разворачивает образ на `p9` (macOS: raw-slice; Linux: `dd` + `e2fsck -fy` +
`resize2fs`), затем можно ставить карту в NanoPi.

> macOS не умеет `e2fsck`/`resize2fs` (нет ext4-тулинга) — не страшно: журнал
> ext4 доиграется на первом старте платы, а размер `p9` уже задан фазой 1. Если
> хочется чистого `fsck`/resize — делайте фазу 2 на Linux (подойдёт Beelink
> `.105`).

## Проверить бэкапы

```bash
ls -lh <nfs>/nanopi104/nanopi104-p9-*.img.gz
cat    <nfs>/nanopi104/nanopi104-p9-*.e2image.img.gz.meta
gzip -t <образ>                       # быстрая проверка целостности
sha256sum -c <образ>.sha256
```

## Замечания

- **Консистентность:** снимок `p9` — crash-consistent. Гарантированно целы
  статичные данные (конфиги); в теории могут быть неконсистентны логи, писавшиеся
  в момент снятия — их подчистит `e2fsck` при восстановлении.
- **Размер образа:** режим `e2image` даёт мелкий образ независимо от того,
  обнулено ли свободное место (`fstrim` на .104 до `p9` не достаёт). `MODE=dd`
  прочитает весь раздел (28 ГБ, включая мусор в свободных блоках) → большой образ;
  использовать только если зачем-то нужен именно побайтовый raw.
- **Не роняет плату:** cgroup `MemoryMax=256M` в юните — синхронный потолок;
  если джоб (вместе с dirty-страницами NFS) упрётся, тормозит/убивается **он**, а
  не система. Это осознанная страховка на 1 ГБ-плате.
- **Никаких сетевых правок на .104** (interface/DNS/routing) скрипты не делают —
  только временный NFS-mount, снимаемый в конце. Плату это не может оставить
  offline после ребута.
