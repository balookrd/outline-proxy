# Бэкап и восстановление NanoPi .104 (userdata → NFS)

Периодический бэкап боевой NanoPi-NEO3-Plus `198.51.100.104` на NFS и восстановление
на новую microSD, если старая карта умрёт.

Реальные имена узлов, домены и адреса парка в этом документе заменены условными: `198.51.100.0/24` — домашняя сеть (`.102`, `.104` и т. д. — последний октет). Соответствие — в локальном некоммитируемом `FLEET.local.md`.

## Почему бэкапится только `p9`

Карта `/dev/mmcblk0` — это Rockchip raw-boot раскладка (GPT, 29.84 GiB):

| Раздел | Что | Меняется? |
|--------|-----|-----------|
| `p1`–`p7` | uboot / misc / dtbo / resource / kernel / boot / recovery — сырые блобы, их грузит U-Boot напрямую, не из `/boot` | почти нет |
| `p8` | `rootfs` ext4 — стоковый образ FriendlyElec (overlay lower) | почти нет |
| `p9` | `userdata` ext4 — overlay upper (`/data/root`): весь стейт платы — конфиги, systemd drop-in'ы, `zram-swap`, sysctl, всё, что правилось руками | да |

`p1`–`p8` восстанавливаются перезаливкой оригинального образа FriendlyElec.
Уникальное — только `p9`, поэтому бэкапится он. `tar` корня не подходит: он не
заберёт raw-загрузчик `p1`–`p7`, и новая карта не загрузится.

Особенности платы, учтённые в скриптах:

- В рабочем namespace `p8`/`p9` не смонтированы — initramfs собирает overlay и
  делает `switch_root`. Поэтому образ снимается прямо с блочного устройства
  `/dev/mmcblk0p9`.
- 1 ГБ RAM, склонность к memory-livelock: бэкап идёт ночью, с `Nice=19`,
  `IOSchedulingClass=idle` и cgroup-лимитом `MemoryMax=256M` (`MemoryHigh=192M`).
- В `p9` занято ~1 ГБ из 28 ГБ. Режим `e2image -ra` читает только занятые блоки, а
  не весь раздел, — меньше чтения с карты и меньше нагрузки на плату.

## Как работает бэкап

- Модель push: `backup-p9.sh` запускается на самой `.104`, сам монтирует NFS и пишет
  туда сжатый образ. Расписание — таймер `nanopi104-backup.timer`: воскресенье 04:00
  локального времени плюс случайная задержка до 15 минут (`RandomizedDelaySec=15min`);
  пропущенный запуск выполняется после загрузки (`Persistent=true`).
- Формат образа (по умолчанию `MODE=e2image`): `e2image -ra` отдаёт обычный
  разреженный ext4-образ размером с ФС (номинально ~28 ГБ), но читает лишь ~1 ГБ
  занятых блоков; свободное место — нули, `gzip -1` ужимает образ до ~0.3–0.6 ГБ.
  Образ — простой ext4, разворачивается `gunzip | dd` на macOS или Linux.
- Файлы на NFS (в подкаталоге `NFS_SUBDIR`): `nanopi104-p9-<TS>.e2image.img.gz` +
  `.sha256` + `.meta` (uuid, размеры, sha, минимальный размер целевого раздела
  `restore_min_target_bytes`). Хранятся последние `KEEP` образов (по умолчанию 6).
- Перед записью скрипт проверяет, что на NFS свободно не меньше занятого в `p9`
  плюс 512 МиБ; после записи — `gzip -t` образа.

## Установка (на .104)

1. Скопируйте каталог на плату (с мака, из корня репозитория):

   ```bash
   scp -r ops/nanopi104-backup mmv@198.51.100.104:/tmp/
   ```

2. Установите скрипт и юниты. `install-on-104.sh` ставит `nfs-common` (и
   `e2fsprogs`, если нет `e2image`), кладёт `backup-p9.sh` в `/usr/local/sbin/`, юниты
   в `/etc/systemd/system/`, конфиг в `/etc/default/nanopi104-backup` (существующий не
   перезаписывает). Пока в конфиге `NFS_HOST=CHANGE-ME…`, таймер не включается:

   ```bash
   ssh mmv@198.51.100.104
   cd /tmp/nanopi104-backup
   sudo ./install-on-104.sh
   ```

3. Впишите `NFS_HOST` и `NFS_EXPORT`:

   ```bash
   sudoedit /etc/default/nanopi104-backup
   ```

4. Запустите первый бэкап вручную и проверьте лог (последняя строка — `backup OK`):

   ```bash
   sudo systemctl start nanopi104-backup.service
   journalctl -u nanopi104-backup.service -n 60 --no-pager
   ```

5. Включите еженедельный таймер:

   ```bash
   sudo systemctl enable --now nanopi104-backup.timer
   systemctl list-timers nanopi104-backup.timer
   ```

## Параметры `/etc/default/nanopi104-backup`

Конфиг лежит отдельно от скрипта, поэтому обновление скрипта не затирает настройки.

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `NFS_HOST` | `CHANGE-ME.nfs.host` | NFS-сервер; со значением по умолчанию скрипт завершается с ошибкой |
| `NFS_EXPORT` | `/export/nanopi-backups` | экспортируемый путь |
| `NFS_OPTS` | `vers=4,soft,timeo=50,retrans=3,noatime,nolock` | опции `mount -t nfs` |
| `NFS_SUBDIR` | `nanopi104` | подкаталог в экспорте |
| `KEEP` | `6` | сколько образов хранить |
| `MODE` | `e2image` | `e2image` — только занятые блоки; `dd` — весь раздел побайтово |
| `STOP_SERVICES` | `0` | `1` — остановить `outline-ws-rust.service` на время снятия образа |

`STOP_SERVICES=1` останавливает `outline-ws-rust` на время чтения `p9` (меньше
записей в раздел) и запускает его сразу после чтения, до проверки и ротации. По
умолчанию `0` — снимок crash-consistent, как после выдёргивания питания: журнал ext4
доигрывается при восстановлении. Конфиги на плате меняются редко, поэтому дефолта
достаточно.

## Восстановление (умерла карта → новая)

Восстановление делается не на `.104`, а на маке или любом Linux с картридером. Две
фазы.

### Фаза 1 — залить оригинальный образ FriendlyElec

Нужен тот образ, которым плату заливали изначально. Он воссоздаёт GPT, raw-загрузчик
`p1`–`p7`, стоковый `p8` и `p9`.

```bash
# macOS (карта = diskN из `diskutil list external physical`)
diskutil unmountDisk /dev/diskN
xzcat friendlyelec-nanopi.img.xz | sudo dd of=/dev/rdiskN bs=4m      # или gunzip -c

# Linux
xzcat friendlyelec-nanopi.img.xz | sudo dd of=/dev/sdX bs=4M conv=fsync status=progress
```

Новая карта должна быть не меньше старой (тот же класс 32 ГБ). После заливки `p9`
должен быть не меньше размера ФС из `.meta` (`restore_min_target_bytes`, ~28 ГБ).
Стоковые образы FriendlyElec обычно расширяют `userdata` до конца диска при первом
старте [проверить: делает ли это образ, которым заливали `.104`]; если нет — расширьте
`p9` через `parted` перед фазой 2. `restore-p9.sh` сверяет размер раздела с `.meta` и
не пишет в меньший раздел.

### Фаза 2 — наложить последний бэкап `p9`

```bash
./restore-p9.sh /path/to/nanopi104-p9-YYYYMMDD-HHMMSS.e2image.img.gz
# спросит устройство карты, покажет что затрёт, потребует ввести имя раздела + YES
```

Скрипт проверяет `gzip -t` и `.sha256`, отказывается писать на внутренний диск,
разворачивает образ на `p9` (macOS: raw-slice `/dev/rdiskNs9`; Linux: `dd` +
`e2fsck -fy` + `resize2fs`). После этого карту можно ставить в NanoPi.

На macOS нет `e2fsck`/`resize2fs`: журнал ext4 доиграется на первом старте платы, а
размер `p9` уже задан фазой 1. Для `fsck` и resize до установки карты выполните фазу 2
на Linux, например на Beelink `.102`.

## Проверка бэкапов

```bash
ls -lh <nfs>/nanopi104/nanopi104-p9-*.img.gz
cat    <nfs>/nanopi104/nanopi104-p9-*.e2image.img.gz.meta
gzip -t <образ>                       # целостность gzip
sha256sum -c <образ>.sha256           # запускать из каталога с образом
```

`<nfs>` — точка монтирования `NFS_HOST:NFS_EXPORT` на машине, где проверяете.

## Известные ограничения

- Консистентность: снимок `p9` crash-consistent. Конфиги, которые не менялись в момент
  снятия, целы; логи, писавшиеся в этот момент, могут быть неконсистентны — их
  исправит `e2fsck` при восстановлении на Linux.
- Размер образа: режим `e2image` даёт маленький образ независимо от того, обнулено ли
  свободное место (`fstrim` на `.104` до `p9` не достаёт). `MODE=dd` читает весь раздел
  (28 ГБ, включая мусор в свободных блоках), образ получается большим; использовать
  только если нужен побайтовый raw.
- Память: `MemoryMax=256M` в юните — жёсткий потолок cgroup. Если джоб вместе с
  dirty-страницами NFS упрётся в него, тормозится или убивается джоб, а не система.
- Сеть: скрипты не меняют интерфейсы, DNS и маршрутизацию на `.104` — только временный
  NFS-mount в `/run/nfs-backup.XXXXXX`, снимаемый в конце.
