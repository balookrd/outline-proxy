# Liveness-watchdog для outline-юнитов

Внешний сторож: перезапускает `outline-ws-rust` / `outline-ss-rust`, когда
процесс жив, а обслуживание встало. Каталог содержит скрипт
`outline-watchdog`, шаблонные юниты `outline-watchdog@.service` /
`outline-watchdog@.timer` и установщик `install.sh`.

Реальные имена узлов, домены и адреса парка в этом документе заменены условными: `fleet.example` — домен парка; `relay-a`…`relay-d` — промежуточные cloud-узлы; `exit-a`…`exit-e` — выходные узлы; `198.51.100.0/24` — домашняя сеть (`.102`, `.104` и т. д. — последний октет). Соответствие — в локальном некоммитируемом `FLEET.local.md`.

## Чего не видит systemd

systemd следит за процессом, а не за тем, обслуживает ли он кого-нибудь.
Отказ, ради которого это написано (relay-c, 2026-07-22, 3.5 часа простоя
незамеченными):

- юнит `active`, порты в `LISTEN`, `NRestarts=0`;
- cgroup душит процесс через `MemoryHigh` (`memory.events: high 714194`),
  единственный worker на 1 vCPU висит в `D` на `mem_cgroup_handle_over_high`;
- `oom_kill=0` — OOM-killer не сработал, значит systemd ничего не заметил;
- async-рантайм стоит целиком: `Recv-Q` на `:9091` растёт, скрейпы копятся,
  журнал молчит часами.

Ни `Restart=on-failure`, ни `WatchdogSec=` тут не помогают: первый ждёт
падения процесса, второй требует `sd_notify` из приложения. Единственный
сигнал, совпадающий с тем, что видит пользователь, — отвечает ли юнит на
свой собственный `/metrics`. Его и проверяем.

## Как работает

`outline-watchdog <unit> [url] [threshold]`:

- URL по умолчанию выводится из имени юнита: `outline-ws-rust` →
  `http://127.0.0.1:9091/metrics`, `outline-ss-rust` →
  `http://127.0.0.1:9090/metrics`. Для другого имени юнита без явного URL
  скрипт выходит с кодом 2;
- проверка — `curl -fsS -m 5`: ответ не 2xx или нет ответа за 5 с считается
  промахом;
- успех обнуляет счётчик промахов в `/run/outline-watchdog/<unit>.misses`,
  промах увеличивает его и пишет в журнал сообщение с приоритетом
  `daemon.warning` (тег `outline-watchdog`);
- на `threshold`-м промахе подряд (по умолчанию 3) — запись `daemon.err` и
  `systemctl restart <unit>`;
- остановленный юнит (`systemctl is-active` = false) не трогается вообще,
  чтобы сторож не воевал с ручным `systemctl stop` во время обслуживания;
- счётчик обнуляется до рестарта: если рестарт сам подвиснет, следующий
  тик начнёт счёт заново, а не перезапустит юнит повторно немедленно.

Таймер: `OnBootSec=2min` (даёт юниту подняться после перезагрузки),
`OnUnitActiveSec=1min`, `AccuracySec=5s`. Сервис — `Type=oneshot` с
`TimeoutStartSec=30`. При пороге 3 от зависания до рестарта проходит около
3 минут.

## Установка

```bash
scp -r ops/watchdog <host>:/tmp/ && ssh <host> 'cd /tmp/watchdog && sudo ./install.sh'
```

Скрипт идемпотентен и включает таймер только для тех юнитов, которые узел
намерен крутить — `enabled` либо уже запущенных. Одного наличия
unit-файла мало: на серверных нодах клиентский юнит лежит рядом, но
намеренно `disabled`, и сторож для него означал бы таймер раз в минуту
навсегда ради того, что никто не собирается запускать. Юнит, который
`enabled`, но сейчас остановлен, сторожа получает — его ждут обратно, а до
тех пор проверка молча выходит. Если узел перестал крутить юнит, повторный
прогон снимает оставшийся от прошлой установки таймер. Если на узле нет ни
одного подходящего юнита, `install.sh` завершается с кодом 1.

При переустановке узла через `ops/provision-node` сторож приезжает из бандла:
профили `relay-a` и `exit-a` собирают `outline-watchdog` и оба шаблонных юнита и
включают таймеры (`outline-watchdog@outline-ss-rust.timer`, на `relay-a` ещё
`outline-watchdog@outline-ws-rust.timer`).

Парк на 2026-07-23 (с тех пор состав сменился, см. `FLEET.local.md`;
[проверить: какие из текущих узлов под сторожем]):

| Узлы | Роль | Под сторожем |
|------|------|--------------|
| relay-c, relay-d, `198.51.100.104`, `198.51.100.105` | клиент + сервер | ws + ss |
| exit-d, exit-c, exit-a (`*.fleet.example`) | exit-серверы за бугром | ss |

На exit-нодах по одному ядру и от 960 МБ RAM (exit-c — самая тесная), то
есть ровно тот профиль, на котором и случился livelock: там сторож нужен не
меньше, чем на клиентских.

## Проверка

```bash
# здоровый путь: тихо, exit 0
sudo /usr/local/sbin/outline-watchdog outline-ws-rust; echo $?

# счёт промахов без риска рестарта (порог заведомо недостижим)
sudo /usr/local/sbin/outline-watchdog outline-ws-rust http://127.0.0.1:9/metrics 99

# что он делал
journalctl -t outline-watchdog
systemctl list-timers 'outline-watchdog@*'
```

Полное срабатывание (три промаха → рестарт) проверено вживую на relay-d:
`pid 844928 → 903549`, после рестарта метрики снова отдают 200, аплинки
зелёные.

## Отключение

```bash
sudo systemctl disable --now outline-watchdog@outline-ws-rust.timer \
                             outline-watchdog@outline-ss-rust.timer
```

## Что это не лечит

Сторож — обвязка вокруг симптома. Первопричина на маленьких узлах —
рост памяти под всплеском флоу и cgroup-throttle. Лимиты памяти задаются в
[`ops/memory-tuning`](../memory-tuning/README.ru.md). Каждый рестарт сторожа
виден в `journalctl -t outline-watchdog` строкой `unresponsive … restarting`;
если он срабатывает регулярно, чинить надо память, а не интервал таймера.
