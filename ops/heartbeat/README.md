# Heartbeat-приёмник для dead-man switch

Внешний наблюдатель, который присылает письмо, когда **сам мониторинг замолчал**.

## Зачем, если есть алерты в Grafana

Grafana на `.102` шлёт письма о деградации аплинков. Но она не может сообщить о
собственной смерти: если умрёт Beelink, контейнер, VictoriaMetrics или домашний
канал — не будет ни алертов, ни признака, что алертов больше нет. Тишина в почте
неотличима от «всё хорошо».

Поэтому цепочка развёрнута наоборот: Grafana **постоянно** шлёт пульс наружу, а
снаружи за ним следят. Пропал пульс — пришло письмо.

## Как работает

```
Grafana (.102)              cloud1 / cloud2
   │                              │
   │ правило DeadMansSwitch       │
   │ (firing всегда, repeat 5m)   │
   └──POST /hb/<token>───────────►│ nginx: access_log heartbeat.log, 204
                                  │
                                  │ heartbeat-watch (systemd timer, раз в 5 мин)
                                  │ последняя запись старше 15 мин?
                                  └──► письмо через Gmail SMTP
```

Ключевая деталь — **условие правила ходит в датасорс**: это `count(up) >= bool 1`,
а не константа `vector(1)`. Если VictoriaMetrics умрёт, запрос перестанет
отвечать, правило перестанет срабатывать, пульс прекратится и наблюдатели
пришлют письмо. Константа в этом случае продолжила бы бодро пульсировать поверх
мёртвой базы и скрыла бы ровно ту аварию, ради которой всё написано.

Приёмник не поднимает ни своего порта, ни своего сертификата: на 443 сидит
`outline-ss-rust`, который непонятный ему HTTPS-трафик отдаёт в nginx на
`127.0.0.1:8080` с `proxy_protocol`. Наш `location` живёт в том же
`server`-блоке, где уже лежат `/rust-ws-exporter/metrics` и соседи.

## Почему наблюдателей два

Один наблюдатель не отличает смерть `.102` от собственной изоляции. Провайдерские
блокировки — обычное дело: aeza и senko сегодня полностью недоступны из РФ,
и точно так же может отвалиться путь до любого cloud-узла.

Поэтому читать письма нужно так:

- письмо **от одного** узла — скорее всего сломан путь до этого узла;
- письма **от обоих** — действительно лежит `.102`.

Имя наблюдателя стоит в теме письма (`[cloud1] outline: no heartbeat from .102`).
Цена такой схемы — два письма вместо одного при настоящей аварии; это сознательный
размен: лучше два письма, чем ни одного.

## Установка

```bash
rsync -a --delete ops/heartbeat/ sysadm@cloud1.beerloga.su:/tmp/heartbeat/
ssh sysadm@cloud1.beerloga.su 'cd /tmp/heartbeat && sudo ./install.sh'
```

`install.sh` идемпотентен и **не перезагружает nginx** — только проверяет конфиг
через `nginx -t` и печатает команду для владельца. Узел обслуживает боевой
трафик, решение о `reload` принимает человек.

До запуска на узле должен лежать токен:

```bash
sudo install -d -m 0700 /etc/heartbeat-watch
printf '%s' '<токен>' | sudo tee /etc/heartbeat-watch/token >/dev/null
sudo chmod 0600 /etc/heartbeat-watch/token
```

Токен — общий секрет для обоих узлов и для URL webhook'а в Grafana; генерируется
один раз (`openssl rand -base64 24 | tr -d '=+/'`). В репозитории его нет: в
`nginx-heartbeat.conf` стоит плейсхолдер `__HEARTBEAT_TOKEN__`, подстановку
делает установщик.

## Секреты

| Файл | Права | Что внутри |
|------|-------|------------|
| `/etc/heartbeat-watch/token` | `0600 root` | общий токен heartbeat-URL |
| `/etc/heartbeat-watch/smtp.env` | `0600 root` | `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_TO` |

`SMTP_PASSWORD` — app-password Google (16 символов, требует включённой
двухэтапной аутентификации), тот же, что у Grafana. Наблюдатели шлют почту
**сами**, не через Grafana: в этом и смысл — путь доставки не должен зависеть от
того, за чем следим.

## Проверка

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://cloud1.beerloga.su/hb/<токен>   # 204
sudo tail -1 /var/log/nginx/heartbeat.log                                          # свежая строка
sudo /usr/local/sbin/heartbeat-watch --dry-run                                     # state=up
systemctl list-timers heartbeat-watch.timer --no-pager                             # NEXT в пределах 5 мин
```

`--dry-run` печатает решение и **не трогает ничего**: ни письма, ни файла
состояния. Вывод — `state=up`, `state=down send=DOWN`, `state=down send=none`
или `state=up send=RESOLVED`.

Отдельный флаг `--simulate` делает то же, но состояние сохраняет — он нужен
тестам, чтобы прогонять цепочку переходов. Руками его звать не надо: диагностика,
меняющая состояние, пометит аварию как «уже уведомлено» и проглотит следующее
настоящее письмо. Так и случилось при первой раскатке 2026-08-07, поэтому флаги
и разведены.

Поведение watcher'а покрыто офлайновыми тестами — `./test-heartbeat-watch.sh`
(нужен только python3, боевые узлы не трогает).

## Грабли

- **Логротация.** `/var/log/nginx/*.log` ротируется ежедневно, и сразу после
  ротации живой лог пуст. Watcher поэтому смотрит и в `heartbeat.log.1` —
  иначе каждую ночь возникала бы выдуманная авария.
- **Отсутствие лога — это не авария.** До первого пульса судить не о чем, и
  свежая установка обязана молчать. Письмо появляется только после того, как
  пульс был и пропал.
- **Якорь вставки в nginx-конфиг.** В `beerloga.su` первым идёт закомментированный
  `:80`-блок с тем же `server_name *.beerloga.su;`. Вставка по первому совпадению
  `server_name` уронила бы `include` вне `server`-блока, поэтому установщик
  цепляется за `listen 127.0.0.1:8080 proxy_protocol;` и требует ровно одного
  совпадения.
