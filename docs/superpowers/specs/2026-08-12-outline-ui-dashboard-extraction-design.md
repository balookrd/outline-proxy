# Вынос дашбордов в `outline-ui` (дизайн)

Дата: 2026-08-12
Статус: согласовано в чате, ждёт вычитки владельцем

## Проблема

Оба бинаря несут web-UI, который не имеет отношения к переносу пакетов. Клиент
отдаёт дашборд по аплинкам и топологии, сервер — дашборд управления юзерами, и
каждый вшит в процесс, который везёт боевой трафик. Отсюда три следствия.

**Web-поверхность на боевых узлах.** Достучаться до любого из этих листенеров
равносильно владению всеми токенами инстансов, с которыми он настроен, — это
сказано в самом коде (`auth.rs`: «reaching this listener is equivalent to holding
all of those tokens»). Такие полномочия висят на том же процессе, что и data
plane.

**Правка UI стоит рестарта data plane.** `dashboard.html` попадает в бинарь через
`include_str!`, поэтому косметическая правка требует пересборки и раскатки того
самого бинаря, который везёт трафик, — и рестарта, роняющего все флоу на узле.
Ровно это пришлось заплатить 2026-08-12 за колонку с потерями.

**UI не может переехать в кластер**, пока он функция бинаря, — хотя всё
остальное наблюдаемое (Grafana, VictoriaMetrics) уже живёт в k3s.

Цель — отдельный бинарь, который отдаёт оба дашборда и больше ничего, чтобы UI
развернуть в k3s и убрать с узлов.

## Почему это дёшево: дашборды уже агрегаторы

Ни один из них не читает локальное состояние. Оба — HTTP-клиенты, которые
разлетаются по control API каждого настроенного инстанса и рисуют ответы:

- `backend_client.rs` (ws) открывает `TcpStream::connect(host, port)` на каждый
  `control_url`; локальный узел там — просто ещё одна запись с `127.0.0.1`;
- `spawn_dashboard_server(config, shutdown)` принимает только `DashboardConfig` и
  канал остановки. Он не касается ни `UplinkRegistry`, ни листенеров, ни TUN.

Приваривает их к бинарю не сам дашборд, а путь старта. Проверено 2026-08-12:

- `load_uplinks` отвергает конфиг без единого аплинка (`bail!("no uplink
  configured")`, `"uplinks is present but empty"`) — то есть конфиг только под
  дашборд сегодня даже не загрузится;
- `bootstrap::run_with_config` безусловно строит `UplinkRegistry` и запускает
  probe-, warm-standby-, cert-check-, loss-sampler- и reselect-циклы ещё до
  того, как поднимется дашборд.

Значит дашборды не нужно *переписывать* — их нужно *отцепить*.

Связь с бинарями-хозяевами слабая. Весь ws-дашборд тянет из крейта ровно четыре
вещи: `crate::config`, `http::constant_time_eq`, `http::body::read_limited_body`,
`http::serve`. Ss-дашборд — `crate::config` и немного `crate::server`.

## Решения

**Один бинарь `bins/outline-ui`, оба дашборда на одном порту** через
`Router::nest("/ws", …)` и `Router::nest("/ss", …)`. Один под, один Service, один
Ingress; `/` — небольшая страница со ссылками на оба, а не редирект: ни один из
UI не «главнее» другого.

**axum для обоих.** Ss-дашборд уже на axum; ws — на ручном hyper с `match` по
пути (`mod.rs`, 182 строки). `nest` у axum закрывает требование префиксов из
коробки, а переписать `match` в маршруты — механическая работа. Обратный путь
означал бы вручную повторить экстракторы axum для ss-хендлеров.

**Дашборды уходят из бинарей полностью** — без feature-флага и без «пусть
полежит на всякий случай». Флаг оставил бы web-поверхность скомпилированной в
боевые бинари и две копии UI, которые разъедутся.

**Свежее соединение на запрос, без пула.** Ws-клиент уже открывает новое TCP+TLS
на каждый вызов с `Connection: close`, у ss есть `control_pool.rs`. Агрегатор
делает горстку запросов на просмотр страницы против дюжины инстансов, так что пул
оптимизирует то, что не горячее, а его удаление убирает состояние из сервиса,
который в остальном stateless. Пул не переносим.

## Структура

```
bins/outline-ui/
  Cargo.toml
  src/main.rs         конфиг, один axum-листенер, остановка
  src/config.rs       [server] + [[ws.instances]] + [[ss.instances]]
  src/auth.rs         гейт по credentials: Basic/Bearer + WWW-Authenticate
  src/backend.rs      HTTP(S)-клиент к control API инстанса (ws backend_client + ss proxy/tls)
  src/assets.rs       общая статика: outline-logo.png, страница-указатель
  src/ws/mod.rs       маршруты под /ws
  src/ws/api.rs       topology / instances / activate / reselect / set_enabled / apply
  src/ws/dashboard.html
  src/ws/uplinks.html
  src/ws/tests/       api, auth, guard, backend_client — переезжают
  src/ss/mod.rs       маршруты под /ss
  src/ss/api.rs       instances / users CRUD
  src/ss/dashboard.html
  src/ss/tests/       auth, guard, handlers, proxy — переезжают
  src/index.html      ссылки на /ws и /ss
```

В каждом каталоге-источнике по 15 файлов, и это число важно дважды.
`outline-logo.png` грузят оба UI — он переезжает тоже и отдаётся один раз из
`assets.rs`, а не дублируется на каждый префикс. И в каждом каталоге уже лежит
подкаталог `tests/`: у ws — api, auth, guard, backend_client; у ss — auth,
control_pool, guard, handlers, proxy. Тесты едут вместе с кодом, который они
проверяют, — именно это делает перенос малорисковым: поведение уже закреплено, и
поломка вылезет сразу.

Исключение — тесты `control_pool`: они уходят вместе с самим пулом (см.
«Решения»).

## Два гейта, оба переезжают

Каждый дашборд прогоняет две независимые проверки до маршрутизации, и обе
переносятся как есть. Одна не заменяет другую.

**Credentials** (`auth.rs`) отвечают на вопрос *кто* может управлять панелью.
Bearer — для скриптов, Basic — для браузера, `WWW-Authenticate` — чтобы браузер
показал форму входа, а не голый 401.

**Origin policy** (`guard.rs`, 177 строк у ws и 204 у ss) отвечает *откуда*
может прийти запрос. Она существует потому, что одних credentials против CSRF
мало: браузер сам прикладывает закэшированные Basic-креды к межсайтовому
запросу, и чужая страница поедет на авторизации оператора. Обратно тоже верно —
origin не аутентифицирует: curl вообще не шлёт `Origin`, и это разрешено
намеренно.

Порядок важен и сохраняется: origin внутри, credentials снаружи, чтобы
неавторизованный получил простой 401, а не 403 с описанием того, чего этот
листенер ждёт.

Одно следствие для развёртывания: за ingress браузерный `Host` — публичное имя
(`ui.k3s.beerloga.su`), а не адрес, на котором слушает под. Это имя обязано быть
в `allowed_hosts`, иначе UI ответит 403 сам себе.

## Отдача HTML под префиксом

Оба UI обращаются к своим API абсолютно (`fetch("/dashboard/api/instances")`).
Под `nest("/ws", …)` такие URL промахнутся, и хуже того — два UI столкнутся на
одних и тех же путях `/dashboard/api/*`.

Посчитано 2026-08-12: **17 абсолютных URL и 12 вызовов `fetch` на все три
HTML-файла** — ограниченная правка, а не переписывание.

Механика: в каждый HTML добавляется одна строка

```js
const API_BASE = "__BASE__";
```

а вызовы становятся `fetch(\`${API_BASE}/dashboard/api/…\`)`. Хендлер, который
отдаёт страницу, подставляет вместо `__BASE__` строку `/ws` или `/ss` в момент
ответа. Механизм подстановки уже есть — `ui.rs` так же подменяет
`__DASHBOARD_REFRESH_MS__`.

`<base href>` отвергнут: он молча переписывает все относительные URL и якоря на
странице, то есть чинит fetch ценой того, чего никто не проверял.

## Конфигурация

Отдельный TOML — у UI нет причин читать конфиг data plane:

```toml
[server]
listen = "0.0.0.0:9000"
# Обязателен. В поде листенер на 0.0.0.0, и доступ к нему даёт все токены
# инстансов ниже. token_file предпочтительнее: секрет приезжает смонтированным
# файлом, а не строкой конфига.
token_file = "/etc/outline-ui/secrets/ui-token"

[[ws.instances]]
name = "beelink102"
control_url = "http://198.18.1.102:9191"
token_file = "/etc/outline-ui/secrets/ws-beelink102"

[[ss.instances]]
name = "cloud1"
control_url = "https://cloud1.beerloga.su/rust-ss-exporter"
token_file = "/etc/outline-ui/secrets/ss-cloud1"
```

Токены инстансов после ротации 2026-08-12 разные на каждый узел, поэтому конфиг
UI несёт их восемь. Каждый читается из файла, чтобы ConfigMap оставался без
секретов, а Secret ротировался без правки конфига.

## Что удаляется из бинарей

**ws-rust**: `src/http/dashboard/` (15 файлов вместе с `tests/` и логотипом),
feature `dashboard` с зависимостями `outline-uplink/cert-check` и `base64`, а
также `[dashboard]` из схемы конфига.

**ss-rust**: `src/server/dashboard/` (15 файлов вместе с `tests/` и логотипом) и
его подключение в `server/mod.rs`.

`constant_time_eq`, `read_limited_body` и `http::serve` **остаются**: их
использует control-плоскость и листенер метрик. Ничего не выносится в общий
крейт — после ухода дашбордов на каждой стороне остаётся ровно один потребитель.

Бинари худеют и перестают отдавать HTML; их control- и metrics-листенеры не
затрагиваются.

## Развёртывание

Deployment + Service + Ingress в namespace `monitoring`, рядом с Grafana. Конфиг
в ConfigMap, девять токенов (один UI + восемь инстансов) — в Secret,
смонтированном в `/etc/outline-ui/secrets/`.

Достижимость уже доказана: из пода в кластере отвечают все control API
(проверено 2026-08-12 — `401` от `198.18.1.102:9191`, `198.18.1.104:9191` и
`https://cloud1.beerloga.su/rust-ws-exporter/…`, то есть сеть проходит и не
хватает только токена). Ноды k3s — `10.10.10.51-53`, парк — `198.18.1.x`,
маршрут между ними работает.

`[server].token` обязателен, а сверху на Ingress можно навесить basic-auth
middleware traefik — такой паттерн в кластере уже есть (`registry-auth`).

## Тестирование

Существующие подкаталоги `tests/` переезжают вместе с кодом и обязаны остаться
зелёными — они уже покрывают auth, guard, ws api, ws backend client, ss proxy и
handlers. Новые тесты покрывают только то, что добавляет сам перенос:

- `auth.rs`: без credentials → 401 с `WWW-Authenticate`; верный Bearer →
  проходит; неверный токен → 401; сравнение constant-time.
- Отдача под префиксом: запрос к `/ws/` возвращает HTML, у которого `API_BASE`
  равен `/ws`, к `/ss/` — `/ss`, и ни в одном ответе не остаётся плейсхолдера
  `__BASE__`.
- Маршрутизация: `/ws/dashboard/api/instances` и `/ss/dashboard/api/instances`
  попадают в разные хендлеры и не сталкиваются.
- `backend.rs`: инстанс, вернувший 401, всплывает как ошибка этого инстанса в
  агрегированном ответе, а не роняет всю страницу.
- После удаления `cargo check -p outline-ws-rust` и `-p outline-ss-rust`
  проходят и с дефолтными фичами, и с `--no-default-features`, а полный гейт из
  `AGENTS.md` (fmt, clippy `-D warnings`, tests) зелёный.

## Риски и известные ограничения

**UI становится единой точкой управления парком.** Сегодня два листенера на двух
узлах держат каждый свои токены; после переноса один под держит все восемь. Это
и есть смысл (одно место охранять), но цена этого пода растёт — отсюда
обязательный токен и опциональная авторизация на ingress.

**Control API открыты на `0.0.0.0` по обычному HTTP.** `.102` и `.104` слушают
`0.0.0.0:9191` / `0.0.0.0:9190` без firewall, поэтому bearer-токены UI пойдут по
LAN открытым текстом. Это было до изменения и отслеживается отдельно; вынос
дашбордов ничего здесь не улучшает и не ухудшает.

**Локального UI на узле не остаётся.** После удаления открыть дашборд на самом
узле будет нечем. Диагностика узла, у которого сломана сеть до кластера,
откатывается на `curl` к его control API.

**Доступность кластера становится доступностью UI.** Если k3s лежит, дашборда
нет вообще. Приемлемо: дашборд — удобство оператора, а не зависимость data
plane, и у Grafana ровно то же свойство.

## Вне области

Метрики самого процесса UI, TLS внутри пода (его терминирует ingress) и любые
изменения в том, что дашборды показывают. Это переезд, а не редизайн: HTML
меняется только там, где этого требует префикс API.
