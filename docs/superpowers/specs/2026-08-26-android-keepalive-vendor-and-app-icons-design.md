# Android: честные статусы keep-alive, вендорские экраны и иконки приложений — дизайн

**Дата:** 2026-08-26
**Статус:** согласовано с владельцем, готово к написанию плана

## Проблема

Клиент на Xiaomi 12 Lite (Android 14) выдал приложению разрешение на работу
с батареей. Карточка «Ignore battery optimisation» сначала показывала
«Allowed», затем — «Not allowed», при том что в настройках телефона у
приложения стоит «Без ограничений».

### Диагноз

Статус читается напрямую из системы при каждой перерисовке
(`PowerManager.isIgnoringBatteryOptimizations`), значение нигде не кэшируется.
Значит UI не врёт: он честно зеркалит стандартный Doze-whitelist, и смена
«Allowed» → «Not allowed» означает, что флаг действительно снялся.

Сталкиваются три независимых слоя, и пользователь видит их как один:

1. **Стандартный Doze-whitelist** — единственное, что читает наш код.
2. **Вендорский автозапуск** (MIUI «Автозапуск») — на Xiaomi **выключен по
   умолчанию для всех приложений**, из стандартного API не виден.
3. **Вендорская политика батареи** (MIUI «Экономия заряда батареи» →
   «Без ограничений») — то, что клиент и выставил. В Doze-whitelist не пишет.

Отзыв стандартного флага на MIUI документирован: в AdGuard
[#3739](https://github.com/AdguardTeam/AdguardForAndroid/issues/3739)
настройка «Don't optimize» «is reset back to 'Optimize' after some time»;
тикет закрыт как Won't Fix — это поведение прошивки. На MIUI 12 системный
диалог Doze-исключения в ряде случаев вообще не появляется
([Briar #2132](https://code.briarproject.org/briar/briar/-/issues/2132)).

Вывод: `isIgnoringBatteryOptimizations()` на MIUI/HyperOS нельзя трактовать
как «настроено навсегда», и одного этого разрешения там недостаточно.

### Сопутствующие дефекты, найденные при разборе

- **Преждевременное перечитывание.** `refresh++` вызывается сразу после
  запуска системного экрана, то есть до того, как пользователь что-либо
  выбрал. Возврата с системного экрана мы не получаем, поэтому карточка
  показывает устаревшее значение до следующего случайного пересоздания.
- **Samsung в списке автозапуска.** `AUTOSTART_COMPONENTS` содержит два
  компонента `com.samsung.android.lool` (`…sm.ui.battery.BatteryActivity`),
  но у One UI **нет** списка автозапуска — это экраны батареи. Плитка
  обещает пользователю не то, что открывает.

## Цели

1. Экран перестаёт показывать устаревшие статусы.
2. Пользователь Xiaomi (и других вендорских прошивок) видит **все** места,
   которые нужно настроить, с точными названиями пунктов.
3. Список приложений в раздельном туннеле показывает иконки.
4. Внешний вид вендорских карточек проверяем на эмуляторе без живого
   устройства.

## Не-цели

- **Чтение состояния автозапуска через hidden-API.** Библиотеки вроде
  `MIUI-autostart` это умеют, но reflection в скрытые API — ровно то
  поведение, из-за которого сборку помечает Play Protect. Статус вендорских
  карточек остаётся «Проверьте вручную».
- Автоматическое включение вендорских настроек: API не существует ни у
  одного из вендоров.
- Изменение логики самого туннеля.

## Фичи

### F1. Статусы перечитываются при возврате на экран

Статусы keep-alive перечитываются, когда экран снова становится видимым, а
не по факту нажатия кнопки. Это покрывает все пути возврата: системный
диалог, настройки через шторку, переключение задач.

Преждевременный `refresh++` из обработчиков кнопок убирается — он читает
состояние до решения пользователя.

Затрагивает все карточки экрана, а не только батарейную: `alwaysOnSeen`,
точные будильники, уведомления, тип сети страдали тем же.

### F2. Карточка вендорской политики батареи

Отдельная карточка, показываемая только на прошивках, где такая политика
существует отдельно от Doze.

- Статус: всегда «Проверьте вручную» (амбер) — читать нечем.
- Кнопка ведёт на вендорский экран политики; для Xiaomi это прямая ссылка
  `com.miui.powerkeeper/…HiddenAppsConfigActivity`, с запасным вариантом на
  общий экран батареи приложения.
- Текст называет пункт дословно. Где формулировка разъехалась между
  версиями прошивки — приводятся оба варианта: «Экономия заряда батареи» →
  «Без ограничений» (в MIUI 12 — «Контроль активности» → «Нет ограничений»).

### F3. Карточка автозапуска называет конкретный тумблер

Имя вендора в заголовке остаётся. Меняется описание: вместо общего
«откройте экран и разрешите» — что именно включить.

| Вендор | Что включить |
|---|---|
| Xiaomi / Redmi / POCO | «Автозапуск»; на MIUI 14/HyperOS также «Автозапуск в фоновом режиме» |
| Huawei, Honor | «Запуск приложений» → снять «Управлять автоматически» → включить «Автозапуск», «Косвенный запуск», «Работа в фоновом режиме» |
| Oppo, realme | «Разрешить автозапуск» |
| vivo, iQOO | «Автозапуск» |
| OnePlus | «Автозапуск» |
| Asus | «Диспетчер автозапуска» |
| Meizu | «Работа в фоновом режиме» |
| Tecno, Infinix, itel | «Управление автозапуском» |
| **Samsung** | **Не автозапуск.** Список неспящих приложений (Настройки → Батарея → «Ограничения в фоновом режиме»). Сам список One UI переименовывает между версиями («Неспящие приложения», «Никогда не отключать»), поэтому в тексте называется экран — он стабилен — и приводятся оба варианта |

Samsung переносится из списка автозапуска в собственную карточку с честным
текстом. Прошивки без отдельного списка (Pixel/AOSP, Sony, Motorola,
Nothing, Lenovo, HMD/Nokia) карточку автозапуска не получают.

### F4. Иконки приложений в раздельном туннеле

Строка списка получает иконку приложения слева от названия.

- `AppInfo` **не меняется**: он намеренно свободен от `PackageManager`, на
  этом держится юнит-тест `filterNetworkApps` без устройства.
- Иконка грузится лениво, только для строк, которые реально видны, в
  IO-потоке, и кладётся в `LruCache` с ограниченным размером.
- Иконка масштабируется до размера показа: хранить сотни adaptive-иконок в
  исходном разрешении нельзя.
- Пока иконка едет — нейтральный плейсхолдер того же размера, чтобы строки
  не прыгали.
- Новых зависимостей не добавляется.

### F5. Debug-подмена вендора

Отладочный оверрайд, позволяющий увидеть вендорские карточки на эмуляторе,
где ни одного вендорского пакета нет.

- Хранится в `SharedPreferences`, читается **только** при `BuildConfig.DEBUG`.
- Подменяет и определение вендора, и проверку доступности экрана — иначе
  карточка не покажется, так как `resolveActivity` на эмуляторе вернёт
  `null`. Кнопка при этом ничего не откроет, что безопасно: запуск обёрнут
  в `launchSafely`.
- В UI ничего не появляется; задаётся из CLI через `run-as` (debug-сборка
  это позволяет).
- В релизной сборке кода нет.

## Архитектура

Вендорские знания собираются в одну таблицу профилей вместо нынешнего
плоского списка компонентов. Профиль описывает всё, что мы знаем о прошивке:

- сопоставление с `Build.MANUFACTURER`;
- кандидаты экранов автозапуска (наиболее специфичный первым);
- кандидаты экранов вендорской политики батареи;
- какие строки показывать (название тумблера либо, для многошаговых
  прошивок вроде Huawei/Honor и особого случая Samsung, — собственное
  описание).

Разрешение «какой профиль у этого телефона» и «какой интент запускать» —
чистая логика без `PackageManager`, отделённая от Android-вызовов так же,
как это уже сделано в `filterNetworkApps`. Это делает её юнит-тестируемой
без устройства.

Выбор экрана остаётся защищённым в два слоя, потому что живых устройств у
нас нет: `resolveActivity` перед показом кнопки и `launchSafely` при
запуске. На незнакомой прошивке карточка просто не появится.

Загрузка иконок живёт в отдельном небольшом модуле: кэш плюс
composable-хелпер, отдающий иконку по имени пакета. Экран раздельного
туннеля о механике загрузки не знает.

## Строки

Все новые строки добавляются в `values/strings.xml` и `values-ru/strings.xml`
одновременно: в проекте включён fatal-гейт `MissingTranslation` /
`ExtraTranslation`, расхождение уронит сборку.

Описание автозапуска строится как шаблон с подстановкой названия тумблера —
это покрывает большинство вендоров одной парой строк. Huawei/Honor (цепочка
из трёх переключателей) и Samsung (иная подсистема) получают собственные
описания.

Русские формулировки проходят `ru-text:ru-check`, как и остальной интерфейс.
Названия пунктов прошивок — это цитаты из вендорского UI: они переводятся не
дословно, а берутся такими, как их видит пользователь на своём языке.

## Тестирование

**Юнит-тесты** (JVM, без устройства, рядом с кодом в
`android/app/src/test/java/com/outline/proxy/`):

- сопоставление `Build.MANUFACTURER` → профиль вендора, включая регистр и
  неизвестного производителя;
- Samsung не попадает в автозапуск и получает собственный профиль;
- прошивки без вендорского слоя не дают ни одной вендорской карточки;
- выбор первого доступного кандидата среди экранов.

**Проверка внешнего вида на эмуляторе** (`Pixel_10`, методика уже
отработана): под каждым вендором из таблицы снимается экран «Поддержание
связи» и проверяется, что карточки, заголовки и тексты отображаются
целиком, без обрезаний и наложений. Отдельно снимается список раздельного
туннеля с иконками.

**Сборка и гейт:** `./gradlew :app:testDebugUnitTest :app:assembleDebug
:app:lintDebug`. Rust не затрагивается, но гейт `android/rust` должен
остаться зелёным.

## Риски и ограничения

- **Вендорские интенты непроверяемы.** Живых устройств нет ни у нас, ни у
  владельца; телефон клиента недоступен. Отсюда двухслойная защита
  (`resolveActivity` + `launchSafely`) и сознательный отказ от единственного
  способа прочитать состояние (hidden-API).
- **Формулировки прошивок плавают** между версиями (MIUI 12 → 14 →
  HyperOS). Там, где расхождение известно, в тексте даются оба варианта;
  полной гарантии совпадения с конкретной сборкой нет.
- **Экран удлиняется.** Добавляется до двух карточек, но только на тех
  прошивках, где они осмысленны; на стоковом Android вид не меняется.
- **F1 чинит отображение, а не прошивку.** Если HyperOS снимет Doze-флаг
  снова, честный ответ — «Нужно действие»; именно поэтому появляются F2 и
  F3, показывающие остальные два слоя.
