# Форма начала сессии: убрать метки и нарезать по браузерным размерам — дизайн

Дата: 2026-11-02. Статус: согласован с владельцем по частям, ждёт ревью спеки.

## Зачем

Классификаторы «TLS внутри TLS» (Xue et al., USENIX Security 2024) узнают прокси по началу сессии: внешняя
запись размером с вложенный ClientHello, через RTT — всплеск размером с ответ сервера с сертификатами, затем
короткая запись (Finished). Работа упреждающая: признаков, что нас уже так распознают, нет; приоритет — не
навредить скорости и совместимости.

## Что показал замер

Стенд: docker, Chromium 156, наши `outline-ss-rust` / `outline-ws-rust` из `d36c734c`, RTT носителя 40 мс.
Отчёт и CSV: scratchpad `early-shape/REPORT.md` (вне репозитория), выводы — в памяти проекта
(`early-session-shape-measurements`).

| Носитель | Что видно снаружи |
|---|---|
| `ws_h1` | CH одной записью CH+59 (SS) / +58..66 (VLESS); через RTT одна s→c запись = внутренний flight +128 (SS) / +21 (VLESS); перед CH отдельная запись 130–141 B (заголовок SS2022) |
| `ws_h2`, `xhttp_h2` | запись 26 B (голый заголовок кадра DATA), затем CH режется на постоянную 1041 + остаток; flight одной записью |
| `ws_h3`, `xhttp_h3` | записи растворены в пакетах 1439–1452, суммы и паузы видны (вне рамок, см. ниже) |
| VLESS на ws/h2 | отдельная s→c запись 21 B (ответ `[VER,0]`) за ~1 RTT до flight |

Паддинг 0..256 структуру не меняет: число и порядок записей те же, каждая растёт на 4+U(0..256); cover-кадры в
начале не срабатывают (включаются на простое 250–1500 мс).

Chromium (TCP, 48 соединений): после рукопожатия c→s `1 + 53/63/79 + 87 + 336..838`; s→c 2×NewSessionTicket
74–298 или SETTINGS 445–937 + 57, затем ответ (1283 / 2631 / 16401). Записей ≥ 1,5 КБ первым запросом нет.

## Решения владельца

- Включение: всегда на padded-путях, без новых ключей конфига (часть 2); часть 1 — всегда.
- Направления: оба (клиент и сервер формируют свои отправки).
- Порядок: сначала метки (часть 1), потом нарезка (часть 2).
- Пауза «запрос — RTT — ответ» сейчас не скрывается; отпечаток h3-стека — отдельный следующий дизайн.

## Не цели

- h3-носители (QUIC сам режет на пакеты по MTU; нарезка не меняет суммы и паузы).
- UDP (SS-UDP, VLESS-UDP, датаграммы): одна запись = один пакет, резать нельзя.
- Тайминги (задержки, фоновый трафик).
- Отпечаток h3-стека: Initial 1200 против 1250/1252, лесенка проб MTU у клиента (у Chromium проб нет).
- Изменение провода: всё ниже меняет только то, как отправитель группирует данные в записи; старые узлы совместимы
  в обе стороны.

## Часть 1. Убрать постоянные метки (всегда, на всех путях)

### 1.1. Записи 26 и 1041 на h2 (клиент и сервер)

Причина: крейт `h2` (0.4.15, `codec/framed_write.rs`) видит, что TLS-поток не поддерживает векторную запись, и
пишет заголовок кадра и полезную нагрузку раздельно (`poll_write_buf` по `Chain`), а для данных крупнее
`CHAIN_THRESHOLD_WITHOUT_VECTORED_IO = 1024` порог даёт кусок 1024. rustls делает из каждого вызова записи отдельную
TLS-запись: 9+17 = 26, 1024+17 = 1041.

Решение: адаптер `CoalescingWrite<T>` поверх TLS-потока, который отдаётся `h2`:
- `is_write_vectored() -> true`;
- `poll_write_vectored` склеивает все переданные срезы (до лимита, например 16 КиБ — размер записи TLS) в один
  буфер и делает **один** `poll_write` нижнего потока; частичная запись нижнего потока обрабатывается как обычно
  (возвращается число принятых байт);
- остальное — прозрачный проброс.
С векторным I/O `h2` использует порог 256 и отдаёт заголовок вместе с данными — кадр уходит одной записью.

Где: клиентские h2-носители (`crates/outline-transport/src/h2/shared.rs`, `xhttp/h2.rs`) и h2-листенер сервера
(`bins/outline-ss-rust/src/server/bootstrap/axum.rs` / `tls.rs` — место, где TLS-поток отдаётся hyper/h2). Точные
точки — в плане.

### 1.2. Отдельная запись ответа VLESS (сервер)

Причина: `bins/outline-ss-rust/src/server/transport/vless/tcp.rs` сразу после подключения к цели кладёт
`[VERSION, 0]` отдельным сообщением в `data_tx`.

Решение: ответ не отправляется сразу, а ставится перед первыми данными от цели одним сообщением (с паддингом, как
сейчас, через `frame_downlink_message`). Если цель закрылась, ничего не прислав, ответ уходит один перед закрытием.
Пути resume (ack-prefix v1, replay v2) и mux не меняются, если ответ там уже идёт вместе с данными; иначе — тот же
приём. VLESS-UDP: ответ — тоже перед первым ответным пакетом (клиент откроет датаграммы чуть позже; до этого
пакеты идут потоком, как и сейчас при `unarmed`).

### 1.3. Отдельная запись заголовка SS2022 (клиент)

Причина: `crates/outline-transport/src/tcp_transport/writer/mod.rs::send_chunk` при первом вызове (адрес цели)
сразу пишет кадр заголовка; первые данные приложения (CH) приходят через ~4 мс и уходят следующей записью. У VLESS
заголовок уже склеивается с первыми данными.

Решение: кадр заголовка строится как сейчас, но не пишется, а откладывается; первый `send_chunk` / `send_chunks`
с данными пишет заголовок и первый чанк одним `write_frame`. Если данных нет за `SS2022_HEADER_HOLD = 50 мс`
(протоколы, где первым говорит сервер: SSH, SMTP), заголовок уходит один, как сейчас. Writer получает метод
`flush_pending_header()`; таймер живёт в relay-цикле, который читает данные клиента (SOCKS-relay и upstream-задача
TUN-движка): ожидание первого чтения обёрнуто в `tokio::time::timeout(SS2022_HEADER_HOLD)`, по истечении
вызывается `flush_pending_header()`, и цикл продолжает читать как обычно — новой задачи на сессию нет. Пробы (`send_chunk(&[])` в
`probe/tcp_tunnel.rs`, миграция в `outline-tun`) — сохраняют текущее поведение (явный сброс заголовка).

### 1.4. Паддинг всего downlink VLESS-mux (сервер, исправление)

Найдено при планировании: на сервере весь downlink VLESS-mux идёт мимо паддинга — заголовок ответа
(`vless/mod.rs` resume и fresh), данные подсоединений (`vless_mux/tcp_sub.rs`, `udp_sub.rs`) и кадры завершения
(`vless_mux/frames.rs::send_end`), хотя uplink декодируется как padded. На padded-пути это сломало бы декодер клиента;
наш клиент mux не инициирует, поэтому не проявлялось. Решение: схема паддинга пути хранится в `MuxState` и
передаётся в задачи подсоединений; каждая отправка идёт через `frame_downlink_message`. На не-padded пути поведение
прежнее.

### 1.5. Xray-подписка не берёт padded-эндпоинты (ops/access-keys, исправление)

Найдено при планировании: `ops/access-keys/xray_json.py::_vless_path` берёт первый VLESS-эндпоинт типа без учёта
`padded`, а Xray паддинг не умеет; на .104 padded-эндпоинты стоят первыми. Решение: Xray-подписка строится только по
непадед эндпоинтам, а при их отсутствии `<user>.json` не создаётся (как Outline-артефакт уже пропускает padded-пути).

## Часть 2. Нарезка начала сессии (padded-пути, TCP-сессии на h1 и h2)

### Окно

Для каждой сессии и каждого направления — своё окно: первые `N` сообщений или первые `B` байт полезной нагрузки,
что раньше; `N` случайно в 6..=10, `B` случайно в 16..=24 КиБ. После окна — обычный паддинг 0..256, писатель
объединяет записи как сейчас. Задержек нет.

### Нарезка

| Направление | Режем, если сообщение больше | Куски | Ориентир Chromium |
|---|---|---|---|
| клиент → сервер | 900 B | случайные 300..=850 B, последний — остаток (если остаток < 300, приклеивается к предыдущему) | HEADERS 336–838 |
| сервер → клиент | 1500 B | 2..=4 куска, каждый 600..=2800 B, сумма = сообщение (последний — остаток) | ответы 1283 / 2631 |

Каждый кусок — отдельное сообщение `Binary` с обычной добивкой 0..256 (как сейчас на padded-путях).

### Короткие записи в начале (только клиент → сервер)

Перед первым куском первого крупного сообщения сессии с вероятностью 1/2 отправляются 1..=2 cover-кадра
(`real_len = 0`) с добивкой 40..=100 B — как браузерные `1 / 53..79 / 87` после рукопожатия. Cover-кадр — существующий
формат, получатель его уже отбрасывает.

### Отдельные записи TLS

В окне каждый кусок и каждый cover-кадр отправляется со своим сбросом (flush), чтобы писатель не склеил их в один
вызов записи: на h1 это отдельная запись TLS, на h2 — отдельный кадр DATA (после 1.1 — одна запись с заголовком).
Вне окна — текущее поведение.

### Компоненты

- `early_shape` (чистая логика, без RNG и часов — RNG передаёт вызывающий, как в `padding.rs`): состояние окна
  (`msgs_left`, `bytes_left`), функция «разрезать сообщение» → список размеров кусков, функция «cover перед
  первым куском» → 0..=2 размеров. Размещение: общий код в `crates/outline-wire` (без зависимости от `rand`) +
  тонкие обёртки на стороне клиента (`outline-transport`) и сервера (`outline-ss-rust`), как у `carrier_padding`.
- Клиент: точки, где сейчас применяется паддинг — `WsWriteTransport::write_frame` (SS-TCP) и
  `WsFrameSink::send_frame` (VLESS-TCP); формирователь создаётся на сессию, если путь padded и носитель h1/h2.
- Сервер: `ChannelSink` (SS-TCP downlink) и downlink VLESS-TCP (`frame_downlink_message`); формирователь на сессию,
  если путь padded и сессия пришла по h1/h2 (`route.protocol`).

## Ошибки и края

- Сумма кусков без добивки всегда равна исходному сообщению (инвариант, тест).
- Сообщения с control-сигналом (`OCTL`) и cover-кадры по таймеру простоя не режутся и не считаются в окно.
- Resume / migration сессии: окно не перезапускается (новая сессия — новое окно).
- Если нижний поток вернул ошибку на сбросе — как сейчас при ошибке записи (сессия закрывается).

## Тестирование

- Юнит (`outline-wire`, `tests/early_shape.rs`): размеры кусков в диапазонах; окно останавливается по `N` и по `B`;
  короткие сообщения не режутся; сумма кусков = сообщение; cover 0..=2, размеры 40..=100; детерминизм на seeded RNG.
- Юнит: `CoalescingWrite` — векторный вызов из нескольких срезов даёт ровно один `poll_write` нижнего потока;
  частичная запись корректна.
- Юнит/интеграция: ответ VLESS приходит одним сообщением с первыми данными; при пустом upstream — один; заголовок
  SS2022 уходит вместе с первыми данными, а без данных — один через 50 мс.
- e2e: существующие `bins/outline-ws-rust/tests/e2e_padding.rs` и TLS-носители — данные доходят без искажений;
  плюс тест на крупный первый запрос по padded `ws_h1` (нарезка в окне не ломает поток).
- Повтор замера на стенде (`early-shape`). Критерии успеха:
  - h2: нет записей 26 и 1041; VLESS: нет отдельной s→c 21 B; SS: нет отдельной записи 130–141 B;
  - padded h1/h2: в окне нет c→s записей > 1,5 КБ; внутренний flight приходит ≥ 2 записями;
  - размеры первых записей укладываются в диапазоны Chromium (c→s 300–850 + короткие; s→c 600–2800).

## Выкатка

Провод не меняется, поэтому порядок свободный; как обычно — серверы, затем клиенты, по одному узлу. После выкатки —
выборочная проверка падения скорости больших загрузок (не должно быть: окно ≤ 24 КиБ) и рестартов.

## Цена

Несколько сотен байт добивки и 1–4 лишних записи TLS на сессию, только в начале; до 50 мс на установку для
протоколов, где первым говорит сервер (часть 1.3).
