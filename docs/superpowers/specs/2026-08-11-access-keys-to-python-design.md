# Генерация access-key артефактов переезжает в Python (дизайн)

Дата: 2026-08-11
Статус: согласован в чате; ждёт ревью владельца

## Задача

Клиентские конфиги (`.conf`) генерирует серверный бинарь — режим
`AppMode::GenerateKeys`, 804 строки в `config/access_key.rs` плюс 531 строка
тестов. Подписки Xray-JSON (`.json`) с 2026-08-11 генерирует Python
(`ops/xray-json-sub/`). Два генератора пишут в один каталог, и любая правка
формата ссылок требует пересборки бинаря и выкладки на парк.

Правки эти — не редкость. История совместимости с xray-семейством
(`happ`, `hiddify`, `v2rayN`) — это последовательность мелких итераций по
ALPN, форме пути XHTTP и режимам `packet-up` / `stream-one`, и каждая стоила
раскатки бинаря на все узлы.

Цели, все три:

1. менять формат ссылок без пересборки и раскатки бинаря;
2. держать генерацию всех артефактов в одном месте;
3. убрать из серверного бинаря то, что не относится к data plane.

## Что есть сейчас (проверено 2026-08-11)

Генерация в Rust имеет ровно двух потребителей:

- `AppMode::GenerateKeys` — режим CLI, в котором бинарь не поднимает сервер, а
  пишет артефакты и выходит. Его зовёт `save-keys.sh` на узлах.
- `GET /control/users/{id}/access-urls` → `build_access_key_artifacts_for_user`.
  Единственный клиент этого эндпоинта — серверный дашборд
  (`bins/outline-ss-rust/src/server/dashboard/`), три кнопки-чипа `Outline` /
  `SS` / `VLESS`. **`[dashboard]` не сконфигурирован ни на одном из четырёх
  узлов**, где генерируются ключи (`cloud1`, `cloud2`, `nuxt`, `nuxt2`), то есть
  в проде эндпоинт не вызывает никто.

`POST /control/users` ссылок не возвращает — он отдаёт `UserView`.

Артефакты складываются в `/var/www/html/<keys-prefix>/` и раздаются
через nginx. Отчёт о записи уходит в `/opt/outline/outline-ss-rust/users.txt`
(28 686 байт на cloud1).

Реально генерация нужна на `cloud1` / `cloud2` — это точка входа мобильных
клиентов; на `nuxt` / `nuxt2` `save-keys.sh` тоже есть. Генератор должен
оставаться узло-агностичным: `public_host`, `public_scheme` и `url_base` он
берёт из `[access_keys]` локального конфига.

Две детали вскрылись только при раскатке 2026-08-11 и вошли в решение:

- **`file_extension` в боевых конфигах отсутствует.** Расширение `.conf`
  передавалось бинарю флагом `--access-key-file-extension` из `save-keys.sh`.
  Генератор, читающий только конфиг, писал бы `<user>.yaml`, и все клиентские
  ссылки отдавали бы 404. Поэтому у CLI есть флаг `--file-extension`,
  переопределяющий конфиг, и он обязателен в `save-keys.sh`.
- **На `nuxt` / `nuxt2` балансер должен указывать на сам узел.** Дефолтная пара
  cloud1+cloud2 дала бы там подписку, ведущую на другие хосты. Узлы передают
  `--node <свой хост>`.

## Решение

### Что уходит из Rust

| Файл | Что удаляется |
|---|---|
| `config/access_key.rs` | целиком (804 строки) |
| `config/tests/access_key.rs` | целиком (531 строка) |
| `config/resolved.rs` | `AccessKeyConfig`, его `Default`, поле `access_key` в `Config` |
| `config/validation.rs` | `impl AccessKeyConfig` (проверка `public_scheme`) |
| `config/cli.rs` | `--public-host`, `--public-scheme`, `--access-key-url-base`, `--access-key-file-extension`, `--print-access-keys`, `--write-access-keys-dir` |
| `config/loader.rs`, `lib.rs` | режим `AppMode::GenerateKeys` и его ветка |
| `server/control/{server,handlers,manager}.rs` | роут `/control/users/{id}/access-urls`, `get_user_access_urls`, `access_urls`, `AccessUrlsView`, `AccessUrlError` |
| `server/dashboard/{mod,handlers}.rs` | прокси-роут `/dashboard/api/users/{id}/access-urls` |
| `server/dashboard/dashboard.html` | три кнопки-чипа и их обработчик |

### Что остаётся и почему

Секция `[access_keys]` в `config/file.rs` **не удаляется**. Структуры конфига
помечены `#[serde(deny_unknown_fields)]`, а секция присутствует в боевых
`config.toml` на всех четырёх узлах: убрав её парсинг, мы уронили бы сервер при
старте — сразу везде, включая узлы, куда бинарь приедет раньше правки конфига.

Она остаётся принимаемой, но инертной. Прецедент в кодовой базе есть
(`padding.throttle_edge_min_bytes_per_sec`), но с одним отличием: там уместен
warn «удалите ключ», здесь — нет. Секцию теперь читает Python, и советовать её
удалить было бы вредно. Принимаем молча, с комментарием в коде, что владелец
секции переехал в `ops/access-keys/`.

### Что появляется в Python

Каталог `ops/access-keys/` заменяет `ops/xray-json-sub/`:

| Файл | Ответственность |
|---|---|
| `config_model.py` | `config.toml` → юзеры с разрешёнными полями: `enabled`, `method`, `password`, `vless_id` и шесть путей (`ws_path_tcp`, `ws_path_udp`, `ws_path_vless`, `ws_path_ss`, `xhttp_path_vless`, `xhttp_path_ss`), плюс `[access_keys]` |
| `uri.py` | percent-encoding, SIP002-userinfo, ALPN-список, шесть URI-строителей, `ssconf://`, метки-фрагменты |
| `outline_yaml.py` | Outline-артефакт `<user>.conf` |
| `xray_json.py` | Xray-JSON подписка — переезжает как есть |
| `artifacts.py` | Сборка трёх файлов на юзера из слоёв выше; плюс `legacy_artifacts` — семь файлов в форме бинаря, только для сверки, на диск не пишутся |
| `generate_keys.py` | CLI: атомарная запись и отчёт |

На узлах — `/opt/outline/access-keys/`; `save-keys.sh` сводится к одному вызову
вместо двух. Прежний `/opt/outline/outline-ss-rust/generate_xray_json.py`
удаляется.

### Новая раскладка: три файла на юзера

Сегодня бинарь пишет до семи файлов на юзера — по одному на артефакт, и шесть
из них содержат ровно одну строку с URI. Раскладка меняется на три файла:

| Файл | Условие | Содержимое |
|---|---|---|
| `<user>.conf` | есть `password` | Outline YAML (как сейчас, побайтово) |
| `<user>.json` | есть `vless_id` и хотя бы один путь VLESS | Xray-JSON подписка с балансером (как сейчас) |
| `<user>.txt` | есть хоть один URL | все URL юзера, по одному в строке |

Расширение `.conf` берётся из `[access_keys] file_extension`; `.json` и `.txt`
фиксированы.

Содержимое `<user>.txt` — plain-список, порядок фиксирован и повторяет порядок
генерации артефактов в бинаре:

```
ssconf://<host>/<base>/<user>.conf      # если есть password и задан url_base
ss://...#<host-short>:<user>-ss-ws
ss://...#<host-short>:<user>-ss-xhttp-packet-up
ss://...#<host-short>:<user>-ss-xhttp-stream-one
vless://...#<host-short>:<user>-vless-ws
vless://...#<host-short>:<user>-vless-xhttp-packet-up
vless://...#<host-short>:<user>-vless-xhttp-stream-one
```

Строки, для которых нет условия (нет `ws_path_ss`, нет `vless_id` и так далее),
просто отсутствуют — файл не содержит пустых мест. Комментариев и меток внутри
нет: метка носителя и так живёт во fragment каждого URI, а комментарии сделали
бы файл непригодным как подписка для xray-клиентов.

Первая строка — `ssconf://`, ссылка на собственный `<user>.conf` для
Outline-клиента: это тоже «раздельный URL», просто другого клиента.

**Сами URI не меняются ни на байт** — меняется только то, как они разложены по
файлам. Это разделение важно: перенос по-прежнему обязан воспроизвести формат
ссылок точно, и любые правки формата остаются отдельной задачей.

Выключенные юзеры (`enabled = false`) не попадают никуда: `effective_users`
фильтрует их до генерации. Дубликаты `id` — ошибка.

### Старые артефакты удаляются

Шесть файлов вида `<user>-vless-ws.conf` перестают генерироваться и удаляются с
узлов при переключении. Владелец подтвердил (2026-08-11), что подписок на эти
URL нет — файлы использовались как источник для копирования ссылки вручную.
Каталог чистится явным шагом, а не оставляется зарастать.

Формы URI:

```
vless://<id>@<authority>?type=ws&security=<tls|none>[&alpn=<list>]&path=<path>&encryption=none#<fragment>
vless://<id>@<authority>?type=xhttp&mode=<mode>&security=<...>[&alpn=<list>]&path=<path>&encryption=none#<fragment>
ss://<b64(method:password)>@<authority>?type=ws&security=<...>[&alpn=<list>]&path=<path>#<fragment>
ss://<b64(method:password)>@<authority>?type=xhttp&mode=<mode>&security=<...>[&alpn=<list>]&path=<path>#<fragment>
```

`security` = `tls` при `public_scheme = wss`, иначе `none`; порт по умолчанию
443 для `wss` и 80 для `ws`. `<b64>` — url-safe base64 без паддинга от
`method:password`. `<fragment>` = `<host-short>:<user>-<proto>-<carrier>[-<submode>]`,
где `host-short` — часть хоста до первой точки (или адрес целиком, если это IP).

ALPN — списки различаются по носителю, и это главная ловушка переноса:

| Носитель | `[server.h3]` настроен | иначе |
|---|---|---|
| WS | `h3,h2,http/1.1` | `h2,http/1.1` |
| XHTTP `packet-up` | `h3,h2,http/1.1` | `h2,http/1.1` |
| XHTTP `stream-one` | `h3,h2` | `h2` |

`stream-one` не получает `http/1.1`, потому что поверх h1 он отбивается с 505
(hyper не умеет full-duplex), и приглашать клиента выбрать этот транспорт
нельзя. При `public_scheme = ws` (plain HTTP) параметр не эмитится вовсе — ALPN
это расширение TLS.

Кодирование, побайтово как в Rust:

- query-значения: сохраняются `A-Za-z0-9` и `-._~`, остальное → `%XX`
  **заглавными** hex;
- fragment: то же плюс `:`;
- `path` нормализуется ведущим слэшем;
- host: IPv6 заворачивается в скобки;
- `url_base` обязан начинаться с `http://` или `https://`, хвостовой слэш
  срезается;
- `ssconf://` получается заменой схемы `https://` / `http://`;
- `sanitize_filename`: не-`[A-Za-z0-9._-]` → `_`, пустой результат → `user`;
- YAML-строки квотятся с экранированием `\` и `"`.

### users.txt

Формат отчёта о записи сохраняется — блоки, разделённые пустой строкой:

```
user: <id>
written_file: <path>
config_url: <url>          # если задан url_base
access_key_url: <ssconf-url>
```

Отчёт печатается в stdout, а `save-keys.sh` перенаправляет его в `users.txt`.

Раскладка сменилась с «блок на артефакт» на «блок на юзера», иначе отчёт
описывал бы файлы, которых больше нет:

```
user: <id>
written_conf: <path>       # если есть password
written_json: <path>       # если есть vless_id и путь
written_txt: <path>
config_url: <url>          # если задан url_base
access_key_url: <ssconf-url>
```

Это единственное место, где формат намеренно расходится со старым: `users.txt`
— ops-артефакт для человека, его никто не парсит. Флаг `[access_keys] print`
(на проде `false`) сохраняется и, как прежде, добавляет перед основным отчётом
второй — с путями, которые *будут* записаны, — и пустую строку-разделитель.

### Как ловим расхождение

Раскладка меняется, поэтому `diff -r` каталогов больше не годится: сверять надо
**URI, а не файлы**.

**Golden-файлы.** В репозитории — синтетический `config.toml` с фейковыми
кредами, покрывающий все ветки (юзер только с SS, только с VLESS, с обоими,
с per-user путями, с per-user `method`, выключенный, с id, требующим
санитизации), и эталон, снятый с текущего бинаря. Эталон хранится в форме
«имя артефакта → содержимое», то есть ровно как его пишет бинарь сегодня;
тесты собирают из вывода Python те же пары и сверяют побайтово. Так эталон
остаётся снимком *старого* поведения и не подстраивается под новый код.

**Сверка на узле.** Перед переключением `save-keys.sh` на каждом узле:
Rust пишет свои семь файлов в один scratch-каталог, Python — свои три в другой,
после чего сверяется, что множество URI совпало. Конкретно: `<user>.conf`
сравнивается побайтово, а строки `<user>.txt` — с содержимым шести
одностроковых файлов плюс `ssconf://`-ссылка из отчёта. Расхождение хоть в
одном символе останавливает раскатку.

## Что НЕ входит

- **Перенос генерации на узлы, где её нет.** `save-keys.sh` есть на четырёх
  узлах — там и остаётся.
- **Изменение формата самих ссылок.** Меняется раскладка по файлам, но каждый
  URI обязан остаться побайтово прежним; правки формата URI — отдельной задачей
  после.
- **Откат старых семи файлов.** Раскладка «файл на артефакт» не
  восстанавливается: откат на этом шаге — это возврат `save-keys.sh` к вызову
  бинаря, который снова создаст их сам.
- **Возврат кнопок в дашборд.** Решено убрать их вместе с эндпоинтом.
- **Секция `[access_keys]` в `config.toml`.** Остаётся на месте, её читает
  Python.

## Риски

- **Побайтовое расхождение URI.** Главный риск: лишний `%2C`, потерянный
  `http/1.1`, другой регистр hex — и ссылка импортируется, но не работает.
  Закрывается golden-файлами и сверкой URI на узле; именно поэтому перенос
  запрещено совмещать с правками формата.
- **Удаление старых артефактов.** Шесть файлов на юзера удаляются с узлов.
  Владелец подтвердил, что подписок на эти URL нет; если бы они были, отказ был
  бы тихим — клиент просто перестал бы обновляться. Удаление идёт отдельным
  шагом после того, как новые три файла уже лежат и проверены, так что окна без
  артефактов не возникает.
- **`deny_unknown_fields`.** Удаление секции `[access_keys]` из парсера уронило
  бы сервер на старте на всех узлах. Секция остаётся принимаемой; это
  зафиксировано тестом.
- **Порядок раскатки.** Бинарь без генерации, приехавший раньше, чем Python
  начал писать артефакты, оставит узел без свежих ключей. Порядок обязателен:
  Python → сверка → переключение `save-keys.sh` → бинарь.
- **Разнородный парк.** Пока новый бинарь не раскатан везде, на части узлов
  генерация останется в Rust. Это допустимо: `save-keys.sh` там уже зовёт
  Python, а неиспользуемый режим бинаря вреда не приносит.
- **Потеря функции дашборда.** Кнопки исчезнут. Дашборд не развёрнут, так что
  заметить будет некому — но если его поднимут, ссылки придётся брать из
  файлов.
- **`provision-node`.** `collect-from-reference.sh` выпарсивает
  `--write-access-keys-dir` из `save-keys.sh`, чтобы узнать каталог ключей.
  После переключения этой строки в файле не станет — парсер надо научить новой
  форме, иначе клон узла получит пустой `ACCESS_KEYS_DIR`.

## Проверки

1. `python3 -m unittest` в `ops/access-keys/` — golden-сверка зелёная.
2. На каждом узле: множество URI, собранное из Python-вывода, совпадает с
   множеством из Rust-вывода, а `<user>.conf` совпадает побайтово. Расхождение
   в одном символе останавливает раскатку.
3. `cargo check -p outline-ss-rust`, `cargo clippy --workspace --exclude
   sockudo-ws --all-targets --no-deps -- -D warnings`, `cargo test --workspace
   --exclude sockudo-ws`, `cargo fmt --check` по списку пакетов из `AGENTS.md`.
4. Тест, что конфиг с секцией `[access_keys]` по-прежнему загружается новым
   бинарём.
5. Сервер стартует с боевым `config.toml` (сухой прогон `--check` или запуск на
   одном узле под наблюдением).
6. После переключения в каталоге на каждого юзера ровно три файла, старых
   шести нет, и `<user>.conf` имеет тот же sha256, что и до переключения.
7. `<user>.txt` скачивается по HTTPS и импортируется в Happ как подписка —
   plain-список URI клиент принимает.

## Порядок раскатки

Работа делится на два плана, и граница между ними проходит после шага 6.
Первый заканчивается тем, что артефакты на всех четырёх узлах пишет Python, а
Rust-генерация ещё цела и служит эталоном для отката. Второй удаляет её из
бинаря. Разделение намеренное: пока Python не отработал на проде, откат — это
одна строка в `save-keys.sh`.

**План 1 — переключение на Python:**

1. Python-пакет в репозиторий, golden-тесты зелёные.
2. Выложить `ops/access-keys/` на `cloud2`, сгенерировать в scratch-каталог,
   сверить URI против текущих артефактов — совпало.
3. Переключить `save-keys.sh` на `cloud2`, прогнать, убедиться, что три новых
   файла на месте и `<user>.conf` не изменился.
4. Удалить старые шесть файлов на юзера на `cloud2`.
5. Шаги 2–4 на `cloud1`, затем `nuxt`, `nuxt2` — по одному узлу.
6. Поправить `collect-from-reference.sh` под новую форму `save-keys.sh`.

**План 2 — вычистка Rust:**

7. Удалить код из Rust, прогнать CI-гейт.
8. Раскатать бинарь по `ops/deploy/deploy-binary.sh`, по одному узлу.
