# `max_carrier_flows`: общий лимит носителей для TCP+UDP

**Дата:** 2026-08-20
**Статус:** дизайн утверждён, реализация не начата
**Повод:** лимит носителей не покрывает TCP-путь TUN; всплески памяти сохраняются
и после снижения буферов носителя

## Проблема

`[tun] max_carrier_flows` задумывался как потолок на число одновременно живых
**носителей** — каждый туннельный флоу дозванивается своим. Фактически он
применяется только к UDP-пути (`crates/outline-tun/src/udp/lifecycle.rs:167`).
TCP-путь знает лишь общий `max_flows`
(`crates/outline-tun/src/tcp/engine/flow_ops.rs:195`), и туннельные TCP-флоу
тарифицируются наравне с direct.

Измерено на `.104` (cgroup-лимит 700 MiB): при `max_carrier_flows = 256`
одновременно наблюдались 256 туннельных UDP (упёрлись ровно в cap) **и до 318
туннельных TCP** — суммарно порядка 574 носителей. Скачки RSS +300…+426 MiB за
пять минут коррелируют именно с туннельными флоу (`tcp_tunn` R²=0.193,
`udp_tunn` R²=0.127), тогда как direct-флоу не коррелируют вовсе (0.012 и
0.003). После снижения буферов носителя (спека
`2026-08-20-carrier-buffer-reduction-design.md`, раскатано 2026-08-20) базовое
потребление упало, но всплески остались: на `.102` зафиксирован `MemoryPeak`
672 MiB при том, что метрики за то же окно показывали максимум 240 MiB —
всплеск целиком уместился между скрейпами.

## Решение

Сделать `max_carrier_flows` **общим** потолком на туннельные флоу обоих
протоколов, с LRU-эвикшном при упирании.

### 1. Общий счётчик слотов

Новый разделяемый ресурс по образцу `dial_admission`
(`crates/outline-tun/src/engine.rs:118-125` — там же и связывать):

```rust
pub(crate) struct CarrierSlots {
    used: AtomicUsize,
    cap: usize,   // 0 = выключено
}
```

Создаётся один раз в `TunEngine`, раздаётся обоим движкам через
`OnceLock<Arc<CarrierSlots>>` + сеттер (`set_carrier_slots`), ровно как
`set_dial_admission`. Не семафор: при упирании нужен эвикшн, а не ожидание.

Потолок считается как сейчас у UDP (`udp/engine.rs:116-122`): `0` → `max_flows`,
иначе `min(max_carrier_flows, max_flows)`.

### 2. Учёт слота на TCP-пути

Слот занимается в `insert_flow` (`tcp/engine/flow_ops.rs:190`), если исходный
маршрут — `TunRoute::Group`, и хранится в состоянии флоу как **RAII-гвард**
`CarrierSlot`, который возвращает слот в своём `Drop`.

**Правка дизайна по ходу реализации: гвард вместо флага.** Изначально
планировался `carrier_slot_held: bool` + освобождение в существующем
`impl Drop for TcpFlowState`. Это неверно: состояние флоу живёт за асинхронным
мьютексом, а эвикшн отдаёт жертву фоновому закрывателю — проверка «держу ли я
ещё слот» и само освобождение разъезжаются, и счётчик дрейфует. Гвард делает
освобождение следствием времени жизни флоу, а не тем, что какая-то ветка
teardown про него вспомнила. Дополнительный выигрыш: `UdpFlowState`, у которого
`Drop` вообще нет, получает ту же гарантию без его заведения.

**Временное превышение при эвикшне — осознанно.** Слот жертвы освобождается
только когда её состояние дропнется в фоновом закрывателе, поэтому сразу после
эвикшна обычный `try_acquire` отказал бы новичку, который уже оплатил своё
место. Для этого случая есть `acquire_evicted()` — занимает слот без проверки
потолка. Превышение ограничено числом флоу, ещё не догоревших в очереди
закрытия, и сходится по мере их завершения; без этого лимит залипал бы на всё
время сноса одной жертвы.

**Переучёт на флипе маршрута — обязателен.** При `route_by_sni` connect-таск
пере-резолвит маршрут уже после вставки флоу в таблицу и перезаписывает
`state.routing.route` (`tcp/engine/tasks/upstream/connect.rs:224`), в обе
стороны:

- `Group → Direct` — слот освободить, флаг снять;
- `Direct → Group` — слот занять (при упирании — эвикшн, как при вставке).

Без этого счётчик разъезжается с реальностью и лимит залипает в занятом
состоянии. `route_by_sni = true` стоит на боевых узлах, так что путь не
гипотетический.

### 3. Эвикшн

**Общий счётчик, но раздельные LRU.** Единый индекс на два протокола потребовал
бы общего типа ключа (`TcpFlowKey` против `UdpFlowKey`) и колбэка-диспетчера,
потому что само действие эвикшна протоколозависимо: TCP рвёт флоу RST'ом
(`abort_flow_with_rst`), UDP отправляет его в пул закрытия (`enqueue_close`).
Цена такой унификации выше выигрыша, поэтому каждый протокол вытесняет своих.

TCP нужен **отдельный индекс только туннельных флоу**: текущий `eviction_index`
(`tcp/engine/mod.rs:45`) содержит и direct, поэтому `pop_oldest` мог бы выбросить
direct-флоу и не освободить ни одного носителя. Добавляется
`carrier_eviction_index: FlowEvictionIndex` рядом; туда попадают только флоу с
занятым слотом, и он же обновляется на флипе маршрута.

Жертва — старейший по `last_seen`, то есть самое давно молчавшее соединение;
активная закачка не страдает. Причина закрытия — `"carrier_cap"` (отдельно от
существующего `"evicted"` по `max_flows`, иначе два разных лимита сольются в
одну метрику).

**Осознанный компромисс:** если своих туннельных флоу нет (например, UDP занял
все слоты, а приходит TCP-SYN), эвиктить некого — новый флоу получает отказ
(TCP: `bail!` как сейчас при `max_flows`; UDP: дроп датаграммы с warn, как
сейчас). Кросс-протокольное вытеснение не делаем.

### 4. Наблюдаемость

- Новый gauge `outline_ws_tun_carrier_flows_active` — занятые слоты (скаляр без
  лейблов: счётчик общий). Регистрация рядом с `outline_ws_tun_max_carrier_flows`
  (`crates/outline-metrics/src/registration/tun.rs:132-143`), сеттер рядом с
  `crates/outline-metrics/src/tun.rs:88`, заглушка в `stub.rs:254`.
- Событие эвикшна — новая метка `event="carrier_cap_evicted"` у существующих
  `record_tun_tcp_event` / `record_tun_udp_event`; новых регистраций не нужно.

Без этого срабатывание лимита останется невидимым — ровно та беда, из-за которой
всплески памяти до сих пор ловились только по `MemoryPeak`.

### 5. Документация и совместимость

Дефолт `max_carrier_flows = 0` (выключено, `bins/outline-ws-rust/src/config/load/tun.rs:30`)
не меняется, поэтому узлы без явной настройки не затронуты. Формулировка
«UDP-only» правится везде: `README.md:391-401`, `README.ru.md:389-399`, описание
метрики `outline_ws_tun_max_carrier_flows`
(`crates/outline-metrics/src/registration/tun.rs:136` — сейчас говорит «TUN UDP
flows»), плюс записи в CHANGELOG обоих языков.

**Операционный риск, требующий действия при раскатке.** На `.104` и `.102` стоит
`max_carrier_flows = 256`. Сейчас это потолок только для UDP, а по факту узлы
несли до ~574 носителей суммарно. После изменения 256 станет общим потолком —
это вдвое жёстче, и на всплесках пойдут обрывы туннельных флоу. Значение на
узлах нужно пересмотреть в том же окне, что и выкатку (для `.104` разумно
300–350: выше типичного p99, ниже пиков, которые убивали процесс). Это правка
боевого конфига и делается только с явного согласия владельца.

## Что НЕ делается

- **Кросс-протокольный эвикшн** — см. компромисс выше.
- **Учёт стоимости носителя по типу** (h3 дороже ws) — лимит считает штуки, а не
  байты. Разная цена носителей — отдельная задача, вместе с починкой
  `CARRIER_FLOW_MEMORY_ESTIMATE_BYTES` (`crates/outline-metrics/src/tun.rs:86`),
  который сейчас захардкожен и занижает в 7–20 раз.
- **Амплификация в `direct_reader`** (`Vec::with_capacity(16_384)` → `Bytes` без
  усечения) — отдельная задача.

Образцы уже есть в репозитории:

- `crates/outline-tun/src/udp/tests/eviction.rs:415` —
  `carrier_cap_binds_before_the_flow_table_limit` и парный тест про то, что
  direct-флоу в лимит не входят;
- `crates/outline-tun/src/tcp/engine/tests/mod.rs:1245` —
  `tun_tcp_flow_limit_uses_activity_eviction_index`;
- `crates/outline-tun/src/tcp/engine/tests/dial_admission.rs` — образец теста на
  ресурс, общий для двух движков.

Новые тесты (пишутся до реализации):

1. TCP: туннельные флоу упираются в `max_carrier_flows` раньше `max_flows`, и
   жертвой становится старейший **туннельный**, а не direct.
2. TCP: direct-флоу слот не занимают.
3. Общий счёт: слоты, занятые UDP, уменьшают доступное TCP (и наоборот).
4. Флип маршрута: `Group → Direct` освобождает слот, `Direct → Group` занимает;
   после серии флипов счётчик равен фактическому числу туннельных флоу.
5. `Drop`: снос флоу любым путём (close, RST, эвикшн) возвращает слот.

CI-гейт целиком и в порядке: `fmt` (явный список пакетов) → `clippy --workspace
--exclude sockudo-ws --all-targets --no-deps -D warnings` → `test --workspace
--exclude sockudo-ws`.

## Верификация на проде

Раскатка — отдельно, по явному согласию владельца, по одному узлу. Наблюдать:

- `outline_ws_tun_carrier_flows_active` против `outline_ws_tun_max_carrier_flows`
  — упирается ли лимит в реальности;
- `tun_tcp_events_total{event="carrier_cap_evicted"}` — темп обрывов; всплеск
  сразу после рестарта не считать регрессией, судить по установившемуся темпу;
- `MemoryPeak` юнита — главный критерий: всплески должны перестать доходить до
  cgroup-лимита;
- жалобы на обрывы: если темп эвикшнов заметный, значение cap поднимать.
