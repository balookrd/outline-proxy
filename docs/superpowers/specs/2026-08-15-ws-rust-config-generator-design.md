# Генератор клиентского конфига ws-rust для Android

Дата: 2026-08-15. Статус: дизайн утверждён, реализации нет.

## Задача

На узле уже есть генератор Xray-подписки (`ops/access-keys/xray_json.py`): он
читает `config.toml` узла и пишет `<user>.json` — конфиг для Happ и прочих
xray-клиентов. Нужен его аналог для **нашего** клиента: `<user>.toml`,
готовый конфиг `outline-ws-rust`, который забирает Android-приложение.

Конфиг должен включать фичи, которые узел реально несёт, и — явно —
failover между узлами, цепочку fallback-носителей внутри узла и миграцию
живых флоу между носителями.

## Что уже есть

- `ops/access-keys/` — генератор артефактов на Python, stdlib-only:
  `config_model.py` (разбор серверного `config.toml`), `uri.py` (построение
  `ss://` / `vless://` ссылок, байт-в-байт как в удалённом Rust-режиме),
  `xray_json.py` (рендер подписки), `generate_keys.py` (запись + отчёт),
  `golden/` (эталон 32 артефактов).
- Клиент `outline-ws-rust` умеет: `[[outline.uplinks]]` с цепочкой
  `[[outline.uplinks.fallbacks]]`, группы `[[uplink_group]]` с политикой
  балансировки, share-link'и (`link = "vless://…"` / `"ss://…"`) как форму
  задания wire'а, миграцию живого флоу между носителями
  (`[tun.tcp] carrier_migration`).
- Android-приложение (`android/app`): `ServerProfile.toToml()` собирает
  куцый конфиг из одной ссылки; поле `rawTomlOverride` подставляет готовый
  TOML вместо генерации.

## Решения

### Где живёт

Новый модуль `ops/access-keys/ws_toml.py` — **только рендер**, без I/O, как
`xray_json.py`. Запись файла и строки отчёта — в `generate_keys.py`.

Вход тот же, что у xray-генератора: `config_model.load(config.toml)` плюс
флаг `--node` (по умолчанию `cloud1.beerloga.su`, `cloud2.beerloga.su`).
Наследуется и допущение xray-генератора: у перечисленных узлов одинаковые
пути и креды юзера. Узел, на котором генератор запущен, диктует
серверные фичи (h3, padding, resumption, cluster) для всех узлов списка.

### Артефакт

Четвёртый файл на юзера — `<user>.toml`. Права `0640` (`root:www-data`),
атомарная запись через временный файл + `os.replace`, каталог из
`[access_keys] write_dir` — всё как у трёх существующих артефактов.

Условие выпуска: собралась хотя бы одна цепочка wire'ов (см. ниже).
Юзер без `vless_id` и без combined-SS-пути `<user>.toml` не получает.

Отчёт в stdout получает две новые строки на юзера:

```
written_toml: <путь>
ws_url:       https://…/<user>.toml
```

`<user>.txt` **не меняется**: он покрыт golden-корпусом, снятым с бинаря,
и переснять этот эталон больше нечем.

### Раскладка узлов и носителей

Один `[[outline.uplinks]]` на узел из `--node`:

```toml
[[outline.uplinks]]
name = "cloud1"
group = "main"
weight = 1.0
link = "vless://…"          # primary wire

  [[outline.uplinks.fallbacks]]
  link = "vless://…"        # и так далее по цепочке
```

Все wire'ы задаются share-link'ами через существующий `uri.py` — тем же
кодом, что строит `<user>.txt`, поэтому две формы не могут разъехаться.
Креды едут внутри ссылки, так что ни `method`/`password`, ни `vless_id`
на уровне аплинка не пишутся.

Порядок цепочки фиксирован:

| # | wire | зачем в этом месте |
|---|------|--------------------|
| 0 (primary) | `vless-xhttp` `stream-one` | лучший носитель: QUIC + full-duplex |
| 1 | `vless-ws` | другая carrier-семья, тот же прокси-протокол |
| 2 | `ss-ws` (combined) | другой прокси-протокол — переживает блокировку, специфичную для VLESS |
| 3 | `ss-xhttp` `stream-one` | то же, но по XHTTP |
| 4 | `vless-xhttp` `packet-up` | самый совместимый и самый дорогой — last resort |

Wire, для которого у юзера нет пути или креда, отсутствует; уцелевшие
сдвигаются вверх, и первый из них становится primary. SS-only юзер
получает цепочку из wire'ов 2–3, VLESS-only — из 0, 1, 4.

**ALPN не размножает wire'ы.** ws-rust сам даунгрейдит носитель внутри
wire'а (`ws_h3 → ws_h2 → ws_h1`, `xhttp_h3 → xhttp_h2 → xhttp_h1`), поэтому
на носитель приходится одна ссылка. Значение `alpn` берётся тем же
`uri.alpn_list`, что строит ссылки для `<user>.txt` (`h3,h2,http/1.1` при
поднятом `[server.h3]`, иначе `h2,http/1.1`; для `stream-one` — без
`http/1.1`): ws-rust читает **первый** токен как запрошенный режим, а
остальные и так описывают его встроенную цепочку даунгрейда. Ссылка
получается байт-в-байт той же, что в `.txt`, — сверять глазами и
диагностировать проще, чем две формы одного и того же. Это отличие от
xray-генератора, где ALPN — селектор и каждая его величина требует
отдельной ноги.

**Split-SS в цепочку не идёт.** `ss://` разворачивается только в
combined-путь (`ss_ws_url` / `ss_xhttp_url`); для раздельных
`ws_path_tcp` / `ws_path_udp` формы ссылки нет, а длинная форма означала бы
второй способ описывать wire в том же генераторе. Юзер без combined-путей
просто не получает SS-wire'ов.

### Группа и failover

```toml
[[uplink_group]]
name = "main"
mode = "active_passive"
routing_scope = "global"
shared_resume = <из [cluster] enabled сервера>
reselect_interval = "6h"
warm_standby_tcp = 1
warm_standby_udp = 1
tun_wire_dial = true
health_weighted_selection = true
```

`active_passive` + `global` — классический primary/backup: один узел несёт
весь трафик, поэтому выходной IP стабилен и source-IP-зависимая логика на
стороне сервисов не ломается. `auto_failback` **не выписывается**: уехав на
резервный узел после отказа, клиент там и живёт; обратно двигает только
плановый `reselect_interval`.

`tun_wire_dial = true` — единственный ключ здесь, без которого фича молча
не работает: по умолчанию он `false`, и тогда каждый TUN-дозвон уходит на
wire 0, а вся цепочка fallback'ов остаётся декорацией. Android — это ровно
TUN, поэтому ключ обязателен.

На аплинках выписывается `shuffle_wires = true` — анти-DPI реролл
неактивных wire'ов.

### Миграция носителей

Клиентская сторона миграции почти вся включена дефолтами бинаря:
`[tun.tcp] carrier_migration` = `true`, `tcp_symmetric_replay_enabled` =
`true`, ring mid-session retry — 256 KiB. Генератор выписывает
`carrier_migration = true` явно (конфиг должен читаться как декларация
намерения), но менять умолчания ему незачем.

Реально решает серверная сторона, и она читается из конфига узла:

- `[session_resumption] enabled` — без него сервер не минтит Session ID,
  клиентский `carrier_migration` инертен, и живой флоу на смерти носителя
  рвётся честным разрывом;
- `[session_resumption] downlink_buffer_bytes` — без него (или при `0`)
  реплеится только uplink-хвост, а downstream-байты, потерянные на мёртвом
  носителе, остаются дырой в ответе сервера. Для скачивания или SSE это
  разница между «мигрировал» и «мигрировал с повреждением»;
- `[cluster] enabled` — на кластерной группе `shared_resume = true`
  превращает переключение активного узла в мягкую миграцию живых сессий.
  Без кластера `active_passive` при смене активного аплинка **рвёт**
  привязанные сессии RST — это штатное поведение, гарантирующее egress-
  консистентность, но пользователь должен знать о нём заранее.

Каждый из трёх случаев даёт строку предупреждения в отчёте, а не тихо
изменённый конфиг.

### Padding

Клиентский `[padding]` — глобальный переключатель (per-uplink override
есть, per-wire — нет), и он не согласуется по проводу: сервер, не ждущий
падинга на этом пути, скормит падёные кадры своему обычному декодеру и
уронит сессию.

Поэтому `enabled = true` выписывается, только если **все** пути,
попавшие в цепочку, перечислены в серверном `[padding] paths`. Частичное
покрытие даёт `enabled = false` плюс строку в отчёт с перечислением
непокрытых путей — чинится это на сервере, а не подгонкой клиента.

### Профиль хоста (Android)

```toml
[tun]
path = "vpn"
mtu = 1500

[tun.tcp]
sniffing = true
carrier_migration = true
```

`path` непустой нужен, чтобы загрузчик активировал TUN (сам дескриптор
приходит из `VpnService` через `RunOptions.tun_fd`). `mtu` обязан совпадать
с `VpnService.Builder.setMtu` — на Kotlin-стороне это константа
`ServerProfile.TUN_MTU`. `sniffing` нужен для TLS/QUIC-случаев (домен
должен доехать до выходного узла, а не резолвиться локально).

`[socks5]`, `[metrics]`, `[control]`, `[dashboard]` не выписываются: в
Android-сборке этих фич нет, а `deny_unknown_fields` превращает лишнюю
секцию в отказ бинаря на старте.

### Доставка в приложение

Правок Kotlin не требуется: содержимое `<user>.toml` кладётся в
`rawTomlOverride` профиля. `ws_url` в отчёте — чтобы файл можно было
передать ссылкой, а не текстом.

## Реализация

Модули:

- `ws_toml.py` — `build_config(user, nodes, features) -> str`. Внутри:
  сборка цепочки wire'ов, сборка группы, минимальный TOML-writer
  (basic-strings с экранированием `"` и `\`, фиксированный порядок секций).
  `tomllib` умеет только читать, зависимостей извне не берём.
- `config_model.py` — `ServerConfig` расширяется тремя полями: `padding`
  (enabled + paths), `session_resumption` (enabled + downlink_buffer_bytes),
  `cluster_enabled`. Разбор — такой же осторожный, как `_h3_in_alpn`:
  зеркалит серверные умолчания, а не угадывает их.
- `generate_keys.py` — запись четвёртого артефакта и две строки отчёта.

## Проверка

Два уровня, потому что байтовая сверка не доказывает загружаемость:

1. **Python, `test_ws_toml.py`** (unittest, stdlib-only, без сети) — рендер
   для юзеров синтетического `golden/config.toml` сверяется с фикстурой.
   Отдельно проверяются: усечение цепочки для SS-only и VLESS-only,
   `alpn=h2` без `[server.h3]`, отказ от padding при частичном покрытии,
   `shared_resume` от `[cluster]`.
2. **Rust, `bins/outline-ws-rust/src/config/tests/`** — фикстура кладётся в
   дерево и грузится штатным `load_config`. У схемы `deny_unknown_fields`:
   один ключ, разошедшийся со схемой, роняет бинарь на старте — как в своё
   время `[dashboard]` на парке. Этот тест ловит дрейф в CI, а не на
   телефоне.

Фикстура — не golden в прежнем смысле («снято с бинаря»): источника истины
вне этого генератора у неё нет. Она фиксирует принятый формат и меняется
осознанно, вместе с изменением формата.

## Что осталось за рамками

- Автоматическое обновление конфига в приложении по URL (режим подписки на
  Kotlin-стороне) — сейчас файл вставляется вручную.
- Split-SS (`ws_path_tcp` / `ws_path_udp`) как wire.
- Профиль `desktop` (с `[socks5]` и `[metrics]`) — генератор выпускает
  только Android-профиль.
- Loss-driven failover (`loss_failover_ratio`) — на шумной мобильной сети
  он двигал бы трафик между узлами без просьбы оператора.
