# Подписка на конфиг по URL (дизайн)

Дата: 2026-08-15
Статус: согласовано в чате

## Контекст

Профиль сервера в Android-клиенте задаётся вручную: структурированные поля
(vless/ss share-link) или `rawTomlOverride` как escape-hatch
([ServerProfile.kt](../../../android/app/src/main/java/com/outline/proxy/ServerProfile.kt)).
`toToml()` собирает из полей клиентский TOML, а при непустом override отдаёт его
дословно.

Владелец генерирует персональные конфиги на сервере и раздаёт по секретному URL,
пример: `https://cloud.beerloga.su/<token>/alice.toml`. Тело — **готовый
клиентский TOML целиком** (`[tun]`, `[tun.tcp]`, `[padding]`, `[[uplink_group]]`,
`[[outline.uplinks]]` с fallback'ами), а не xray-JSON-подписка как у Happ. То
есть один URL = один законченный конфиг с несколькими uplink'ами внутри, а не
список серверов.

Задача — как в Happ: указать URL в интерфейсе, клиент скачивает конфиг и
периодически обновляет его в фоне.

## Цель

Профиль может брать свой TOML не из ручных полей, а из HTTPS-URL: скачивать при
добавлении, обновлять по расписанию в фоне и переживать недоступность источника
за счёт кэша.

## Не-цели

- **Парсинг подписки в список серверов.** Тело — цельный конфиг, не список
  outbound'ов; разбирать его в структурированные поля не нужно и не будем.
- **Загрузка через туннель.** Запрос идёт напрямую (наш пакет исключён из VPN),
  как в Happ. Случай «источник доступен только через туннель» — известное
  ограничение, кэш его смягчает, чинить в этой итерации не будем.
- **Настраиваемый интервал обновления.** Фиксированные 12 часов; выносить в UI —
  по запросу позже (YAGNI).

## Архитектура

### Модель: режим профиля «источник = URL»

`ServerProfile` получает три поля:

| Поле | Смысл |
|---|---|
| `configUrl: String` | HTTPS-URL подписки. Пусто → профиль работает по-старому |
| `cachedToml: String` | Последний успешно скачанный и провалидированный TOML |
| `updatedAt: Long` | Время последнего успешного обновления (epoch ms), 0 = никогда |

`toToml()` при непустом `configUrl` возвращает `cachedToml`. Приоритет:
`configUrl` → `cachedToml`; иначе прежняя логика (`rawTomlOverride` → поля).
Список профилей, выбор, connect и keep-alive не меняются — подписка для них
просто ещё один профиль.

Кэш (~2.5 КБ) живёт в самом профиле в SharedPreferences рядом с остальными
полями — отдельный файл ради пары килобайт не нужен.

### ConfigFetcher

Отдельный объект, скачивание на `Dispatchers.IO` голым `HttpURLConnection` (без
новых сетевых зависимостей):

- **только HTTPS.** Тело несёт UUID и пароли серверов; `http://` отклоняется до
  соединения.
- **Валидация ответа.** Принимается, только если тело непустое и похоже на наш
  конфиг — содержит `[tun]` или `[[outline.uplinks]]`. Иначе результат — ошибка,
  кэш **не** трогается. Это страховка от URL, который вернул HTML-заглушку,
  капчу или страницу 404 вместо TOML: подменить рабочий кэш мусором нельзя.
- Таймауты (connect/read), лимит тела 200 КБ, редиректы только https→https.
- Результат — sealed `FetchResult { Success(toml) | Failure(reason) }`, без
  бросков наружу.

Разбор «валиден ли текст как конфиг» выносится в чистую
`ConfigValidation.looksLikeConfig(text): Boolean` — тестируется на JVM без сети.

### Обновление

| Момент | Поведение |
|---|---|
| Добавление/правка URL в форме | Синхронно с индикатором. Профиль-подписку нельзя сохранить рабочей без первого успешного скачивания |
| Расписание в фоне | `SubscriptionWorker` (WorkManager), период 12 ч. Обновляет кэш всех профилей с `configUrl`. Ошибка сети — прежний кэш остаётся, активный туннель не трогается |
| Ручная кнопка в списке | Немедленное обновление одного профиля |
| Connect при пустом кэше | Страховка: если `cachedToml` пуст, попытка скачать перед подъёмом |

`SubscriptionWorker` регистрируется при сохранении первого профиля-подписки и
снимается, когда таких профилей не осталось.

### UI

- **Форма профиля:** поле «Config URL (subscription)». Заполнено → поля vless/ss
  скрываются (источник конфига один). Сохранение с непустым URL запускает
  скачивание и показывает прогресс/ошибку; при ошибке и пустом кэше профиль не
  сохраняется как рабочий.
- **Список:** у профиля-подписки строка «обновлено N ч назад» (или «не
  обновлялось») и кнопка ручного обновления. Ошибка последнего обновления видна,
  но использованию кэша не мешает.

## Безопасность

- **URL — секрет.** Токен в пути (`/<token>/alice.toml`) — тот же access-key
  секрет, что в репозитории под запретом логирования. Хранится в приватных
  SharedPreferences; в логах маскируется (хост + последние символы), целиком URL
  не пишется никуда.
- **HTTPS обязателен** — иначе UUID/пароли ушли бы открытым текстом.
- **Кэш содержит те же секреты** — лежит в приватном хранилище приложения, как и
  ручные профили сегодня.

## Обработка ошибок

| Ситуация | Реакция |
|---|---|
| `http://` URL | Отклонить в форме, до сети |
| Сеть недоступна / таймаут | `Failure`; в форме — ошибка, в фоне — тихо, кэш цел |
| Тело не похоже на конфиг | `Failure`, кэш не перезаписан |
| Тело > 200 КБ | Обрыв чтения, `Failure` |
| Пустой кэш и первое скачивание не удалось | Профиль не рабочий, connect предупреждает |

## Тестирование

**JVM-юниты** (`testDebugUnitTest`):
- `ConfigValidation.looksLikeConfig` — да/нет на примерах TOML, HTML, пустого;
- `ServerProfile.toToml()` — при `configUrl` отдаёт `cachedToml`, приоритет над
  override и полями; JSON round-trip новых полей.

**На устройстве** (HONOR PNM-N49, отладка по USB): URL живой, поэтому проверяется
реальное скачивание `alice.toml`, подключение по нему, и что кнопка обновления
перечитывает конфиг. Загрузку по HTTP и «мусорный ответ» проверить синтетически
(правкой URL).

## Пересечение с keep-alive

Обе фичи добавляют `androidx.work`. Подписку делаем первой — зависимость заведёт
она; в плане keep-alive соответствующий шаг станет no-op. `SubscriptionWorker` и
`WatchdogWorker` — независимые periodic work с разными тегами и периодами.

## Зависимости

`androidx.work:work-runtime-ktx` — новая (если ещё не добавлена keep-alive'ом).
Сетевых библиотек не добавляем: `HttpURLConnection` из платформы.
