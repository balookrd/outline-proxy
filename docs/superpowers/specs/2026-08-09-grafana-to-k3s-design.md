# Миграция Grafana с `.102` в k3s

Дата: 2026-08-09. Область: `ops/nanopi-r5c-k3s/apps/monitoring/`, `ops/grafana/`,
узлы `198.18.1.102` и k3s-ноды.

## Что есть сейчас

Grafana OSS 13.0.2 в docker на `198.18.1.102` (`/opt/grafana/grafana.sh`,
`4000 → 3000`, `--user 1000:1000`, `--restart=unless-stopped`). Состояние —
`/opt/grafana/data`, 107 МБ:

| Часть | Размер | Судьба при переезде |
|---|---|---|
| `plugins/` | 92 МБ | **не едет** (см. ниже) |
| `grafana.db` | 15 МБ | едет после чистки |
| `dashboards/` | 576 КБ | не едет — приходит из git через ConfigMap |
| `unified-search/` | 252 КБ | не едет, индекс перестроится |

Grafana 13 держит дашборды в **unified storage** (таблицы `resource` /
`resource_history` внутри той же SQLite), а не в легаси-таблицах
`dashboard`/`dashboard_provisioning` — последние пусты, и это норма, а не
поломка провижининга.

Живых дашбордов десять. Пять приходят провижинингом из
`ops/grafana/dashboards/`; **семь существуют только в БД** и в git их нет:
`Power`, `Temperature`, `Node Exporter Full`, `Tunnels`, `Outline`,
`VictoriaMetrics`, `Xray Dashboard`. Экспорт их в git — отдельная задача.

Внешние завязки: единственный датасорс `http://198.18.1.102:8428`
(VictoriaMetrics, заведён через UI и живёт только в БД), SMTP через Gmail,
Telegram-бот и heartbeat dead-man в provisioning алертинга, семь alert-правил.

## Решение

Переносим **только Grafana**. VictoriaMetrics остаётся на `.102` — у неё 90 дней
истории и своя IOPS-нагрузка, её переезд был бы отдельной работой с переводом
всех scrape-целей парка. Датасорс продолжает смотреть на `198.18.1.102:8428`.

Переключение одномоментное: гасим контейнер на `.102`, поднимаем под в кубере.
Окно недоступности — минуты. Параллельная работа отвергнута: два инстанса шлют
дублирующиеся алерты и два heartbeat'а, а dead-man от этого начинает врать.
`/opt/grafana` не удаляем — это путь отката.

### Что именно едет

Только `grafana.db`, и то после чистки. Плагины (92 МБ) не переносятся:
`elasticsearch` (39 МБ) дублирует core-плагин — Grafana сама пишет в лог
`Skipping loading of plugin as it's a duplicate`; `grafana-lokiexplore-app`,
`grafana-exploretraces-app`, `grafana-metricsdrilldown-app`,
`grafana-pyroscope-app` — штатные app-плагины 13.x, ставятся сами;
`marcusolsson-dynamictext-panel` **отключается** — проверено, что он не
используется ни в одном дашборде (ни в git, ни в БД).

### Чистка БД

Перед копированием, на остановленной Grafana:

1. удалить из `resource_history` все строки семи мёртвых UID
   (`outline-ws-uplinks`, `outline-ws-rust-tun-tcp`, `outline-ws-rust-native-burst`,
   `outline-ws-rust-ws-tcp-live`, `outline-ws-rust-ws-h2-tcp-live`,
   `begqoward2epsf`, `eecdqgyv3buv4c`);
2. у живых дашбордов оставить только текущую версию;
3. `VACUUM`.

Сейчас история — 176 строк по дашбордам, до 20 версий на каждый при JSON до
252 КБ; отсюда и 15 МБ. После чистки ожидаются единицы мегабайт. Откат версий
через UI после этого недоступен — сознательный размен, о котором знает владелец.

## Компоненты в кластере

### Хранилище

PVC `grafana-data`, StorageClass `local-path` (единственный, он же default), 2 Gi.
Данные лягут на NVMe: на нодах `/var/lib/rancher` — это отдельный диск 119 ГБ.

`nodeSelector` из текущего манифеста **убирается**: local-path создаёт PV с
node-affinity, поэтому под и так приколачивается к ноде с данными, а лишний
селектор только мешает, если PVC уедет на другую ноду.

`strategy: Recreate`, одна реплика — SQLite не терпит второго писателя.

### Провижининг

| Что | Объект | Монтируется в |
|---|---|---|
| Датасорс VictoriaMetrics | ConfigMap `grafana-datasources` | `/etc/grafana/provisioning/datasources` |
| Провайдер дашбордов | ConfigMap `grafana-dashboard-provider` | `/etc/grafana/provisioning/dashboards` |
| Сами дашборды, по одному на файл | ConfigMap `grafana-dashboard-<имя>` | `/etc/grafana/dashboards` |
| Алертинг (rules, policies, contact-points) | **Secret** `grafana-alerting` | `/etc/grafana/provisioning/alerting` |

Датасорс сейчас нигде в git не описан — заводим его файлом, чтобы кластерная
Grafana не зависела от содержимого перенесённой БД.

Дашборды монтируются в `/etc/grafana/dashboards`, а не в
`/var/lib/grafana/dashboards`, как на `.102`: последний путь внутри PVC, и
ConfigMap туда не положить. Соответственно `options.path` в провайдере другой —
единственное расхождение с хостовой конфигурацией.

Один ConfigMap на дашборд, а не общий: лимит объекта — 1 МиБ, а `outline-ws-rust`
весит 252 КБ, `outline-ss-rust` — 180 КБ.

Алертинг уезжает в Secret, потому что `contact-points.yaml` несёт
telegram-токен и heartbeat-токен. Подстановку `__HEARTBEAT_TOKEN__`,
`__TELEGRAM_BOT_TOKEN__`, `__TELEGRAM_CHAT_ID__` из host-local файлов делает
скрипт раскатки — так же, как сейчас для `.102`.

### Доставка дашбордов из git

ConfigMap'ы генерируются из `ops/grafana/dashboards/*.json` скриптом, а не
коммитятся: иначе те же 570 КБ JSON лежали бы в репозитории дважды и неизбежно
разошлись бы. Существующий `ops/grafana/dashboards/deploy.sh` (сейчас копирует
файлы на `.102`) получает второй режим — `--k3s`, который на каждый файл делает
`kubectl create configmap ... --from-file=... --dry-run=client -o yaml |
kubectl apply -f -`.

Grafana Git Sync (`provisioning.grafana.app`, механизм в 13.x уже
инициализируется) рассматривался и отвергнут: фича свежая, а репозиторий
локальный — доступа из кластера к нему нет.

### Секреты

`grafana-smtp` (пароль Gmail, монтируется файлом — как сейчас через
`GF_SMTP_PASSWORD__FILE`) и `grafana-alerting` (см. выше). Оба создаются вне git.

Secret с паролем администратора **не нужен**: на `.102`
`GF_SECURITY_ADMIN_PASSWORD` не задан, пароль живёт в БД и переезжает вместе с
ней. Задавать env в кубере значило бы молча переустановить пароль при каждом
старте пода. Соответственно `grafana-admin.secret.example.yaml` из репозитория
удаляется — он описывает механизм, который мы сознательно не используем.

### Образ и окружение

`grafana/grafana-oss:13.0.2` — версия пинуется. Сейчас на `.102` тянется
`latest`, то есть очередной `docker pull` может привезти новый мажор; в кластере
это означало бы миграцию схемы БД при случайном рестарте пода.

Env: `TZ=Europe/Moscow`, `GF_DATABASE_WAL=true`, `GF_SMTP_*` как на хосте.
`GF_PLUGINS_PREINSTALL` **не задаётся**.

`securityContext`: `runAsUser: 472`, `fsGroup: 472` — штатный uid образа. Файлы
БД на `.102` принадлежат uid 1000, поэтому при заливке в PVC делается
`chown 472:472`.

### Способ заливки данных

PVC создаётся, поднимается временный под с `busybox` и примонтированным PVC,
архив с почищенной БД заходит через `kubectl cp`, распаковывается, выставляется
владелец, под удаляется. Так мы не зависим от внутреннего устройства
local-path и его путей на ноде.

## Хвосты за пределами пода

**Scrape-job `grafana`** в VictoriaMetrics на `.102` смотрит на
`127.0.0.1:4000` и после переезда будет собирать пустоту. Перенацеливается на
`https://grafana.k3s.beerloga.su/metrics` — сертификат валидный, `/metrics`
отдаётся без авторизации. Требует проверки, что имя резолвится с самой `.102`.
Конфиг VM перечитывается без рестарта: `curl -X POST http://127.0.0.1:8428/-/reload`.

**Ingress уже готов** с прошлой работы: `grafana.k3s.beerloga.su` →
`service grafana:3000` в ns `monitoring`, TLS от общего wildcard. Ничего менять
не нужно — HTTPS заработает сразу после старта пода.

**Бэкап.** CronJob раз в сутки: `sqlite3 .backup` (безопасная копия работающей
БД) → tar.gz на NAS `198.18.1.125:/mnt/HD/HD_a2/k8s`, ротация 7 копий. Требует
`nfs-common` на трёх нодах — сейчас NFS-клиента там нет. Ставим: он всё равно
понадобится для nfs-provisioner под будущие приложения.

Бэкап здесь не формальность: семь ручных дашбордов существуют только в этой БД.

## Порядок раскатки

1. Секреты и ConfigMap'ы в кластер, дашборды через новый режим `deploy.sh`.
2. Остановить Grafana на `.102`, снять `--restart=unless-stopped`.
3. Почистить БД (бэкап до чистки), убедиться в размере.
4. Создать PVC, залить БД через временный под.
5. Применить Deployment, дождаться готовности.
6. Проверить: HTTPS, вход под прежним паролем, датасорс, все 10 дашбордов,
   7 alert-правил, отсутствие лишних плагинов.
7. Перенацелить scrape-job VM, перечитать конфиг.
8. `nfs-common` на ноды, CronJob бэкапа, проверить первую копию на NAS.

## Что НЕ входит

- Переезд VictoriaMetrics.
- Экспорт семи ручных дашбордов в git.
- nfs-provisioner и StorageClass `nfs-client` (ставим только `nfs-common`).
- Удаление `/opt/grafana` на `.102` — остаётся как откат.
- Раскатка остальных приложений (`home`, `outline`, `vpn`).

## Риски

- **local-path привязывает под к ноде.** Потеря ноды = restore из бэкапа на NAS.
  Для домашнего кластера приемлемо; альтернатива (SQLite поверх NFS) опаснее.
- **UID датасорса.** Дашборды ссылаются на датасорс по UID, а не по имени.
  Провижининг обязан создать его ровно как `adnsc1wi03doga` (name `prometheus`,
  `isDefault`), иначе перенесённые панели окажутся без данных, и выглядеть это
  будет как «дашборды сломались при переезде».
- **Чистка истории необратима.** Бэкап `grafana.db` снимается до неё.
- **Провижининг с `allowUiUpdates: false`** делает пять дашбордов read-only —
  как и сейчас на `.102`, но в кластере это заметят впервые.
- **Окно без мониторинга** на время переключения: алерты в это время не
  вычисляются, dead-man на cloud1/cloud2 может успеть сработать, если окно
  затянется.
