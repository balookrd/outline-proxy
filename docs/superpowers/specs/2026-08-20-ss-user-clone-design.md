# Кнопка «Дублировать УЗ» в ss-панели `outline-ui` (дизайн)

Дата: 2026-08-20
Статус: согласовано в чате, ждёт вычитки владельцем

## Контекст

`outline-ui` — агрегирующий web-UI парка (`bins/outline-ui/`): отдаёт два
дашборда (`/ss`, `/ws`) и лендинг, сам data plane не несёт — только проксирует
к control API каждого узла, подставляя bearer-токен на своей стороне
(см. [`2026-08-12-outline-ui-svelte-rewrite-design.md`](2026-08-12-outline-ui-svelte-rewrite-design.md)).

ss-панель (сервер `outline-ss-rust`) несёт вкладку **Users** — CRUD
Shadowsocks-ключей выбранного узла:

- фронт: `features/ss/Users.svelte` (владеет вызовами API, тостами, поллингом),
  `features/ss/UsersTable.svelte` (таблица + строчные действия edit/block/delete),
  `features/ss/UserDrawer.svelte` (форма create/edit);
- форм-логика вынесена в framework-free `lib/userForm.ts` (unit-тестируемая
  сборка payload; тесты в `lib/userForm.test.ts`);
- API-слой: `lib/api.ts` (`listUsers`/`createUser`/`updateUser`/…), эндпоинт
  узла — `/ss/dashboard/api/users` → control API `/control/users` (GET/POST) и
  `/control/users/{id}` (GET/PATCH/DELETE).

Модель пользователя (`lib/types.ts::User`) несёт `id`, `enabled`, `method`,
`fwmark`, `ws_path_{tcp,udp,ss,vless}`, `xhttp_path_{tcp,udp,ss,vless}`,
`aliases` и **флаги** `has_password`/`has_vless_id`. Секреты (`password`,
`vless_id`) сервер наружу **не отдаёт** — только факт их наличия
(`UserView` в `server/control/manager.rs`).

## Проблема

Чтобы завести нового пользователя, похожего на существующего (тот же носитель:
метод + WS/XHTTP-пути), админ в форме создания вручную:

- придумывает `password` и/или `vless_id` — а это криптосекреты, которые
  нельзя брать «из головы»;
- заново проставляет все пути и метод, повторяя их с шаблонного пользователя.

Хочется: на строке конкретного пользователя нажать одну кнопку и получить почти
готовую форму нового — с уже сгенерированными секретами и скопированным
носителем, дописав только имя (`id`).

## Технические факты, определяющие дизайн

Изучение серверной стороны (`bins/outline-ss-rust`) выявило ограничения,
которые задают форму решения:

1. **Пути нельзя генерировать произвольно.** `manager.rs::validate_new`
   принимает `ws_path_*`/`xhttp_path_*`, только если они **предрегистрированы
   при старте** (`allowed_tcp_paths`, `allowed_udp_paths`, `allowed_vless_paths`,
   `allowed_xhttp_*`). Неизвестный путь → `400 "… was not registered at
   startup; restart the server …"`. Значит пути — это выбор из фиксированного
   пула носителей, а не per-user секрет: при клонировании их надо **копировать
   как есть**.

2. **Единственное уникальное-и-секретное на пользователя — `password`,
   `vless_id` и `id`.** `access_url` не заполняет никто (ни `UserView` в
   ss-rust, ни агрегатор `bins/outline-ui/src/backend.rs`) — в таблице всегда
   «—». То есть показать готовую ss:// / vless:// ссылку после клонирования
   неоткуда; практический результат клонирования — **сами сгенерированные
   секреты**, которые надо показать админу в форме.

3. **Генерация `password` зависит от метода** (`crypto/user_key.rs`):
   - `2022-blake3-*` — пароль есть base64 от master-key фиксированной длины
     (`cipher.rs::key_len`): 16 байт для `aes-128-gcm`, 32 для `aes-256-gcm`
     и `chacha20-poly1305`;
   - остальные (`aes-*-gcm`, `chacha20-ietf-poly1305`) — произвольная непустая
     строка (EVP-деривация master-key из неё).

   Сервер **мультиметодный**: каждый пользователь несёт свой метод
   (`user_entry.rs::effective_method`), сервер обрабатывает его по **его**
   методу. Поэтому клон с **явно заданным** методом работает независимо от
   серверного дефолта — генерацию можно делать **на клиенте**, привязав формат
   пароля к методу из формы. Правки data-plane бинаря и деплоя на парк **не
   требуется**.

4. **`aliases` копировать нельзя.** `user_entry.rs::validate_ip_aliases`
   требует глобальной уникальности **имён алиасов** (пространство имён = все
   `user.id` + все имена алиасов). Клон с теми же именами → `400 "alias …
   collides with another user id or alias"`. По смыслу алиасы — это привязка
   учёта к конкретным source-IP клиентов шаблона; у нового пользователя свои
   клиенты. Решение владельца: **не копировать**.

5. **`method = default`.** Если у шаблона `method` не задан (`None`), UI не
   знает эффективный серверный шифр (control API его не отдаёт; серверный
   дефолт в коде — `chacha20-ietf-poly1305`, но админ мог переопределить
   `[shadowsocks] method`). Генерировать пароль вслепую нельзя. Решение
   владельца: **попросить выбрать конкретный метод** — пароль генерируется,
   как только метод выбран.

## Цель

Добавить в ss-панель действие **«Дублировать»** на строке пользователя: клик
открывает штатную форму создания (`UserDrawer` в create-режиме),
предзаполненную из шаблонного пользователя, с уже сгенерированными и видимыми
секретами и пустым `id` в фокусе. Только фронтенд (`bins/outline-ui/frontend`);
control API, ss-rust-бинарь и деплой на парк — не трогаем.

## Дизайн

### 1. UX-поток

- В `UsersTable.svelte`, в сниппете `rowActions` (сейчас: edit / block /
  delete), добавляется **четвёртая** иконка-кнопка «Clone» (иконка дублирования
  — две наложенные карточки), tooltip/`aria-label` вида «Clone {id}».
- Клик → `Users.svelte::openCloneDrawer(user)`: снимок шаблонного пользователя
  (как и `editingUser`, снапшот на момент клика — фоновый поллинг не должен
  перетирать форму), затем `drawerOpen = true` в **режиме клонирования**.
- Открывается тот же `UserDrawer`, но в create-режиме (не edit): заголовок
  «Clone user», кнопка «Create», поля предзаполнены (см. §2), `id` пустой и в
  фокусе. Админ вписывает `id` → «Create» → существующий путь
  `createUser` → рефетч списка.

### 2. Матрица переноса

| Поле | Поведение при клонировании |
|---|---|
| `method`, `fwmark` | копируется как есть |
| `ws_path_{tcp,udp,ss,vless}` | копируется как есть |
| `xhttp_path_{tcp,udp,ss,vless}` | копируется как есть |
| `enabled` | копируется как есть |
| `password` | **генерируется новый**, если `has_password` (см. §3) |
| `vless_id` | **генерируется новый** `crypto.randomUUID()`, если `has_vless_id` |
| `id` | пустой, вводит админ |
| `aliases` | **не копируется** (пусто) |

Набор идентичностей клона повторяет шаблон: SS-only юзер → у клона только
`password`; VLESS-only → только `vless_id`; оба → оба.

### 3. Генерация секретов (на клиенте)

Источник энтропии — WebCrypto (`crypto.getRandomValues` / `crypto.randomUUID`).
`password` генерируется по **текущему** значению поля `method` в форме и
перегенерируется при его смене:

| method формы | формат пароля |
|---|---|
| `2022-blake3-aes-128-gcm` | base64(16 случайных байт) |
| `2022-blake3-aes-256-gcm` | base64(32 случайных байт) |
| `2022-blake3-chacha20-poly1305` | base64(32 случайных байт) |
| `aes-128-gcm` / `aes-256-gcm` / `chacha20-ietf-poly1305` | случайная строка (base64url ~24 байт) |
| `default` (пусто) | **не генерируется**; подсказка «выберите метод» |

- Рядом с полями `password`/`vless_id` — кнопка **↻ «перегенерировать»** и
  toggle **«показать»** (в клон-режиме значения показываются открыто: их надо
  скопировать и передать клиенту).
- `default`: поле пароля пустое, под ним подсказка «Choose a method to generate
  a password». Как только выбран конкретный метод — пароль генерируется. `id`
  всё равно обязателен, `password || vless_id` — тоже (штатная валидация
  `validateUserForm`).

### 4. Модель компонентов

Логика — в framework-free `lib/userForm.ts` (чисто, unit-тестируемо):

- `generatePassword(method, rng): string | null` — по таблице §3; `null` для
  `default`. `rng` инъектируется (по умолчанию WebCrypto) ради детерминизма в
  тестах.
- `generateVlessId(rng): string` — UUID v4.
- `cloneUserFields(template, rng): UserFormFields` — строит поля формы:
  копирует носитель (§2), кладёт сгенерированные секреты (по `has_password`/
  `has_vless_id`), `id = ''`, `aliases = ''`, `enabled = template.enabled`.

`UserDrawer.svelte` получает третий вход помимо create/edit — **seed для
create**: опциональный проп начальных полей (напр. `seedFields?:
UserFormFields`). При `open` логика становится: `editingUser`
→ `fieldsFromUser`; иначе `seedFields ?? emptyUserFields()`. Плюс флаг
клон-режима для заголовка «Clone user» и открытого показа секретов. Контракт
create/edit не ломается (seed отсутствует → прежнее поведение).

`Users.svelte` добавляет `openCloneDrawer(user)` (снапшот + сборка seed через
`cloneUserFields`) и прокидывает snippet-кнопку «Clone» в `UsersTable`.
`buildUserPayload(fields, editing=false)` уже корректно собирает create-payload
(пустые пути опускаются, `aliases` пусто → опущены) — переиспользуется без
изменений.

### 5. Тесты

`lib/userForm.test.ts` дополняется:

- `generatePassword`: длина/формат base64 для каждого 2022-метода (16/32 →
  корректная base64-длина), непустая строка для не-2022, `null` для `default`;
- `generateVlessId`: валидный UUID v4;
- `cloneUserFields`: копирует носитель, генерит секреты **только** под
  имеющиеся у шаблона идентичности, `id`/`aliases` пусты, `enabled` унаследован;
- `buildUserPayload` поверх результата клонирования даёт валидный create-payload
  (пути присутствуют, секреты присутствуют, `aliases`/пустые поля опущены).

## Крайние случаи

- **Дубль `id`.** Сервер отклонит (`"user id … already exists"`) — штатный
  тост ошибки, форма остаётся открытой.
- **Только `vless_id` у шаблона.** Пароль не генерируется; `default`-подсказка
  про метод не показывается (метод для SS, а SS-идентичности нет). VLESS
  требует хотя бы один `*_path_vless` — он копируется из шаблона, значит клон
  валиден.
- **Заблокированный шаблон** (`enabled=false`). Клон наследует `enabled=false`
  (буквальное «копировать всё»); при желании админ включает тумблер до
  создания.

## Вне scope (YAGNI)

- Серверная генерация секретов и отдельный эндпоинт `clone` на control API.
- Копирование `aliases` (с переименованием или без).
- Автоподстановка `id` (суффикс `-2`/`-3`).
- Показ `access_url` / QR / share-link после создания — `access_url` в этом
  контуре не заполняется вовсе.
- Локализация подписей: дашборд англоязычный («Add user», «Edit user») —
  новые подписи тоже английские («Clone», «Clone user»).
