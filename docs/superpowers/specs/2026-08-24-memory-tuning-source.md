# Источник истины для memory-тюнинга парка

**Дата:** 2026-08-24
**Статус:** дизайн на ревью
**Повод:** cgroup-лимиты и memory-env раскатаны ручным рецептом, живут только на
узлах, теряются при переустановке ОС и несут мёртвые под jemalloc переменные

## Проблема

Memory-drop-in'ы (`/etc/systemd/system/outline-*.service.d/`) на всех семи узлах
поставлены вручную (рецепт `vps-memory-tuning-fleet`, 2026-07-20 и правки
2026-08-09). В репозитории их нет — ни в `ops/provision-node`, ни в бандлах.
Следствия:

1. **Теряются при переустановке ОС** (как было на sebek Debian→Ubuntu) и при
   провижининге нового узла — `install.sh` их не раскатывает.
2. **Разнородны.** На `.104` лимиты в `20-memory.conf`, а env в
   `30-mem-tuning.conf`; на cloud всё в одном файле. У `.104 ss` env нет вовсе,
   у `cloud1 ss` есть `MIMALLOC_PURGE_DELAY`. Никакого единого шаблона.
3. **Несут мёртвый груз.** `MIMALLOC_PURGE_DELAY=0` и
   `MIMALLOC_ARENA_RESERVE=16384` бессмысленны после перехода на jemalloc, а
   второй не действовал и под mimalloc — арена снизу ограничена 32 MiB, и
   16 MiB поднимались до неё. jemalloc настраивается через `malloc_conf`,
   вшитый в бинарь, а не через env.
4. **Только жёсткие лимиты у ws.** До 2026-08-24 `High=Max` у ws на всех узлах
   (аварийная конфигурация под carrier-per-flow) — нет мягкой ступени reclaim.

## Решение

Новый каталог `ops/memory-tuning/` — единственный источник истины, из которого
лимиты и memory-env раскатываются одной командой и переживают reprovision через
явное повторное применение.

### Структура

```
ops/memory-tuning/
  fleet.tsv          # декларативная таблица: узел → лимиты обоих сервисов
  apply.sh           # раскатчик: читает таблицу, ставит drop-in на узел
  README.md          # EN
  README.ru.md       # RU
```

### `fleet.tsv`

Одна строка на узел, разделитель — таб. Два ключа на одну строку: `short`
матчит `--host` в `install.sh` при провижининге, `ssh_target` — `apply.sh` при
пересинхронизации живого парка. Дефис (`-`) означает «сервиса на узле нет,
drop-in не ставить».

```
# short   ssh_target                   ws_high  ws_max  ss_high  ss_max
.104      mmv@198.18.1.104             600M     700M    130M     150M
.102      mmv@198.18.1.102             900M     1000M   300M     400M
cloud1    sysadm@cloud1.beerloga.su    1600M    1800M   500M     700M
cloud2    sysadm@cloud2.beerloga.su    1600M    1800M   500M     700M
nuxt      sysadm@nuxt.beerloga.su      -        -       700M     800M
nuxt2     sysadm@nuxt2.beerloga.su     -        -       700M     800M
sebek     sysadm@188.220.148.143       -        -       380M     450M
```

Значения — снимок фактического состояния парка на 2026-08-24 после введения
ступеней. `High` = ~85–88% `Max`.

**Потолок — не общая RAM, а `MemAvailable`.** Лимит `Max` выше доступной памяти
бесполезен как предохранитель: узел уйдёт в zram-своп и системный OOM раньше,
чем cgroup досчитает до `Max`. Поэтому `Max` держим ниже `MemAvailable` с
буфером под колебания системы. Замерено 2026-08-24:

| узел | RAM | MemAvailable | ss/ws Max |
|---|---|---|---|
| nuxt | 1967 | 1396 | ss 800 — большой запас |
| nuxt2 | 1966 | 1442 | ss 800 — большой запас |
| sebek | 961 | 512 | ss 450 — ниже available с буфером ~60 |
| .104 | 964 | 626 | ws 700 — **близко к available**, кандидат на пересмотр |

На exit-узлах ss — единственный крупный потребитель, делить память не с кем,
поэтому лимиты подняты (nuxt/nuxt2 550→800). sebek **как .104 по общей RAM, но
не по свободной**: там docker+unbound съедают ~448 MiB, available всего 512, так
что ss Max 450 (не 550 и не 700) — выше историч. mimalloc-пика 184 в 2.4×, но с
живым системным буфером. `.102` ws Max выровнен 1024→1000. `Max` для ws не
раздуваем — ждём недельные пики от `fleetwatch`.

### drop-in, который ставит `apply.sh`

Один canonical файл на сервис, заменяет разнородные ручные:
`/etc/systemd/system/<unit>.service.d/20-memory.conf`

```ini
# Managed by ops/memory-tuning/apply.sh — do not edit on the node.
[Service]
MemoryAccounting=yes
MemoryHigh=<high>
MemoryMax=<max>
```

`THREAD_STACK_SIZE_KB=512` для клиентов сохраняется, но **отдельным** файлом
`30-thread-stack.conf` — это не memory-лимит, а параметр рантайма, у него своя
судьба. `MIMALLOC_*` не переносятся: под jemalloc они мертвы.

Старый `30-mem-tuning.conf` (где он есть) `apply.sh` удаляет, чтобы мёртвые
`MIMALLOC_*` не оставались висеть.

### `apply.sh`

```
apply.sh                 # раскатать на все узлы из fleet.tsv
apply.sh <host>          # только один узел
apply.sh --dry-run       # показать, что изменится, ничего не ставя
```

Для каждого узла: пишет drop-in через `ssh … sudo install`, затем
`systemctl daemon-reload` и — поскольку лимиты применяются cgroup'ом на живом
сервисе — **без рестарта** (`daemon-reload` + `set-property`-эквивалент).
Проверяет, что новый `MemoryHigh` выше текущего `MemoryCurrent`, иначе отказ (не
устраивать reclaim-шторм).

Идемпотентен: повторный запуск на неизменной таблице ничего не меняет.

## Интеграция в install.sh (сделано 2026-08-24)

Провижининг нового узла ставит drop-in сам: `collect-from-reference` копирует
`fleet.tsv` в бандл, `install.sh` находит строку узла по `--host` и пишет
`20-memory.conf`/`30-thread-stack.conf` перед запуском сервисов. Ключ `short`
у fleet.tsv специально под это; `ssh_target` продолжает использоваться `apply.sh`.

Узел, отсутствующий в таблице (или сервис с `-`), остаётся с дефолтами systemd —
поведение как до правки. Бандл без `memory-tuning/fleet.tsv` (старый)
пропускается с подсказкой.

## Риски

- **Затираем ручные правки на узлах.** Это и есть цель — сделать таблицу
  единственным источником. Но перед первым прогоном `apply.sh --dry-run`
  сверяется с фактическим состоянием, чтобы не потерять неучтённое.
- **`daemon-reload` на живом сервисе** безопасен для cgroup-лимитов (применяются
  немедленно, без рестарта процесса). НЕ трогает env — новые env-переменные
  подхватятся только при рестарте, поэтому менять лимиты и env — разные по
  последствиям операции, и `apply.sh` предупреждает, если изменился env.

## Критерии приёмки

1. `apply.sh --dry-run` на неизменной таблице показывает «нет изменений» на всех
   семи узлах (значит таблица точно отражает факт).
2. После `apply.sh` у каждого сервиса ровно один memory-drop-in, `High < Max`,
   без `MIMALLOC_*`.
3. `README.md` и `README.ru.md` описывают формат таблицы и порядок раскатки.
