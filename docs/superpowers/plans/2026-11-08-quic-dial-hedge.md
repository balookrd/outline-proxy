# Гонка QUIC-дозвонов с нового порта — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** если на QUIC-рукопожатии за 1 с нет ответа, не ждать 10 с на том же UDP-потоке, а параллельно начать второй дозвон с нового локального порта и взять первое установившееся соединение. Так дозвон, чей UDP-поток выбрасывается на пути, обходится примерно в 1 с вместо 10 с и не валит пробу.

**Архитектура:** новый модуль `crates/outline-transport/src/quic/dial_race.rs` с функцией гонки, обобщённой по попытке дозвона. `connect_h3_connection` (`h3/shared.rs`) и `dial` (`xhttp/h3_pool.rs`) вызывают её вместо одиночного `endpoint.connect_with(..).await`. В гонке участвует только QUIC-рукопожатие. Сборка HTTP/3 (SETTINGS), датаграммы, PMTU-рекордер и `ConnLife` создаются один раз, для победителя.

**Tech Stack:** Rust (edition 2024), quinn 0.11 + vendored quinn-proto 0.11.19, tokio.

## Основание (разбор 2026-11-07/08)

- Симптом на cloud1/2: `HTTP/3 fresh connect timed out after 10s to 77.91.78.220`, а следом WARN `probe stage failed group="main" uplink="nuxt2" probe="tls"` и кап ws_h3 → ws_h2 на 60 с. В журнале cloud1 таймауты есть с 12.10 (с начала журнала), от 2 до 140 в сутки. С домашних .102/.104 до nuxt2 и с cloud до nuxt таких таймаутов почти нет.
- Двусторонний tcpdump long-header-пакетов, cloud1 `enp3s0` и nuxt2 `ens3`, 18:57–00:48 MSK: 885 попыток рукопожатия, 47 без ответа. В 46 из них ни один Initial не дошёл до nuxt2: все 9 отправок за 10 с с того же порта (+0, +1, +3, +7, +10 с, это PTO quinn с `initial_rtt` 333 мс) потеряны. Все 16 таймаутов из журнала совпали с такими попытками.
- В ту же миллисекунду дозвон с соседнего порта проходит за 20 мс. Значит, путь выбрасывает отдельный UDP-поток (5-tuple) целиком, и повторы с того же порта бесполезны. Новый порт даёт новый 5-tuple.
- Доля потерянных потоков в эпизоде (23:27–00:18 MSK) около 13%. Если попытки независимы, две подряд потеряются с вероятностью около 1,7%, три — около 0,2%.

## Global Constraints

- Каждая попытка гонки = свой `client_endpoint` (новый сокет, новый порт), как и сейчас при каждом дозвоне. Сокет не переиспользовать: смысл гонки в новом 5-tuple.
- Попытки выполняются в той же задаче tokio (`FuturesUnordered` / `select!`), НЕ через `tokio::spawn`. Профиль дозвона (`fingerprint_profile::with_dial_profile`) и паддинг носителя (`carrier_padding`) — task-local, а `h3_quic_client_config_with_first_probe` и `h3_dial_offers_udp_datagrams` читают их внутри дозвона. В порождённой задаче профиль потеряется, и ClientHello уйдёт с профилем по умолчанию.
- Внешний бюджет не меняется: `timeout(fresh_connect_timeout(), ..)` (10 с, `dial_timeouts.rs`) охватывает всю гонку плюс сборку HTTP/3. Текст ошибки таймаута не менять: на него опираются `classify_*` и разбор журналов.
- Если попытка завершилась ошибкой (`QUIC handshake failed`, например ICMP unreachable), а других незавершённых попыток нет, гонка возвращает эту ошибку сразу, как сейчас. Ошибка — не признак потерянного потока, и многоадресный failover в `shared_dial` ждёт её быстро.
- Проигравшие попытки закрываются явно. Незавершённый `Connecting` бросается (`drop`). Попытка, которая успела завершить рукопожатие одновременно с победителем, закрывается `connection.close(0u32.into(), b"")`. После этого бросается её endpoint.
- PMTU: всем попыткам один и тот же `first_probe` из кэша; `pmtu_cache::spawn_recorder` — только для победителя.
- `initial_mtu` 1200, раскладку CRYPTO и транспортные параметры не трогать: каждая попытка — обычный дозвон с текущим профилем.
- Тесты — в `tests/` рядом с модулем (`#[cfg(test)] #[path = "tests/dial_race.rs"] mod tests;`).
- Модуль под feature `h3`, как и остальной `quic/`. Сборка с `--no-default-features` должна проходить.
- Комментарии в коде и сообщения коммитов — по-английски; документация — парами EN/RU в одном изменении.
- `git commit` / `git push` — только по явной команде владельца. Коммитить `git commit -- <пути>`. Без трейлера `Co-Authored-By` и без подписи Claude Code.
- Гейт (как в CI): `cargo fmt --check` по пакетам CI, `cargo clippy --workspace --exclude sockudo-ws --all-targets --no-deps -- -D warnings`, оба бинаря с `--no-default-features`, `cargo test --workspace --exclude sockudo-ws`, `cargo test -p outline-transport --all-features`, инварианты CI, Linux в docker (`rust:bookworm`) до коммита.
- Прод не рестартить без согласия владельца; раскатывать по одному узлу.

## Параметры гонки

| Параметр | Значение | Почему |
|---|---|---|
| Задержка первой дополнительной попытки | 1 с | Совпадает с первым PTO quinn (3 × `initial_rtt` 333 мс): на захвате первый повтор Initial уходит ровно через 1,000 с. При RTT 16 мс рукопожатие занимает ~20 мс, при мобильном RTT 300 мс — ~0,7 с, то есть в норме гонка не запускается. |
| Задержка второй дополнительной попытки | 3 с от начала | Второй PTO (+3 с на захвате). Даёт третий 5-tuple, если второй тоже потерян (~1,7% в эпизоде). |
| Максимум одновременных попыток | 3 | Каждый endpoint держит буфер приёма 2,87 МиБ (`TrackedEndpoint`). Лишние endpoint живут не дольше гонки, не больше 10 с. |
| Настройка в конфиге | нет | Константы в `dial_race.rs`. Открытый вопрос ниже. |

## Метрика и журнал

- `outline_ws_quic_dial_hedges_total{kind="ws_h3"|"xhttp_h3", result="won"|"lost"}`:
  - `won` — победила дополнительная попытка (первая потеряна или медленнее);
  - `lost` — дополнительная попытка была запущена, но первая всё же выиграла.
  Отношение `won` к числу дозвонов (`h3_carrier_dialed`) показывает долю потерянных потоков на пути; высокий `lost` значит, что 1 с мало для этого RTT.
- Журнал: запуск дополнительной попытки — `debug`; победа дополнительной попытки — `info` с `server_addr`, номером попытки и временем (событие редкое, по нему видно эпизоды на пути). Проба (без `cache_key`) пишет победу в `debug`, как `ConnLife`.

## Задачи

### Задача 1. Функция гонки и юнит-тесты

- [ ] Написать `quic/tests/dial_race.rs` (под `tokio::time::pause`), фейковая попытка = future с заданной задержкой и результатом и флагом `dropped`:
  - первая попытка завершается за 200 мс → результат первой, вторая не запускалась;
  - первая висит, вторая завершается за 50 мс → результат второй в момент ~1,05 с, первая брошена (`dropped == true`);

## Порядок выкатки

Меняется только клиент (`outline-ws-rust`), сервер не трогается. После коммита и пуша по команде владельца, из `ws-nightly`, через `ops/deploy/deploy-binary.sh`, по одному узлу:

1. **cloud1** — на нём больше всего потерянных потоков до nuxt2. Проверка через сутки, с вечерним пиком 22:00–01:00 MSK:
   - в журнале нет `fresh connect timed out ... to 77.91.78.220`;
   - `outline_ws_quic_dial_hedges_total{result="won"}` растёт в эпизодах;
   - WARN `probe stage failed ... uplink="nuxt2" probe="tls"` и кап ws_h3 → ws_h2 по nuxt2 — около нуля (было 20–60 капов в сутки);
   - `outline_ws_h3_endpoints_active` (gauge по `kind`) без постоянного роста.
2. **cloud2** — те же проверки.
3. **.102**, затем **.104** — там потерь потоков нет; проверка, что `lost` и `won` близки к нулю и мобильный/домашний RTT не вызывает лишних гонок.

Откат: `deploy-binary.sh` хранит предыдущий бинарь; поведение без гонки = прежний бинарь.

## Риски

- **Отпечаток.** Браузер не запускает два QUIC-рукопожатия к одному серверу с разных портов. У нас второе появляется только после 1 с без ответа, то есть когда первый поток уже выброшен на пути. Наблюдатель видит второе рукопожатие только в этом случае.
- **Высокий RTT.** На пути с RTT ≥ ~400 мс рукопожатие может не уложиться в 1 с, и гонка будет запускаться без потерь. Это видно по `result="lost"`; лечится увеличением задержки или её выводом из RTT.
- **Память.** До трёх endpoint по 2,87 МиБ на время гонки (≤ 10 с). Постоянный рост `outline_ws_h3_endpoints_active` = утечка проигравших, это проверяется в задаче 3 и при выкатке.

## Открытые вопросы к владельцу

1. Делать ли настройку (например, `[outline] quic_dial_hedge_ms`, 0 = выключено) или оставить константы? Без настройки меньше кода и конфигов на Android; с настройкой можно выключить гонку без пересборки.
2. Одна дополнительная попытка (1 с) или две (1 с и 3 с)? План исходит из двух.
