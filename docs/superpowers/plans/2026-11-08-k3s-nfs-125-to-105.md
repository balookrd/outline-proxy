# Переключение k3s с NFS `198.18.1.125` на `198.18.1.105`

План переноса всех NFS-данных кластера k3s (`k3s-1/2/3`, `198.18.1.51–53`) со
старого NAS WD MyCloud `198.18.1.125` на NAS UGREEN DXP4800 Plus
`198.18.1.105`. Читатель — тот, кто будет выполнять переключение с мака
(kubectl) и по ssh на `k3s-1` и `.105`.

Выкатка — только с явной команды владельца. Сервисы переключаются по одному.

## Блокер: экспорт `.105` отказывал узлам k3s (снят 2026-11-08)

Снят на шаге 0: владелец поменял правило в UGOS, проверка шага 1 пройдена.

С `k3s-1` любое монтирование `198.18.1.105:/volume1/k8s` (`nfsvers=3`, `4.1`,
`4.2`) даёт `mount.nfs: access denied by server`.

Причина: в nfs-utils маска с `*` сравнивается с именем клиента из обратного
DNS, а не с IP. NAS разрешает `198.18.1.51–53` в `k3s-1`, `k3s-2`, `k3s-3`
(`getent hosts` на `.105`), и эти имена под `198.18.1.*` не попадают. Правило
сработает только для адресов без PTR-записи.

## Шаг 0. Настройка экспорта на `.105`

Выполнено 2026-11-08, итоговое правило (вариант A из шага 3):

```
/volume1/k8s 198.18.1.0/24(rw,async,…,root_squash,all_squash,…,anonuid=1000,anongid=10,…)
```

1. В UGOS, в настройках NFS для общей папки `k8s`, клиент — подсеть
   `198.18.1.0/24`. Маска `198.18.1.*` не подходит: nfs-utils сравнивает её с
   именем из обратного DNS, а узлы разрешаются в `k3s-1..3`.
2. Маппинг пользователей — «все пользователи → администратор»
   (`all_squash,anonuid=1000,anongid=10`, uid 1000 = `sysadm`). Любой uid
   клиента, включая root, пишет на NAS как `1000:10`. Это обходит ACL UGOS
   (`system.ugacl_self`, пускает только root и uid 1000) и повторяет поведение
   MyCloud `.125`, где все приводились к 501. Следствие: `chown` с клиента
   возвращает `EPERM`, поэтому `rsync` в шагах 3–6 — `-rlptH`, без `-o -g`.

   Проверка:

   ```bash
   ssh sysadm@198.18.1.105 'grep k8s /var/lib/nfs/etab'
   ```

3. У `Movies`, `Movies_TV`, `Public` подсеть тоже стала `198.18.1.0/24`,
   squash там прежний (`all_squash,anonuid=65534`). От них зависит Jellyfin на
   `.105`, без отдельного решения не трогать.

## Шаг 1. Проверка экспорта с узлов

Для каждого из `k3s-1`, `k3s-2`, `k3s-3`:

```bash
ssh mmv@k3s-1 'T=$(mktemp -d)
sudo mount -t nfs 198.18.1.105:/volume1/k8s "$T" && grep " $T " /proc/mounts
sudo -u "#1000" sh -c "echo ok > $T/.probe-1000 && cat $T/.probe-1000"
sudo sh -c "touch $T/.probe-root && chown 1000:1000 $T/.probe-root && ls -ln $T/.probe-*"
sudo rm -f "$T"/.probe-*; sudo umount "$T"; rmdir "$T"'
```

Ожидаемо: монтирование проходит, в `/proc/mounts` видна версия `vers=3`, запись
под uid 1000 читается, `chown` проходит.

Результат 2026-11-08: пройдено на `k3s-1`, `k3s-2`, `k3s-3`. Файл, созданный
под uid 1000, на экспорте принадлежит `1000:1000`; `chown` и `chmod 0777` от
root проходят; каталог, созданный root, принадлежит `0:0`. `rsync`
(`/usr/bin/rsync`) установлен на всех трёх узлах.

Версия протокола. У inline-томов нет `mountOptions`, kubelet монтирует без
`nfsvers`. Монтирование без версии на `.105` согласует `vers=3`: v4 сервер
отклоняет (`nfsvers=4.1`/`4.2` → `reason given by server: No such file or
directory`, путь `/volume1/k8s` не входит в псевдокорень v4), и `mount.nfs`
откатывается на v3. Протокол остаётся тем же, что на `.125` (v3 + NLM),
`rsize/wsize` — 1 МиБ вместо 128 КиБ.

## Шаг 2. Первичное копирование данных (без простоя)

Копирование выполняется на `k3s-1`: он монтирует оба NAS. Старый экспорт —
только на чтение.

```bash
ssh mmv@k3s-1 'set -e
sudo mkdir -p /mnt/nas-old /mnt/nas-new
sudo mount -t nfs -o nfsvers=3,ro 198.18.1.125:/mnt/HD/HD_a2/k8s /mnt/nas-old
sudo mount -t nfs 198.18.1.105:/volume1/k8s /mnt/nas-new
which rsync'
```

```bash
ssh mmv@k3s-1 'sudo rsync -aH --numeric-ids --info=stats1 /mnt/nas-old/ /mnt/nas-new/'
```

Первичное копирование шло при `no_root_squash`, поэтому `-a` перенёс владельца
501. После перехода на вариант A владелец сменён на `1000:10` (шаг 3), а все
последующие `rsync` — `-rlptH`.

Проверка: число файлов и объём совпадают.

```bash
ssh mmv@k3s-1 'for d in old new; do sudo find /mnt/nas-$d -type f | wc -l; sudo du -s --apparent-size /mnt/nas-$d; done'
```

Результат 2026-11-08: `rsync` завершился с кодом 0 за 1 мин 27 с
(3492 записи, 1478 файлов, 2,31 ГБ, ~26 МБ/с). По каталогам число файлов и объём
совпали, владельцы и права (`find -printf "%U %G %m %p"`) идентичны. Проверка
содержимого `rsync -rnc` показала расхождения только в файлах, которые работающие
сервисы перезаписали после копирования: `smarthome/{humidity,power}/devices.json*`,
`zigbee2mqtt-data/{database.db,state.json}`. Их снимет финальная досинхронизация
каждого сервиса после остановки (шаги 4 и 6). Точки `/mnt/nas-old` и
`/mnt/nas-new` на `k3s-1` оставлены смонтированными для шагов 3–6.

Каталоги `backup/` и `registry/` после этого копирования считаются
окончательными для бэкапов (шаг 3) и получают финальную досинхронизацию для
registry (шаг 5).

## Шаг 3. Переключение CronJob бэкапов

Делать днём, вне окна 03:30–04:30.

Попытка 2026-11-08 16:23 провалилась, CronJob'ы возвращены на `.125`
(ручной прогон после отката прошёл: `kept: 7`, vmbackup без ошибок).
Ошибки на `.105`:

- `grafana-backup` (uid 472): `PermissionError: [Errno 13] Permission denied: '/backup/grafana/grafana-…db.gz'`
  в каталоге `0777`;
- `vmbackup` (uid 1000): `cannot open directory: open /backup/victoria-metrics/data: permission denied`
  (каталог `0700`, владелец 501).

Причины (проверено `setpriv --reuid=<uid>` с `k3s-1`):

1. На корне общей папки `/volume1/k8s` стоит ACL UGOS
   (`system.ugacl_self`, модуль ядра `ugacl_vfs`). Запись разрешена только
   root и uid 1000 (`sysadm`, единственная учётная запись NAS); uid 472, 501,
   999, 1001, 2000, 65534 получают `Permission denied` даже в каталоге `0777`.
2. MyCloud `.125` приводил всех клиентов к владельцу 501, поэтому вся копия на
   `.105` принадлежит `501:1000`. На `.105` без squash uid 1000 не
   перезапишет файлы `0644`/`0600` и не войдёт в каталоги `0700` с владельцем
   501. Это касается и mosquitto, z2m, smarthome (все uid 1000): до исправления
   переключать их нельзя.

Варианты исправления (выбор за владельцем):

| Вариант | Что сделать | Плюсы | Минусы |
|---|---|---|---|
| A. «Все пользователи → admin» | UGOS: маппинг NFS для `k8s` «все пользователи → администратор» (ожидается `all_squash,anonuid=1000`); до переключения `chown -R 1000:1000` копии от root | поведение как у MyCloud: любой uid пода пишет, включая будущие PVC `nfs-client` | `chown` из подов невозможен (сейчас никто не делает); провижнер делает только `chmod` |
| B. Без squash, точечно | `chown -R 1000:1000` копии (кроме `registry/`, он под root); `grafana-backup` перевести на `runAsUser: 0` | UGOS не трогать | каждый новый под с uid ≠ 1000/0 упрётся в ту же ACL |

Выбран вариант A (2026-11-08). Маппинг в UGOS переключили раньше, чем был
сделан `chown` с клиента, поэтому владельца сменили на самом NAS контейнером от
root (`sysadm` в группе `docker`):

```bash
ssh sysadm@198.18.1.105 'docker run --rm --network none -v /volume1/k8s:/d \
  --entrypoint /bin/sh ugreen/jellyfin:10.10.7 -c "chown -R 1000:10 /d"'
```

1000, 2000, 65534 проходят запись в `backup/grafana`, чтение
`backup/victoria-metrics/data` (`0700`), дозапись в `zigbee2mqtt-data`,

`rsync -rlptH --delete` (код 0, ошибок `chown` нет). Остаются отличия только в

Повтор 2026-11-08 16:43 — успешно. Досинхронизация `backup/` — 0 файлов.

## Откат

Данные на `.125` во время переноса не меняются (монтируются `ro`), поэтому
откат любого сервиса — возврат манифеста:

```bash
git checkout -- <манифест>
kubectl -n <ns> scale deploy/<name> --replicas=0
kubectl apply -f <манифест>
```

Записанное сервисом на `.105` после переключения при этом теряется. Если нужно
его сохранить — до `apply` скопируйте каталог обратно
(`rsync /mnt/nas-new/<каталог>/ → 198.18.1.125`, смонтировав `.125` на запись).

Для провижнера откат — `helm uninstall` и установка со старыми values.
