# Выбор исходящего IPv6-адреса (source)

*English version: [OUTBOUND-IPV6.md](OUTBOUND-IPV6.md)*

Как `outline-proxy` выбирает исходящий (source) IPv6-адрес для трафика, который
он отправляет в интернет: для upstream-соединений сервера (`outline-ss-rust`) и
для direct-дозвонов клиента (`outline-ws-rust`, путь `via = "direct"` / обход
TUN). Обычно оператору нужно одно из двух противоположных:

- Стабильность: держать долгие соединения (SSH, тайлы карт, стриминг) живыми,
  пока хост ротирует IPv6-адреса privacy extensions.
- Ротация: разносить исходящий трафик по множеству source-адресов, чтобы
  наблюдатель не мог связать его весь с одним адресом.

## Чем обратный трафик ограничивает выбор

Выбрать source — простая половина. Сложная — добиться, чтобы ответ вернулся. Что
сработает, решают три условия:

1. NDP. На общем SLAAC-сегменте вышестоящий роутер шлёт Neighbor Solicitation
   на каждый адрес назначения и пересылает ответ, только если кто-то за этот
   адрес ответил. Ядро отвечает лишь за адреса, сконфигурированные на
   интерфейсе. Поэтому случайный, не сконфигурированный source-адрес не получит
   ответ, если NDP за него никто не проксирует.
2. Маршрутизация. Если весь префикс маршрутизируется на хост (делегирование
   DHCPv6-PD или ручной AnyIP-маршрут), ответы на любой адрес из него приходят
   без NDP.
3. Анти-спуфинг (RPF / BCP38). Вышестоящий узел может дропать пакеты, source
   которых вам не выделен. Домашний роутер (например, Keenetic) обычно этого не
   делает; провайдер на общем сегменте — может.

`IPV6_FREEBIND` позволяет сокету забиндить нелокальный адрес, но не помогает с
пунктами (1)–(3): это условия сетевого уровня, их надо выполнить отдельно.

## Серверные режимы (`[outbound]` / `--outbound-ipv6-*`)

Задайте ровно один режим source; конфиг с несколькими загрузчик отвергает
(`... are mutually exclusive; pick one`).

| Режим | Ключ конфига | Пул source | Что нужно для обратного трафика |
|-------|--------------|------------|----------------------------------|
| Статический префикс | `ipv6_prefix = "2a01:…::/64"` | весь CIDR (случайный адрес на коннект) | `IPV6_FREEBIND` + префикс on-link либо AnyIP-маршрут; весь /64 маршрутизирован или отвечает на NDP |
| Пул интерфейса | `ipv6_interface = "enp1s0"` | адреса, сконфигурированные на интерфейсе | ничего сверх: адреса принадлежат ядру, и оно отвечает за них на NDP (работает под обычным SLAAC) |
| Динамический префикс | `ipv6_prefix_interface = "enp1s0"` | весь текущий /64 интерфейса, пересчитывается при refresh | то же, что статический префикс (NDP-proxy / ndppd), но /64 определяется, а не зашит |

### `ipv6_prefix`: статический префикс

Биндит случайный адрес из фиксированного CIDR. Подходит, когда у вас есть
маршрутизируемый префикс, который не меняется. Префикс должен быть достижим
обратно на хост: on-link плюс `IPV6_FREEBIND` (ставится автоматически) либо
AnyIP-маршрут `ip -6 route add local <prefix> dev lo`, где `<prefix>` — CIDR из
`ipv6_prefix`.

### `ipv6_interface`: пул адресов интерфейса

Перечисляет глобальные адреса, сейчас сконфигурированные на интерфейсе, и биндит
случайный. Это сконфигурированные адреса, поэтому ядро отвечает за них на NDP и
RPF проходит; это единственный режим, работающий на обычном SLAAC-сегменте без
ndppd. С privacy extensions (`use_tempaddr=2`) пул следует за ротируемыми
temporary-адресами. На Linux пул читается из `/proc/net/if_inet6`, и
deprecated-, tentative- и dadfailed-адреса пропускаются, поэтому temporary-адрес,
который вот-вот удалят, не выбирается (flow на нём оборвался бы при удалении).

### `ipv6_prefix_interface`: динамический префикс из интерфейса

Определяет текущий глобальный /64 интерфейса и биндит случайный адрес по всему
префиксу, как статический режим, но пересчитывает /64 при каждом refresh
(`ipv6_refresh_secs`, по умолчанию 30). Подходит, когда префикс динамический:
например, провайдер делегирует префикс, меняющийся при каждом реконнекте, а
роутер (Keenetic) ре-анонсирует его в LAN по SLAAC. Как и статическому префиксу,
ему нужен весь /64, маршрутизированный обратно; см.
[NDP-proxy (ndppd) для prefix-режимов](#ndp-proxy-ndppd-для-prefix-режимов).

### Закрепление source

`ipv6_sticky = true` (по умолчанию) вместе с `ipv6_sticky_ttl_secs` (по
умолчанию 1800) закрепляет один source за IP назначения на время TTL — так,
например, Cloudflare-челлендж `cf_clearance` остаётся валиден между
последовательными запросами клиента. Разные назначения по-прежнему получают
разные source, а после TTL назначение получает новый source. Без режима source
по префиксу или интерфейсу настройка ни на что не влияет.

## Клиент, direct-маршрут (`outline-ws-rust`)

Uplink-трафик клиента туннелируется на ваш сервер, и его source никогда не
ротируется. Эти настройки касаются только direct-маршрута (`via = "direct"` /
обход TUN), где клиент сам ходит в интернет.

### `prefer_public_ipv6_src`: стабильный source (по умолчанию `true`)

Ставит `IPV6_PREFER_SRC_PUBLIC` (RFC 5014) на исходящие IPv6-сокеты, чтобы ядро
выбирало стабильный public/SLAAC-адрес вместо ротируемого temporary-адреса
privacy extensions. Без этого direct-IPv6-соединения рвутся, когда у
temporary-адреса истекает `valid_lft` и ядро его удаляет. Поставьте `false`,
чтобы намеренно использовать ротацию privacy extensions для source, принимая,
что долгие flow рвутся при истечении `valid_lft`. Системный `use_tempaddr` на
этот выбор не влияет, влияет только ключ конфига. Только Linux; ядра без этой
опции её игнорируют.

### `direct_ipv6_prefix_interface`: ротируемый /64 (opt-in)

Клиентский аналог серверного `ipv6_prefix_interface`: каждый direct-IPv6-дозвон
биндит случайный адрес из текущего /64 интерфейса, перечитывая
`/proc/net/if_inet6` на каждом коннекте, поэтому следует за динамическим
префиксом. Требование к обратному трафику то же: /64 должен быть
маршрутизирован обратно через ndppd. Если ключ задан, для direct-дозвонов он
имеет приоритет над `prefer_public_ipv6_src`.

## Как выбрать режим

```
Контролируете ли вы префикс, МАРШРУТИЗИРОВАННЫЙ на хост (DHCPv6-PD, AnyIP)?
├── Да, и он статический               → сервер: ipv6_prefix
├── Да, но он меняется (PD/реконнект)   → *_prefix_interface  (+ ndppd)
└── Нет — обычный общий SLAAC-сегмент
        ├── нужна ротация по всему /64  → *_prefix_interface + ndppd
        │     (только если вышестоящий/роутер НЕ делает строгий RPF — сначала тест)
        ├── нужна ротация, NDP/RPF не решить → сервер: ipv6_interface
        │     (ротация только по реальным temporary-адресам)
        └── нужна стабильность (без ротации) → клиент: prefer_public_ipv6_src
```

`*_prefix_interface` — серверный `ipv6_prefix_interface` или клиентский
`direct_ipv6_prefix_interface`.

Типичная топология: провайдер → Keenetic (получает префикс по DHCPv6-PD,
меняющийся при реконнекте) → SLAAC /64 в LAN → хост. Хост видит динамический
`proto ra` /64 на общем сегменте, поэтому режимам «весь /64» нужен ndppd, а
префикс надо пересчитывать — это и делают режимы `*_prefix_interface`.

## NDP-proxy (ndppd) для prefix-режимов

Prefix-режимы (`ipv6_prefix`, `ipv6_prefix_interface` и клиентский
`direct_ipv6_prefix_interface`) биндят случайные, не сконфигурированные адреса.
На SLAAC-сегменте хост должен отвечать на NDP за весь /64, чтобы ответы
возвращались; это делает `ndppd`. Поскольку /64 динамический, проксируемый
префикс должен следовать за ним: `scripts/ndppd-prefix-sync.sh`, который
`ndppd-prefix-sync.timer` запускает раз в 30 с, читает текущий RA `/64`
интерфейса `IFACE` и переписывает `/etc/ndppd.conf` при смене.

Выполняйте от root на хосте, из checkout'а репозитория. Сервисный юнит задаёт
`IFACE=enp1s0`; для другого интерфейса поправьте `Environment=IFACE=` в
`/etc/systemd/system/ndppd-prefix-sync.service` и замените `enp1s0` в строке с
`proxy_ndp` ниже.

```sh
apt install ndppd
install -m 0755 scripts/ndppd-prefix-sync.sh /usr/local/sbin/
install -m 0644 scripts/ndppd-prefix-sync.service scripts/ndppd-prefix-sync.timer /etc/systemd/system/
# ndppd нужны forwarding + proxy_ndp (закрепите в /etc/sysctl.d/):
sysctl -w net.ipv6.conf.all.forwarding=1
sysctl -w net.ipv6.conf.enp1s0.proxy_ndp=1
systemctl daemon-reload
systemctl enable --now ndppd ndppd-prefix-sync.timer
```

Проверка: `cat /run/ndppd-prefix.state` печатает /64, который скрипт записал
последним, в `/etc/ndppd.conf` под `proxy <IFACE>` есть блок `rule <prefix>`, а
каждая смена пишется в журнал с тегом `ndppd-prefix-sync`
(`journalctl -t ndppd-prefix-sync`).

## Ротация и долгие соединения

Когда время жизни префикса короткое, ротация и долгие соединения конфликтуют:

- Режим пула интерфейса ротирует по temporary-адресам ядра. Долгое соединение
  живёт лишь до тех пор, пока у его source-адреса не истечёт `valid_lft` и ядро
  его не удалит, — тогда оно рвётся. Код это не предотвратит: время жизни задаёт
  RA `valid_lft`, который выставляет вышестоящий узел.
- Если роутер ваш и RA `valid_lft` можно поднять, задайте `temp_prefered_lft`
  коротким (частая ротация для новых соединений) и `temp_valid_lft` длинным
  (старые адреса остаются, существующие flow выживают). Потолок
  `temp_valid_lft` — анонсируемый в RA `valid_lft`.
- Если время жизни префикса короткое и изменить его нельзя, выбирайте между
  ротацией и стабильностью долгих flow для каждого хоста настройками выше.
- Режимы `*_prefix_interface` берут префикс от preferred-адреса (никогда не от
  deprecated), поэтому новый flow реже попадает на префикс, который вот-вот
  исчезнет.

## Проверка обратного трафика

Прежде чем полагаться на любой prefix-режим «весь /64», убедитесь, что
вышестоящий узел принимает не сконфигурированный source (NDP + RPF). Выполняйте
от root; замените `2a01:…:dead` на неиспользуемый адрес из вашего /64, а
`enp1s0` — на ваш интерфейс:

```sh
ip -6 addr add 2a01:…:dead/64 dev enp1s0 nodad
ping6 -c3 -I 2a01:…:dead 2606:4700:4700::1111   # есть ответы → NDP/RPF OK
ip -6 addr del 2a01:…:dead/64 dev enp1s0
```

Нет ответа — сегмент не вернёт трафик для произвольных source; используйте
`ipv6_interface` (сервер) или `prefer_public_ipv6_src` (клиент).

Команды для просмотра текущего состояния:

```sh
ip -6 route show proto ra                 # текущий динамический /64 (и его expiry)
ip -6 addr show dev enp1s0                 # temporary vs mngtmpaddr, lifetimes
sysctl net.ipv6.conf.{all,default}.use_tempaddr   # включена ли ротация?
```

## Справочник конфига

Сервер (`outline-ss-rust`): блок `[outbound]` или флаги CLI. Флаг (или его
переменная окружения) перекрывает ключ конфига.

| Ключ | Флаг CLI / переменная окружения | По умолчанию | Значение |
|------|---------------------------------|--------------|----------|
| `ipv6_prefix` | `--outbound-ipv6-prefix` / `OUTLINE_SS_OUTBOUND_IPV6_PREFIX` | не задан | статический CIDR-пул source |
| `ipv6_interface` | `--outbound-ipv6-interface` / `OUTLINE_SS_OUTBOUND_IPV6_INTERFACE` | не задан | пул адресов интерфейса |
| `ipv6_prefix_interface` | `--outbound-ipv6-prefix-interface` / `OUTLINE_SS_OUTBOUND_IPV6_PREFIX_INTERFACE` | не задан | динамический /64 из интерфейса |
| `ipv6_refresh_secs` | `--outbound-ipv6-refresh-secs` / `OUTLINE_SS_OUTBOUND_IPV6_REFRESH_SECS` | 30 | интервал перечисления / пересчёта, секунды |
| `ipv6_sticky` | `--outbound-ipv6-sticky` / `OUTLINE_SS_OUTBOUND_IPV6_STICKY` | `true` | закреплять source за IP назначения |
| `ipv6_sticky_ttl_secs` | `--outbound-ipv6-sticky-ttl-secs` / `OUTLINE_SS_OUTBOUND_IPV6_STICKY_TTL_SECS` | 1800 | TTL закрепления, секунды |

Клиент (`outline-ws-rust`, ключи верхнего уровня конфига):

| Ключ | По умолчанию | Значение |
|------|--------------|----------|
| `prefer_public_ipv6_src` | `true` | стабильный public source для direct-IPv6; `false` → ротация privacy extensions |
| `direct_ipv6_prefix_interface` | не задан | ротируемый /64 source для direct-IPv6 (нужен ndppd) |
| `direct_fwmark` | не задан | `SO_MARK` на сокетах direct-маршрута, чтобы их трафик не уходил обратно в TUN-устройство; только Linux |
