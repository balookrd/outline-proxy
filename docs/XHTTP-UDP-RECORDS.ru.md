# Фрейминг записей SS-UDP поверх XHTTP

*English version: [XHTTP-UDP-RECORDS.md](XHTTP-UDP-RECORDS.md)*

Явные границы датаграмм для Shadowsocks UDP поверх XHTTP-носителя
(`xhttp_h1` / `xhttp_h2` / `xhttp_h3`). Без них байтовый поток носителя молча
склеивает и разрезает пакеты, и каждый per-packet AEAD-декрипт на приёмной
стороне падает.

## Зачем

Датаграм-транспорты исходят из того, что носитель сохраняет границы пакетов:
одна отправка — один пакет, одно чтение — один пакет. Это контракт
`DatagramChannel` в `crates/outline-transport/src/frame_io.rs`.

WebSocket-носитель его выполняет: `Message::Binary` — это настоящий WS-фрейм,
поэтому `from_ws_datagrams` отдаёт SS-слою ровно то, что записал пир.

XHTTP-носитель — нет. Его полезная нагрузка это HTTP-тело, и любой слой ниже
волен перенарезать его как угодно:

- клиентский downlink-ридер форвардит тот кусок, который отдал h1/h2/h3
  (`drain_hyper_body` для h1/h2, `drain_h3_body` для h3);
- серверный uplink-насос stream-one форвардит каждый кадр тела запроса
  (`ingest_uplink_inorder`);
- CDN или любой промежуточный узел может дополнительно склеить или разрезать
  поток.

То есть граница чанка — не граница датаграммы. Два шифрованных пакета, пришедших
слипшимися, декриптуются как один переразмеренный буфер: `aes-256-gcm decryption
failed` / `xchacha20-poly1305 decryption failed` на клиенте и `no configured key
matched the incoming udp data` на сервере. Пакет, пришедший половиной,
декриптуется как огрызок: `UDP packet is too short` / `packet too short`. На бою
эти два симптома шли примерно 5:1.

VLESS-UDP этому не подвержен: он пишет собственные записи `len ‖ payload`, и его
парсер прямо рассчитан на «одна датаграмма несёт несколько записей с
длина-префиксом». Здесь то же свойство даётся SS-UDP.

## Формат записи

Каждая датаграмма уходит на провод одной записью:

```text
record := len:u16 (big endian) || payload[len]
```

| Поле      | Размер             | Значение                                  |
|-----------|--------------------|-------------------------------------------|
| `len`     | `u16` big-endian   | длина следующего за ним payload           |
| `payload` | `len` байт         | одна датаграмма в терминах слоя-носителя  |

Кодек живёт в `crates/outline-wire/src/udp_records.rs` и общий для обоих бинарей.
Декодер (`UdpRecordDecoder`) — потоковый автомат: вход может быть разрезан на
любой границе байта, а один чанк может нести сколько угодно записей, целых и
частичных. Запись с `len = 0` ничего не несёт и пропускается (энкодер такую
никогда не порождает). Датаграмму сверх потолка `u16` выразить нельзя — транспорт
её дропает ровно так же, как дропает любой переразмеренный UDP-пакет: реальных
датаграмм такого размера не бывает.

Фрейминг лежит **снаружи** [carrier-padding'а](PADDING.ru.md): payload записи —
это padding-кадр, когда padding включён, и голый шифрованный пакет, когда
выключен, так что обе фичи сочетаются в любой комбинации.

Фреймятся только SS-UDP-ноги XHTTP-носителя. TCP-ноги (SS-over-XHTTP,
VLESS-over-XHTTP) по своей природе байтовые потоки и не затронуты — как и все
WebSocket-носители и VLESS-UDP.

## Гейт: договорённость на проводе

В отличие от padding'а, который синхронизируется конфигом и не имеет бита на
проводе, фрейминг записей согласуется по сессии одним заголовком:

| Направление       | Заголовок                     | Значение                            |
|-------------------|-------------------------------|-------------------------------------|
| клиент → сервер   | `X-Outline-Udp-Records: 1`    | «эта сессия несёт датаграммы»       |
| сервер → клиент   | `X-Outline-Udp-Records: 1`    | «я тоже буду фреймить эту сессию»   |

Клиент шлёт заголовок на каждом запросе SS-UDP-сессии XHTTP (GET packet-up и его
uplink-POST'ы либо POST stream-one). Сервер отвечает эхом, только если базовый
путь резолвится в SS-UDP-маршрут, и защёлкивает решение на сессии — у
packet-up-клиента GET и POST это разные запросы, и создать сессию может любой из
них.

Фрейминг включается, только если `1` сказали **обе** стороны. Следствия:

- старый сервер не эхнет → клиент сохраняет исторический нефреймленный провод;
- старый клиент не просит → сервер не фреймит;
- сторонний клиент (xray, sing-box, Outline) не затронут: он ни шлёт, ни
  принимает этот заголовок, его провод байт-в-байт прежний.

Именно негоциация делает это on-wire-изменение безопасным для постепенной
раскатки. Она же требует, чтобы возможность доходила до сервера *в момент
дозвона*: warm-standby-стримы SS-UDP дилятся заранее, поэтому пул дилит уже с
флагом (`with_datagram_records`), а не пытается договориться постфактум.

## Порядок раскатки

1. **Сначала серверы.** Сервер, который фреймит только по запросу, для всех уже
   работающих клиентов — no-op.
2. **Потом клиенты.** Обновлённый клиент начинает просить; сессии к обновлённому
   серверу фреймятся сразу, сессии к старому сохраняют текущее поведение.
3. Правок конфига не требуется ни с одной стороны, согласованный рестарт не
   нужен: договорённость — по сессии, поэтому клиент, переподключившийся после
   обновления сервера, подхватит фрейминг на следующем дозвоне.

Откат симметричен: сервер, откаченный назад, перестаёт отвечать эхом, и клиенты
на следующем дозвоне возвращаются к нефреймленному проводу.

## Проверка

Симптом громкий, поэтому фикс видно в логах: на нагруженном SS-UDP-аплинке
XHTTP пропадают пары `decryption failed` / `packet is too short` на клиенте и
`no configured key matched the incoming udp data` / `packet too short` на
сервере, а `ws_h3`-носители того же клиента (где проблемы не было) остаются без
изменений.
