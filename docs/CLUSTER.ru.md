# Mesh-кластер серверов (anycast-вход + shard-relay на home)

*English version: [CLUSTER.md](CLUSTER.md)*

Документ описывает, как несколько серверов `outline-ss-rust` работают одним
кластером: клиент `outline-ws-rust` входит через любой сервер, а сессия
закреплена за своим home-сервером. Сервер, который не является home сессии
(edge), сам терминирует крипту клиента и пересылает application-plaintext на
home по QUIC-каналу mesh; маршрут выбирается по shard-id, зашитому в session id.
Если home недоступен или mesh встал, клиент получает новую сессию — так же, как
на standalone-сервере при resume-miss.

Область: носители VLESS и combined-SS. Раздельный SS кластером не
поддерживается. Шаги развёртывания — в [`CLUSTER-DEPLOY.ru.md`](CLUSTER-DEPLOY.ru.md).

## Почему сама сессия не переезжает

Припаркованное на сервере состояние — живое upstream-соединение:
установленный TCP-сокет к target с его sequence numbers, source-адресом и
состоянием в ядре (`ParkedTcp`) либо привязанный `UdpSocket`
(`ParkedVlessUdpSingle`). Ничего из этого нельзя сериализовать и поднять на
другой машине. Поэтому сессия остаётся на home-сервере, а anycast'ом становится
носитель (клиентский транспорт WebSocket / HTTP/3): он может прийти на любой
edge, а edge релеит байты обратно на home. Для клиента это выглядит как «park на
сервере A, unpark на сервере B»; физически состояние всё время жило на home.

## Роли

- home — сервер, владеющий сессией: upstream-соединение к target (или её
  NAT-записи) и парковка resumption (`OrphanRegistry`). Выбирается один раз, при
  первом подключении, и не меняется до конца сессии. Для релеимой сессии он не
  держит crypto-state — только для клиентов, которых обслуживает напрямую.
- edge — сервер, терминировавший клиентский носитель, а вместе с ним и крипту
  клиента. Может быть home (всё локально) или другим сервером (тогда релеит на
  home).
- mesh — QUIC-канал edge → home, который несёт application-plaintext внутри
  взаимно аутентифицированного TLS 1.3-соединения.
- shard-id — 4-битный идентификатор home, зашитый в session id.

## Shard-id в session id

Resumption-`SessionId` — 16 байт; его генерирует home при первом handshake и
возвращает в `X-Outline-Session` (HTTP/WS) или VLESS-addon `0x10`. На сервере
без `[cluster] enabled = true` это случайные байты. Сервер в кластере
кодирует в него свой shard (`crates/outline-wire/src/cluster.rs`,
`encode_session_id` / `decode_shard`):

```
[ seed: 8 байт (случайные, открыто) | payload: 8 байт (XOR с keystream) ]
                                      старший полубайт payload[0] = shard id
keystream = BLAKE3-keyed(obfuscation_key, seed), усечённый до 8 байт
obfuscation_key = BLAKE3 derive_key("outline-proxy cluster shard-obfuscation v1", cluster_psk)
```

- 4 бита — до 16 серверов (`MAX_SHARDS`). Остаточная энтропия — 124 бита: 64 в
  seed и 60 в payload.
- Shard — подсказка маршрутизации, а не секрет: подделанный shard лишь
  направит edge на чужой home, который ответит resume-miss. Но структура не
  должна быть видна DPI, поэтому payload XOR'ится с keystream под ключом,
  выведенным из общего для кластера `cluster_psk`. Любой член кластера заново
  выводит keystream из seed и читает shard за O(1); общей таблицы маршрутов для
  id нет.
- Любые 16 байт декодируются в какой-то shard, поэтому resume id от сервера вне
  кластера или от сбойного клиента попадает на какой-то home и там даёт
  miss.

Бит `SsPathKind` combined-SS (TCP vs UDP) сидит в XHTTP-URL / WS-сегменте
`/{token}`, а не в 16-байтном resume-id, и эти биты не занимает.

## Решение маршрутизации на edge

Edge должен узнать shard до любого SS/VLESS-payload. Shard приходит в
метаданных носителя раньше тела:

| Носитель | Где shard | Когда виден |
| --- | --- | --- |
| WS / H3 / XHTTP resume | заголовок `X-Outline-Resume: <hex>` | при апгрейде, до тела |
| Первое подключение (нет resume) | — | edge и есть home: обрабатывает локально, генерирует session id с `shard = self` |

```
            client (ws-rust)
          resume? X-Outline-Resume
                      │ carrier (WS/H3)
                      ▼
                  ┌────────┐
                  │  EDGE  │  decode_shard(session_id)
                  └───┬────┘
        shard==self   │   shard!=self
        ┌─────────────┘└──────────────┐
        ▼                              ▼
  LOCAL (как сейчас)          MESH RELAY на home[shard]
  accept→crypto→park          терминирует carrier И крипту,
  →upstream→target            льёт plaintext по mesh QUIC
                                       │
                                       ▼
                              HOME[shard]
                              резюмирует парковку / перепарковывает
                              upstream → target  (state живёт только тут)
```

Home выбирается первым подключением. Клиент без resume-id попадает на
какой-то edge, тот обрабатывает его локально и возвращает session id со своим
shard. Все последующие resume этой сессии — через любой edge — указывают на
этот home. То есть home — сервер, на котором клиент впервые поднял сессию.

## Mesh-транспорт

Граница релея одна и одинакова на всех носителях: edge терминирует крипту
клиента и релеит application-plaintext. Он держит SS-ключи и VLESS-UUID из
собственной конфигурации, аутентифицирует клиента по ним и передаёт на home
только байты. Home держит upstream-сокет (или NAT-записи сессии) и парковку и
ничего не расшифровывает и не перешифровывает. Поэтому сессия переживает смену
узла, а узлам не нужно делить клиентские креды. По сети plaintext идёт только
внутри mesh-QUIC-соединения, взаимно аутентифицированного через `cluster_psk`
(см. [Канал и аутентификация](#канал-и-аутентификация)).

О теле до home доходят две вещи, обе в OPEN-заголовке: как оно кадрировано
(байтовый поток либо датаграммы с длиной) и какой прокси-протокол терминировал
edge (SS или VLESS). По кадрированию home выбирает splice; протокол нужен
только чтобы парковка не резюмировалась через границу протокола — то же правило,
что на прямых resume-путях. Пути запроса в заголовке нет (маршрутизация и
padding — локальное дело edge), вида носителя тоже нет (различие WS/XHTTP до
home не доходит).

Релей SS-UDP тоже маршрутизирует без ключей. Идентичность (пользователь,
routing mark, scope сессии) приходит один раз на поток в setup-обмене, а цель
едет внутри каждой датаграммы: plaintext-edge пересылает SOCKS5-обёрнутое тело
(`TargetAddr || payload`), которое SS-UDP-пакет и так содержит. Ответы идут
зеркально: home оборачивает upstream-датаграмму, а edge запечатывает её ключом
клиента. Иначе нельзя: ответ SS-2022 запечатывается против client session id,
который видит только терминирующий узел. Поэтому способ кодирования ответа
хранится не на NAT-записи, а на привязке к ней, и один upstream-сокет за время
жизни сессии может по очереди обслуживать локально расшифровывающий носитель и
релеимый. Та же привязка решает, какой узел ведёт per-user-учёт.

Идентичность задаёт и правило доступа. Релеимая датаграмма в остальном ничем не
заверена, поэтому `user`, routing mark и scope сессии берутся из парковки, а не
из датаграммы. Сессия переподключает NAT-записи, с которыми парковалась, может
создавать записи для новых целей и не может обратиться к записи другой сессии
или другого пользователя: чужая запись лежит под ключом, который эта сессия
построить не может. Две сессии с одной целью (один DNS-резолвер, много
клиентов) получают две записи, а не отказ.

### Per-user-учёт

Per-user-учёт остаётся на узле, который терминирует клиентскую сессию.
Релеимая сессия считается на edge — он видит реальный протокол клиента; home
пишет тот же трафик только в mesh-счётчики с `role="home"`. Учёт на обоих узлах
удвоил бы байты и запросы каждого релеимого пользователя, причём на home — под
`protocol="http3"` (протокол самой mesh), где дубль неотличим от прямого
H3-трафика и вычесть его нельзя.

Четыре splice'а делают это разделение тремя механизмами:

- Байтовый поток и одноцелевой VLESS-UDP: home не трогает `user_counters`
  парковки. Они проходят через splice без изменений, поэтому более поздний
  прямой resume на home продолжит счёт с того же места.
- SS-UDP: решение передаётся в NAT-читатель через привязку записи
  `UdpResponseCoding::Plaintext`, для которой `terminates_client_session()`
  возвращает `false`. По этому ответу home подавляет свои серии
  `outline_ss_udp_*` с меткой `user` (запросы и байты), с исключением ниже.
- VLESS-mux: слой mux-кадров работает на home, и его sub-connection'ы иначе
  считали бы каждый свой payload. `MuxAccounting::OnTheEdge` выключает эти
  счётчики; edge уже посчитал весь поток mux-кадров один раз как VLESS-байтпоток.

Дропы, о которых решил сам home, считаются на home: oversized-датаграмма или
отказ по лимиту конкурентности релея — локальный факт узла, его не пишет никто
другой. Счётчик oversized-датаграмм
(`outline_ss_udp_oversized_datagrams_dropped_total`) несёт метку `user`, поэтому
эта одна серия `outline_ss_udp_*` с меткой `user` на home для релеимой сессии
всё же появляется.

### Форма парковки в setup-ack

Форму парковки называет home в своём setup-ack. В OPEN её назвать нельзя: на
одном пути VLESS мультиплексирует TCP, UDP и mux, а команда приходит в первом
кадре клиента, который edge может прочитать только после ответа на upgrade, а
ответить он может только после ack на OPEN. Поэтому ack отвечает на то, что
OPEN оставил открытым. Для Shadowsocks-носителя, у которого кадрирование и есть
форма, это `OPEN_ACK_ACCEPTED`; для VLESS — форма парковки. Дальше edge решает
сам: команда, которой нужна эта форма, аттестует пользователя и сплайсится;
любая другая освобождает релей до USER-кадра, по которому home потребил бы
парковку, и обслуживается локально.

Обе проверки на home не потребляют парковку. Фаза 1 спрашивает «есть ли
VLESS-форма?» и сообщает найденную; фаза 2 переспрашивает с объявленной формой
прямо перед `take_for_resume`. Поэтому несовпадение формы парковку не
уничтожает (`outline_ss_mesh_relay_rejected_total{reason="park_shape"}`). Две
альтернативы отклонены: второй релей стоит лишнего mesh-RTT перед первым байтом
полезной нагрузки, а форма, названная на фазе 2, приходит уже после того, как
edge проапгрейдил клиента и отдал ему id home'а, — такую сессию остаётся только
уронить. Подробности — в module doc `server/cluster/mesh/frame.rs`.

### Splice для VLESS-UDP и VLESS-mux

У каждой VLESS-формы есть splice на home. Парковка одноцелевой VLESS-UDP-сессии
— один подключённый сокет, и релей качает в него и из него датаграммы с
длиной-префиксом, так что такая сессия переживает смену edge на том же исходящем
порту. Парковка VLESS-mux — набор: по одному sub-connection со своим
upstream'ом на каждый мультиплексированный id. Мигрирует он так же: сокеты
остаются на home, который выполняет слой mux-кадров, а edge пересылает поток
mux-кадров клиента байт-в-байт как байтовый поток. Отдельное поле на проводе не
понадобилось: mux-кадр несёт собственные длины-префиксы, а граница датаграммы
UDP-sub-connection'а и есть граница кадра. Sub-connection'ы, открытые внутри
релеимого mux, дозваниваются с home; mux, который узел поднял для себя,
дозванивается сам, так что sub-connection'ы не распределяются по двум узлам.
Набор принимается или отвергается целиком
(`outline_ss_mesh_relay_rejected_total{reason="park_incomplete"}`): это одна
запись реестра, и половину набора на каждом узле уже ни один узел не запаркует.

На релеимом mux клиент видит, что кадры склеиваются и режутся. Прямой путь
отдаёт один mux-кадр на бинарное WebSocket-сообщение; релеимый пересылает
mesh-чанки, поэтому в сообщении может прийти несколько кадров или часть одного.
Потоково-ориентированному mux-клиенту (такой подразумевает обрамление mux.cool;
в `outline-ws-rust` mux нет вовсе) разницы нет. Сторонний клиент, который
разбирает «один кадр = одно сообщение», должен буферизовать через границы
сообщений, чтобы возобновиться через чужой edge.

При сбое mesh-downlink релеимый mux заново не паркуется. Сбой завершает релей,
отменяя uplink там, где он стоял, — возможно, внутри записи в sub-connection
или внутри дозвона по кадру `New`. У mux нет ни подтверждённого uplink-офсета,
ни downlink-кольца, чтобы переиграть этот пропуск, в отличие от байтового
splice, который именно поэтому сохраняет upstream при той же отмене. Поэтому
набор закрывается, и клиент поднимает mux заново, а не возобновляет сессию с
молчаливым пропуском в sub-connection.

Слой padding носителя принадлежит edge вместе с криптой над ним: edge сам
кодирует и декодирует padding для своего клиента и релеит plaintext без
padding'а, так что на релеимой сессии home padding-кадров не видит.

### Канал и аутентификация

- Канал: долгоживущие QUIC-соединения между членами кластера, одно на пару
  пиров, с мультиплексом множества сессий. QUIC требует TLS 1.3-handshake
  (quinn на rustls с aws-lc-rs — единственным crypto-provider в графе), а он
  даёт эфемерные ECDHE-ключи с forward secrecy и AEAD на уровне записей. ALPN —
  `outline-mesh/1`, keep-alive 10 с, idle-timeout 30 с
  (`server/cluster/mesh/tls.rs`).
- Аутентификация выводится из PSK, X.509-CA нет. Каждый узел выводит из общего
  `cluster_psk` один и тот же Ed25519-keypair
  (`BLAKE3 derive_key("outline-proxy cluster mesh-auth v1", psk)` → Ed25519-seed)
  и строит из него один и тот же фиксированный self-signed сертификат. Все
  члены кластера получают один сертификат и пинят пиров по его SHA-256-отпечатку
  в обе стороны (mutual TLS). Хелпер пина — `bootstrap/cert_pin.rs`
  (`cert_fingerprint` / `CERT_PIN_LEN`); mesh-верификаторы
  (`MeshServerVerifier`, `MeshClientVerifier`) делегируют проверку подписи
  crypto-provider'у и заменяют только path-валидацию на сравнение пина за
  константное время. External-PSK API в rustls нет, поэтому носителем служит
  сертификат, но подписывать и раздавать его не нужно.
- Forward secrecy: с утёкшим PSK можно выдать себя за пира в будущих
  handshake'ах, но записанный прошлый трафик защищён эфемерными ECDHE-ключами.
- Один QUIC-стрим на сессию. Per-stream flow-control даёт backpressure и
  убирает head-of-line blocking между сессиями — класс отказов, который
  проявился в TUN-pump. Собственный PSK+AEAD-транспорт поверх UDP потребовал бы
  своих nonce, rekey и anti-replay, которые в TLS 1.3 уже есть.

### Раскладка mesh-стрима

Стрим — фиксированная setup-последовательность, затем релеимое тело
(`server/cluster/mesh/frame.rs`):

```
edge → home:  OPEN                     OpenHeader с префиксом длины: version (5), framing tcp|udp,
                                       protocol ss|vless, session_id, resume-возможности клиента,
                                       необязательный адрес клиента
home → edge:  ack (1 байт)             OPEN_ACK_ACCEPTED либо форма парковки, если OPEN её
                                       не зафиксировал (VLESS)
edge → home:  USER                     имя пользователя, которого аутентифицировал edge
                                       (длина 1 байт, ≤ 64)
home → edge:  UPSTREAM-ACK (8 байт)    только если OPEN выставил ack-prefix
home → edge:  хвост downlink-replay    только если OPEN выставил symmetric replay
в обе:        тело                     plaintext: байтовый поток (framing tcp) или
                                       `u32 BE length | payload` на датаграмму (framing udp)
```

Кадра данных на чанк нет. Стрим завершается QUIC `finish` (штатно) или `reset`
с кодом ошибки `CloseReason`:

| `CloseReason` | Код | Значение |
| --- | --- | --- |
| `Fin` | 0 | штатное завершение стрима |
| `Abort` | 1 | reset от пира или ошибка upstream |
| `Budget` | 2 | edge порвал релей по health-budget |
| `Capacity` | 3 | home на лимите релеимых сессий |
| `NoSession` | 5 | у home нет парковки под этим resume id или её владелец — не заверенный пользователь |

Пир на старой сборке отображает `Capacity` и `NoSession` в `Abort`.

### Двухфазное установление

Назвать пользователя в OPEN edge не может: он должен решить, что отправить
клиенту в `101`, раньше, чем прочитает первый зашифрованный кадр клиента.
Поэтому фаза 1 задаёт более узкий вопрос: есть ли под этим resume id парковка
той формы, которую этот OPEN умеет сплайсить? Home отвечает одним ack-байтом или
reset'ом `NoSession`. Этот байт несёт форму парковки, если OPEN не мог её
назвать, — это нужно VLESS-edge до прихода первого кадра. Фаза 2, через один
round-trip, шлёт кадр `USER` с идентичностью, которую аутентифицировал edge;
home повторно проверяет форму и владельца парковки и только потом отдаёт её.
Если кадр `USER` не пришёл за 5 с (`USER_FRAME_WAIT`), home отвергает стрим
(`reason="bad_setup"`) и освобождает его relay-permit.

Ответа фазы 1 edge ждёт до апгрейда клиентского носителя. Благодаря этому отказ
не роняет клиента: edge ещё может обслужить его свежей локальной сессией
(`outline_ss_mesh_relay_opened_total{outcome="refused"}` на edge,
`outline_ss_mesh_relay_rejected_total{reason="no_session"}` на home). Отказ —
штатный ответ на каждую истёкшую парковку и каждый id, который этот home не
выдавал, поэтому симптомом является только доля отказов около 100% от открытий.
Цена — один mesh-RTT на релеимую сессию, один раз при установлении.

Версия протокола одна — `OPEN_VERSION = 5`. Home парсит только её: пир на старой
сборке, в том числе шлющий отставной OPEN v4 (где расшифровывал home), получает
reset обеих половин стрима до всякого ack. Такой edge обслуживает клиента свежей
локальной сессией. Расхождение версий стоит непрерывности сессий, а не трафика.

## Конфиг per-node, общие только имена пользователей

Совпадать между узлами должны только `cluster_psk` и таблица пиров. Пути и
креды у каждого узла свои: edge аутентифицирует клиента по собственной
конфигурации, а home ничего не расшифровывает, поэтому на home по релеимой
сессии ничего не резолвится (ни путь, ни таблица маршрутов, ни ключ
пользователя). Узел может обслуживать `/tcp` там, где его пир обслуживает
`/a1b2`, с разными `password` / `method` / `vless_id` у каждого пользователя, и
релеи между ними работают.

Совпадать должно имя пользователя. Парковка ключуется парой (session id,
пользователь), поэтому home сверяет имя, заверенное edge, с владельцем парковки,
прежде чем отдать сессию. Если `carol` на двух узлах означает разных людей,
resume отвергается
(`outline_ss_mesh_relay_rejected_total{reason="unknown_user"}`), и это
задуманное поведение. На байтовом пути имя — единственный сигнал идентичности:
парковка, сделанная под Shadowsocks, отдаётся VLESS-носителю той же учётки и
наоборот. Поэтому `[[users]].id` и каждое имя из `[users.aliases]` должны
обозначать одного и того же человека на каждом узле. См.
`bins/outline-ss-rust/docs/SESSION-RESUMPTION.ru.md` § Кросс-протокольный
resume; переходы считаются в
`outline_ss_orphan_resume_cross_protocol_total{parked,resumed}`.

Имя — единственное, что mesh накладывает на пользовательский конфиг узла, и
ограничение идёт от провода: имя едет в кадре `USER` с однобайтовой длиной,
потолок — `MAX_USER_LEN` (64) в `server/cluster/mesh/frame.rs`. Пустое имя или
имя длиннее 64 байт не может аутентифицировать релеимую сессию (edge откажется
его отправить, парсер home — прочитать), поэтому сервер с
`[cluster] enabled = true` отвергает такое имя на старте
(`config/validation.rs`, `validate_cluster_user_names`), а не теряет resume на
первом релее. Проверяется всё, что может попасть в кадр `USER`: заверяется
эффективная учётная метка, поэтому ключ `[users.aliases]` становится именем на
проводе, когда исходный IP клиента попадает в подсеть алиаса. Проверяются и id
из `[[users]]`, и имена алиасов. Сервер без `enabled = true` кадр `USER` не шлёт,
и ограничение к нему не применяется.

Дефект, который mesh наследует: SS-TCP-парковка ключуется базовым id
пользователя, а прямой resume и заверение на mesh ищут её по эффективной метке.
Пользователь с `[users.aliases]`, подключившийся из подходящей подсети, поэтому
не проходит проверку владельца при корректном конфиге — и на прямом пути, и на
релеимом. Это дефект ключа парковки, а не конфигурации кластера, поэтому строка
лога `unknown_user` в релее сообщает только наблюдаемый факт и не указывает на
конфиг узлов.

Прежний дизайн (wire v4 и раньше, где расшифровывал home) требовал, чтобы
релеимый путь и креды релеимого пользователя совпадали по всему парку.
Асимметрия давала молчаливую чёрную дыру: релей в маршрут без ключей, где каждый
пакет проваливал аутентификацию до конца сессии. Перенос крипты на edge убрал и
требование, и этот режим отказа.

## Home: accept-цикл и лимиты

Accept-цикл на home различает два масштаба отказа. Ошибка соединения (пир его
закрыл, сработал таймаут) завершает цикл для этого пира. Ошибка стрима (стрим
сброшен до прихода OPEN либо OPEN не парсится этой сборкой, например от пира в
середине rolling upgrade) убирает только этот стрим, предварительно явно его
отвергнув. Соединение продолжает нести уже принятые релеи.

Home держит по одному permit на каждую живую релеимую сессию:
`MESH_MAX_RELAYED_SESSIONS` = 4096 на все пиры (`server/cluster/mod.rs`) —
входной аналог исходящего лимита edge `MESH_MAX_RELAY_STREAMS` = 4096. Стрим,
пришедший при исчерпанных permit'ах, сбрасывается с `CloseReason::Capacity` и
считается в `outline_ss_mesh_relay_rejected_total{reason="capacity"}`; edge
обслуживает такого клиента локально.

В VLESS mux весь мультиплекс паркуется атомарно, и релей несёт его по одному
mesh-стриму, не разнося sub-connection'ы по стримам. Можно ли обслужить набор,
home решает один раз, до того как потребит парковку; дальше повторное
подключение набора частично провалиться не может — каждый запаркованный
sub-connection держит обе половины своего upstream.

Для SS-UDP тело — не байтовый поток. Датаграмма атомарна, поэтому релей
кадрирует каждую как `u32 length | payload` на mesh-стриме и снимает
кадрирование на другой стороне. Сырой байтовый splice дал бы QUIC склеить или
порезать пакеты, а home маршрутизирует по датаграммам, так что сбитая граница —
это пакет не туда. (Пока крипта не переехала на edge, то же склеивание ломало
per-packet AEAD-open на home; из этого инцидента на проде и выросло
кадрирование.) Mesh-QUIC-стрим надёжный и упорядоченный, поэтому на mesh-хопе
пакеты не теряются; путь client↔target остаётся best-effort на последней миле.
На home каждая релеимая SS-UDP-сессия закреплена за своей NAT-записью через
per-session scope (её resume id). Две одновременные сессии к одному
`(user, target)` (второй edge, релеящий того же пользователя, или клиентский
warm-probe рядом с реальным трафиком) не делят один upstream-сокет и
last-writer-wins-слот ответов. Resume перенимает запаркованный scope, так что
смена edge переиспользует ту же запись (один source-port к target).

VLESS-UDP кадрируется так же, но решение приходит позже. Его OPEN —
байтовый, потому что до первого кадра клиента edge не знает, какая сессия стоит
за VLESS-resume-id: TCP, UDP или mux. Форма приходит в ack от home, и именно
форма, а не кадрирование из OPEN, определяет, как разделяется тело. Релей
VLESS-UDP кадрирует датаграммы так же, как SS-UDP: собственные кадры клиента с
`u16`-префиксом разбираются на edge, одна mesh-датаграмма на пакет, и целиком
уходят в единственный сокет парковки. Парковка формы mux разрешается в байтовое
кадрирование, а все границы дают сами mux-кадры внутри.

### Health-budget

Члены кластера находятся в разных странах, поэтому хоп edge → home длинный, и
mesh считается best-effort:

- Edge ограничивает каждую uplink-запись в mesh значением
  `mesh_relay_budget_ms` (по умолчанию 4000). Когда home перестаёт вычитывать
  (завис или встал интерконнект), окно QUIC-отправки заполняется и запись
  блокируется; превышение бюджета означает зависший релей.
- При зависании edge сбрасывает mesh-стрим (`CloseReason::Budget`) и закрывает
  клиентский носитель. Клиент начинает новую сессию локально на edge, и тот
  становится новым home; осиротевшая парковка на медленном home истекает по TTL.
- Бюджет измеряет прогресс, а не RTT. Высокий, но текущий RTT продолжает
  завершать записи, поэтому бюджет срабатывает только при полной остановке и
  никогда — на idle-сессии (idle-uplink блокируется на чтении, а не на записи).
  Остановку чистой загрузки без uplink-записей ловит QUIC idle-timeout mesh
  (30 с).

## Home: park и unpark

`OrphanRegistry`, варианты `Parked` и семантика park/resume — те же, что у
прямого носителя: релеимый resume — это тот же `take_for_resume(id, user)`, а
завершившийся релеимый носитель перепарковывает upstream под тем же id. Разница
в том, что home сплайсит парковку на mesh-стрим с plaintext вместо повторного
прогона accept-пути поверх клиентского сокета, поэтому на этой сессии он не
выполняет ни крипту, ни поиск маршрута.

Отсюда «park на A, unpark на B»: клиент уходит с edge A (или edge A умирает),
home паркует, как при любом обрыве носителя; клиент приходит на edge B с тем же
session id, edge B открывает новый mesh-стрим к home, и home делает unpark в
этот стрим.

## Home выбирается один раз: сессии расслаиваются по home

Балансировщик клиента переключает edge (точку входа), но не home. Home
назначается один раз, при рождении сессии, и не переезжает: первое подключение
без resume-id обрабатывается локально на том edge, куда пришло, этот edge
генерирует session id со своим shard и становится home этой сессии. Resume несёт
уже существующий home в своём shard и указывает туда, где сессия была впервые
поднята.

Когда клиент уходит с ещё живого сервера A как с edge (A получил throttle- или
health-штраф, но не умер) и переходит на B:

- существующие сессии (рождённые на A) сохраняют home A; resume через edge B
  релеится обратно на home A по mesh, поэтому они выживают;
- новые сессии, открытые, пока активный edge — B, создаются на B и получают
  home B.

Сессии клиента делятся между двумя home: старые на A, новые на B. Последствия:

- На корректность не влияет. Сессии независимы; ничто не требует, чтобы сессии
  клиента делили один home.
- Асимметрия путей. Старые сессии идут двойным хопом `client → B → A → target`.
  Если с A ушли из-за плохой последней мили (throttle `edge→client`), старые
  сессии выигрывают (их downlink теперь `B→client`) ценой хопа-интерконнекта
  `A→B`. Если с A ушли из-за плохого upstream (`A→target`), старые сессии на
  home A продолжают страдать: релей через B не меняет сегмент `A→target`. Его
  избегают только новые сессии на B.
- A нельзя разгрузить мгновенно. Пока живы старые сессии, A остаётся их home (по
  mesh от B и напрямую для ещё открытых flow). Нагрузка с A уходит только по мере
  закрытия его сессий.
- Расслоение не растёт бесконечно. Старые сессии закрываются, новые рождаются на
  активном edge, а когда A восстановится и снова станет активным edge, новые
  сессии опять сядут на A. Распределение home следует за активным edge с
  задержкой на время жизни сессий.

Миграции home нет: живой upstream-сокет нельзя перенести между машинами (см.
начало документа). Единственное запланированное смягчение —
[открытый риск 2](#открытые-риски): дать клиенту дозваниваться до home напрямую,
когда тот достижим. Это убирает двойной хоп, но не расслоение (home по-прежнему
там, где сессия родилась). Anycast-вход (§5a в
[`CLUSTER-DEPLOY.ru.md`](CLUSTER-DEPLOY.ru.md)) уменьшает расслоение: один
resume-scope, и home — ближайший по сети узел, а не тот, где клиент оказался в
момент открытия сессии.

| Отказ | Поведение | Сессия |
| --- | --- | --- |
| edge умер | клиент переходит на другой edge (существующая uplink-логика); тот же session id → тот же home → unpark | выживает |
| mesh встал | edge рвёт по health-budget → новая сессия на edge | теряется |
| home умер | shard указывает на мёртвый сервер; edge не достучался по mesh → resume-miss → новая сессия | теряется (как на standalone) |
| shard неизвестен (сервер выведен) | нет пира для этого shard → `outline_ss_mesh_relay_opened_total{outcome="fail"}` → новая сессия | теряется |
| у home нет парковки под этим resume id (истекла либо он её не выдавал) | home отказывает на установлении (`no_session`); edge ещё не апгрейдил клиента → свежая сессия на edge | теряется (штатно: парковки истекают) |
| парковка формы, которую релей с таким OPEN запросить не может (SS-UDP-парковка под VLESS-resume-id или наоборот) | home отказывает на установлении (`park_shape`) без потребления парковки → свежая сессия на edge | теряется на этом носителе; парковка доживает до следующего |
| в mux-парковке не осталось sub-connection для переподключения | home отвергает набор целиком (`park_incomplete`), а не сплайсит часть → клиент переподключается | теряется (набор и так был пуст) |
| mesh-downlink релеимого mux сломался или встал посреди сессии | релей завершается с uplink'ом, отменённым в неизвестной точке, поэтому home закрывает набор, а не паркует заново → клиент поднимает mux заново | теряется намеренно (повторная парковка скрыла бы пропуск в sub-connection) |
| форма парковки не та, что нужна VLESS-команде клиента | home называет форму в ack, edge освобождает релей до USER-кадра, ничего не потребляется → локальная сессия на edge | теряется на этом носителе; парковка доживает до следующего |
| пир на отставной версии протокола | home отвергает OPEN до всякого ack → свежая сессия на edge | теряется (только непрерывность; трафик идёт) |

## Взаимодействие с downstream-throttle detection

Padding-детекция троттлинга (серверный `ThroughputMonitor` → cover-кадр `OCTL`
→ смена uplink на клиенте) работает с кластером, с оговорками ниже. Она
работает на обоих padded WS/XHTTP-носителях — TCP и UDP (SS и VLESS); wire без
padding не мониторится. В кластере UDP-нога едет отдельным носителем на том же
uplink index, поэтому релеится своим mesh-стримом на тот же home и подчиняется
тем же оговоркам: обнаруженный UDP-throttle штрафует UDP-ногу и переносит только
её.

- Сигнал рождается там, где придушенный сегмент. Padding-слой (включая
  cover/`OCTL`-кадры) принадлежит узлу, который терминирует клиента, — edge,
  поэтому на релеимой сессии edge и обнаруживает застрявшую последнюю милю, и
  вставляет `OCTL`-кадр в носитель своего клиента. Через mesh из этого сигнала
  ничего не идёт.
- Реакция клиента не зависит от кластера. Клиент получает `OCTL` по носителю
  от edge, штрафует этот uplink (edge) и переходит на другой edge, который
  релеит на тот же home, — сессия выживает. Правок на клиенте не нужно.
- Детектор на home мерил бы не тот сегмент, поэтому для релеимой сессии он там
  не запускается. На home `out`/backlog отражают сегмент home→mesh, а не
  home→client. End-to-end backpressure (клиент тормозит → edge перестаёт
  вычитывать mesh-стрим → QUIC-окно закрывается → home видит backlog) доносит
  client-throttle, но home не различает сегменты:
  - throttle на `edge→client` (последняя миля): смена edge помогает;
  - throttle на `home→edge` (межстрановой интерконнект): смена edge может помочь
    (другой mesh-путь);
  - throttle на `home→target` (upstream): смена edge не помогает; клиент
    переключается между edge'ами, все уходят в cooldown, и в итоге он переходит
    на новый home и теряет парковку.
- Ложные срабатывания от медленного интерконнекта были главной проблемой
  детектора на home: медленный mesh между странами даёт backlog на home и
  ложный `OCTL`. На edge этого не бывает: edge видит только клиентскую милю, а
  медленный интерконнект проявляется у него как остановка чтения из mesh, а не
  как застрявшая запись клиенту.
- Пересекается с health-budget. Оба реагируют на медленный downstream:
  throttle-детекция мягкая (home сохраняется, трафик уводится), health-budget
  жёсткий (носитель рвётся, новый home). Держите budget жёстким полом,
  срабатывающим только при полной остановке, и проследите, чтобы по wall-clock
  он срабатывал позже окна выдержки throttle (`throttle_window_secs` ×
  `throttle_sustain_windows`, по умолчанию 1 с × 5). Иначе budget порвёт сессию и
  потеряет парковку раньше, чем успеет мягкая миграция.

Детекция локальна для edge. Edge владеет и криптой клиента, и своим
padded-writer'ом, поэтому узел, который видит придушенную последнюю милю, сам на
неё и реагирует: запускает `ThroughputMonitor` поверх своего клиентского
носителя и вставляет cover-кадр `OCTL` напрямую. Медленность `home→edge` и
`home→target` отдана health-budget. Детекция включается серверным ключом
`[padding] throttle_detect_enabled` (по умолчанию `false`), который каждый узел
читает у себя, как и остальной padding-конфиг.

В wire v4, когда расшифровывал home, edge ничего вставить не мог и вместо этого
слал home mesh-control-датаграмму `THROTTLE_HINT`. Обе половины удалены вместе с
этой версией протокола: отправитель — с v4-детектором на edge, а приёмник на
home, его реестр сессий и два счётчика
(`outline_ss_mesh_throttle_hints_received_total`,
`outline_ss_mesh_control_datagram_errors_total`) — потому что OPEN до-v5-пира
отвергается и релеимой сессии, о которой он мог бы прислать hint, у него не
бывает. Mesh не анонсирует поддержку QUIC-датаграмм
(`datagram_receive_buffer_size(None)` в `server/cluster/mesh/tls.rs`): старый пир,
который всё ещё пытается отправить hint, получает ошибку на собственной отправке,
и байты в сеть не уходят.

## Безопасность

- Mesh-аутентификация: взаимный пин сертификата, выведенного из PSK, между
  членами кластера (см. [Канал и аутентификация](#канал-и-аутентификация)).
  Хост без `cluster_psk` не выведет keypair и не откроет relay-стрим.
- Топология не раскрывается: при home-down или чужом владельце edge отвечает
  клиенту обычным resume-miss — тем же молчаливым ответом, что и на
  существующем пути owner-mismatch. Наблюдатель не отличит «нет такого shard» от
  «home лежит».
- Shard обфусцирован ключом кластера, поэтому session id для DPI выглядит
  случайным.
- Что видит edge: на всех носителях edge терминирует крипту клиента, то есть
  видит plaintext этого клиента и держит креды из собственной конфигурации. Это
  та же экспозиция, что у любого входного узла для сессий, которые он
  обслуживает напрямую. Для сессий, которые он не несёт, у него нет ничего, а
  через mesh plaintext идёт только внутри взаимно аутентифицированного TLS 1.3
  QUIC-соединения между узлами, у которых есть `cluster_psk`. Home по релеимой
  сессии не держит клиентского ключа: из того, что он пересылает, он читает
  только адрес цели, по которому маршрутизирует.

## Конфигурация

Сервер (`outline-ss-rust`):

```toml
[cluster]
enabled = true
shard_id = 7                       # 0..15, уникален в кластере
cluster_psk = "<base64>"           # один общий секрет; из него выводятся ключ shard-обфускации и mesh-auth keypair
mesh_listen = "[::]:9443"          # QUIC-listener для входящих релеев (mutual pin из PSK, без CA)
mesh_relay_budget_ms = 4000        # бюджет прогресса: стоит дольше → рвём
peers = [
  { shard = 1, addr = "<shard1_ip>:9443" },
  { shard = 7, addr = "self" },    # свой shard: пропускается до разбора addr
  # ...
]
```

`<shard1_ip>` — IP-адрес пира, которому принадлежит shard 1.

| Ключ | По умолчанию | Что делает | Когда менять |
| --- | --- | --- | --- |
| `enabled` | `false` | Главный выключатель. Без `true` остальная секция игнорируется: обычные случайные session id, mesh-listener не поднимается, релея нет. | Чтобы включить или выключить кластер на узле. |
| `shard_id` | обязателен при включении | Shard этого узла, `0..15`. | Один раз, при вводе узла; должен быть уникален. |
| `cluster_psk` | обязателен при включении | Base64 общего секрета; должен декодироваться в непустое значение. | В работающем кластере — только одновременно на всех узлах: узел с другим PSK не проходит mesh-пин. |
| `mesh_listen` | обязателен при включении | Адрес сокета (`IP:port`), на котором слушает mesh-QUIC. Разбирается как `SocketAddr`, имя хоста не принимается. | Если 9443/udp занят или узел должен слушать только один адрес. |
| `mesh_relay_budget_ms` | `4000` (минимум 1) | Бюджет прогресса одной mesh-записи на edge. | Поднять, если длинные, но идущие паузы интерконнекта рвут релеи; держать выше окна выдержки throttle. |
| `peers` | пусто | Shard → mesh-адрес каждого узла. Свой shard пропускается; `addr` — `IP:port`; повтор shard — ошибка. | При добавлении или выводе узла. |

Проверка (`config/loader.rs`, `resolve_cluster`) идёт на старте и прерывает его
при любой ошибке из таблицы. Listener поднимается на старте в
`ClusterCtx::build` (вызов из `server/services.rs`). Control API сервера
(`PATCH /control/config`) записывает изменения `[cluster]` в `config.toml` и
отвечает `"requires_restart": true`; применяются они только после рестарта.

Единственный общий секрет — `cluster_psk`; CA и сертификатов для раздачи нет.
Он разделяется контекстами BLAKE3 `derive_key`
(`"outline-proxy cluster shard-obfuscation v1"` для session id,
`"outline-proxy cluster mesh-auth v1"` для keypair интерконнекта), так что один
ключ не используется в двух криптоконтекстах.

Клиент (`outline-ws-rust`): без правок кода. Клиент и так резюмит на тот же
uplink с тем же session id, и путь failover между edge уже есть. При
anycast-входе релей для клиента невидим. Без anycast и без надёжного DNS
пропишите каждый узел отдельным uplink'ом и выставьте `shared_resume = true` на
группе (или в `[outline.load_balancing]`): тогда все uplink'и делят один
resume-scope — имя группы, — и на какой бы edge клиент ни подключился, он
предъявляет один resume id, а сессия переживает смену. Пошаговое развёртывание —
в [`CLUSTER-DEPLOY.ru.md`](CLUSTER-DEPLOY.ru.md).

## Ограничение ресурсов

По инварианту workspace «bounded resources» у каждого долгоживущего
mesh-объекта есть лимит:

| Объект | Лимит | Где |
| --- | --- | --- |
| Исходящие relay-стримы (edge) | 4096 на узел по всем пирам (`MESH_MAX_RELAY_STREAMS`); сверх лимита открытие не удаётся, клиент получает локальную сессию | `server/cluster/mod.rs`, `mesh/peer_pool.rs` |
| Входящие релеимые сессии (home) | 4096 на узел по всем пирам (`MESH_MAX_RELAYED_SESSIONS`); сверх лимита стрим сбрасывается с `Capacity` | `server/cluster/mod.rs` |
| Ожидание кадра `USER` после ack | 5 с (`USER_FRAME_WAIT`) | `server/transport/mesh_relay.rs` |
| Простаивающее mesh-соединение | QUIC idle-timeout 30 с, keep-alive 10 с | `server/cluster/mesh/tls.rs` |
| Запаркованная сессия | TTL и лимиты `[session_resumption]` на home | `[session_resumption]` |
| Зависший релей | `mesh_relay_budget_ms` | `[cluster]` |

Лимита на отдельного пира и LRU-вытеснения relay-стримов нет.

## Открытые риски

1. Mesh data-plane (тот же класс тихой порчи, что в TUN-pump). Покрыт тестами в
   `bins/outline-ss-rust/src/server/tests/resumption/cluster.rs`:
   `cluster_relay_streams_large_transfer_sha256` гонит 16 MiB через релей
   chunked SS-AEAD-потоком и сверяет байт-в-байт по SHA-256 в обе стороны;
   `cluster_session_survives_edge_switch` покрывает park и reattach при смене
   edge. Остаток: подтвердить на боевом трафике (сверка SHA-256 большой передачи
   через живой кластер) и держать `git revert` наготове.
2. Двойной хоп через страны повышает RTT долгих bulk-передач; health-budget
   защищает от зависаний, но не от медленности. Возможное продолжение — дать
   клиенту дозваниваться до home напрямую, когда тот достижим, в обход
   edge-релея. Это client-side-маршрутизация поверх mesh, отдельная фаза.
3. VLESS mux паркуется атомарно, и релей несёт весь мультиплекс по одному
   mesh-стриму. Остаточный риск — слой кадров на home: рассинхронизация потока
   mux-кадров там стоит всего набора (он не перепарковывается), тогда как
   байтовый релей потерял бы только носитель.
4. Downstream-throttle detection на релеимых носителях целиком работает на edge
   (см. выше), поэтому home больше не путает интерконнект с последней милей
   клиента. Остаток: edge не отличит настоящий throttle последней мили от
   клиента, у которого канал сам по себе такой медленный, поэтому пороги детектора —
   эвристика. Функция по умолчанию выключена; включая её, учитывайте порядок
   budget и окна выдержки. Ключ `[padding] throttle_edge_min_bytes_per_sec`
   принадлежал отставному mesh-детектору `THROTTLE_HINT` и ни на что не влияет.
   Он всё ещё принимается (`[padding]` отвергает незнакомые ключи, и удаление
   поля сломало бы загрузку конфигов, где он прописан) и пишет предупреждение
   при старте. Уберите его из конфигов; поле будет удалено в одном из следующих
   релизов.
