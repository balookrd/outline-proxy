# Carrier-padding

*English version: [PADDING.md](PADDING.md)*

Паддинг уровня приложения для носителей WebSocket / XHTTP. Ломает корреляцию по
размеру TLS-записей, на которую опираются классификаторы «proxy-inside-TLS»
(TLS-in-TLS), не добавляя второй прокси-протокол, — та же цель, что у паддинга
AnyTLS, но реализованная внутри уже имеющихся в `outline-proxy` носителей.

## Что скрывает паддинг

Когда проксируемый поток туннелируется внутри TLS (Shadowsocks или VLESS поверх
WebSocket / XHTTP), каждая запись приложения, как правило, ложится в одну внешнюю
TLS-запись. Тогда размер этой записи повторяет размер внутреннего проксируемого
чанка. Пассивный классификатор, который не может читать открытый текст TLS, всё
равно видит последовательность размеров записей и узнаёт проксируемый поток,
вложенный в TLS; эту эвристику, среди прочих, применяет российский ТСПУ. У VLESS
поверх WS / XHTTP та же уязвимость, что у Shadowsocks, поэтому он паддится так же.

Паддинг развязывает эти две величины: каждый проксируемый чанк (зашифрованный
Shadowsocks-чанк или VLESS-кадр) оборачивается в кадр с префиксом длины, чей
хвост — случайное число выбрасываемых байт, так что буфер, передаваемый
TLS-слою, больше не имеет фиксированной связи с переносимой полезной нагрузкой.

## Формат кадра

Каждый кадр — `real_len | pad_len | real | pad`:

| Поле       | Размер           | Значение                                |
|------------|------------------|-----------------------------------------|
| `real_len` | `u16` big-endian | длина реальных проксируемых байт        |
| `pad_len`  | `u16` big-endian | длина pad-хвоста                        |
| `real`     | `real_len` байт  | зашифрованный SS-чанк или VLESS-кадр     |
| `pad`      | `pad_len` байт   | случайные байты, отбрасываются на декоде |

Кодек живёт в `crates/outline-wire/src/padding.rs` и делает только фрейминг, без
RNG и без часов: pad-байты и случайный розыгрыш их длины передаёт вызывающий
транспортный слой, как и у кодека SS2022-заголовка. Декодер (`PaddingDecoder`) —
потоковый автомат: вход может быть разрезан на любой границе байт, потому что
DATA-кадры h2 / h3 не выровнены по границам наших кадров. Кадр с `real_len = 0`
несёт только pad — это форма cover-кадра (см. ниже); декодер ничего из него не
выдаёт.

`real` и `pad` ограничены 65535 байтами (потолок `u16`). Транспорт режет более
крупную запись на чанки не больше этого размера перед фреймингом, и pad несёт
только последний чанк записи, так что одна транспортная запись даёт один
случайный хвост независимо от числа сегментов.

## Гейт: синхронизация конфигом, без согласования

Бита возможностей на проводе нет. Пир с выключенным паддингом никогда не фреймит
свои записи и не декодирует; пир с включённым паддингом скормит обычный
(нефреймированный) поток в декодер и упадёт. Поэтому обе стороны должны включить
паддинг вместе, как и cross-transport session resumption. По умолчанию паддинг
выключен: в потоке байт нет кадров паддинга (нарезка начала сессии на h1/h2 всё
равно делит первые сообщения, но читатель потока видит те же байты), поэтому
сторонние клиенты (Happ, Outline, xray, sing-box) работают, пока оператор не
включит паддинг.

- Сервер, на уровне эндпоинта. Паддинг — атрибут эндпоинта:
  `[[endpoint]] padded = true` помечает один путь носителя как паддированный.
  Фреймятся только соединения на `padded`-эндпоинте; все остальные эндпоинты
  сохраняют чистый провод Shadowsocks / VLESS. `[padding]` хранит только
  параметры схемы (диапазон, cover, jitter, детект троттлинга), а не список
  паддируемых путей. Так один сервер может паддить своих клиентов на одном
  эндпоинте (SS или VLESS) и без изменений обслуживать сторонних клиентов, в том
  числе VLESS-клиенты вроде xray / sing-box, на другом, непаддированном.
- Клиент, глобальный дефолт плюс per-uplink override. Глобальный блок
  `[padding]` задаёт параметры схемы (диапазон, cover, jitter) и дефолтный
  on/off — `enabled`. Каждый `[[outline.uplinks]]` может переопределить его
  через `padding = true` / `padding = false`: дозвон берёт per-uplink значение,
  если оно задано, иначе глобальный `enabled` (та же схема override/fallback, что
  у per-uplink `fingerprint_profile`). Оператор может оставить глобальный дефолт
  выключенным и паддить только аплинки, ведущие на его собственные серверы
  (`padding = true`), либо включить его и исключить конкретный аплинк, например
  VLESS-аплинк к стороннему серверу xray / sing-box, через `padding = false`.
  Паддированный дозвон (и SS, и VLESS, и TCP, и UDP) обязан указывать на
  серверные пути, которые тоже паддятся.

## Cover-трафик

При `cover = true` простаивающее соединение шлёт pad-only cover-кадры
(`real_len = 0`) с интервалом, равномерно выбранным из
`[cover_jitter_min_ms, cover_jitter_max_ms]`, чтобы паузы не было видно по
таймингам. Таймер сбрасывается после каждой реальной записи, поэтому cover-кадры
срабатывают только на простаивающем канале и никогда не перемежаются с живым
трафиком. Клиент шлёт cover на uplink-writer'е, сервер — на downlink-writer'е.
Cover-кадр — бинарный data-кадр, а не WebSocket Ping, поэтому он безопасен на
H3-носителе: он не может эскалировать до connection-level `H3_INTERNAL_ERROR`,
к которому может привести Ping от сервера. Декодер получателя отбрасывает
cover-кадры.

## Форма начала сессии

Первые байты TCP-сессии лучше всего видны классификатору по длинам: рукопожатие
TLS внутри туннеля уходит несколькими записями характерных размеров. Поэтому на
h1 / h2 TCP-сессиях, с паддингом и без, первые сообщения режутся на части в обе
стороны (константы — в `crates/outline-wire/src/early_shape.rs`):

| Параметр | Значение |
|---|---|
| Окно, на сессию | первые 6..=10 сообщений или первые 16..=24 КиБ, что наступит раньше; дальше сессия идёт без нарезки |
| Клиент → сервер | сообщение крупнее 900 Б режется на части по 300..=850 Б |
| Вводные cover-кадры (клиент → сервер, только путь с паддингом) | с вероятностью 1/2 на сессию 1-2 pad-only кадра по 40..=100 Б паддинга перед первым разрезаемым сообщением |
| Сервер → клиент | сообщение крупнее 1500 Б режется на части по 600..=2800 Б |

На XHTTP-носителе в режиме packet-up каждая запись клиента — отдельный POST,
поэтому сообщения не дробятся на новые POST. Вместо этого на `xhttp_h2` тело
каждого POST в окне режется на кадры DATA тех же размеров (байты и
`Content-Length` те же, без cover-кадров); это касается и UDP поверх packet-up
POST, и каждый POST по-прежнему несёт одну датаграмму целиком. `xhttp_h1`
packet-up начало сессии не режет.

На пути с паддингом каждая часть — обычный паддированный кадр со своим случайным
хвостом, так что декодер получателя не меняется. На пути без паддинга каждая
часть — обычное сообщение `Binary` без обёртки: получатели читают TCP как поток,
байты те же, меняются только границы сообщений. Ключей конфига нет: нарезка
включена на каждой h1 / h2 TCP-сессии; cover-кадры требуют паддинга.

### Что действует независимо от паддинга

Нарезка начала сессии (сама нарезка, не cover-кадры) паддинга не требует. Ещё
пять правок убирают маркеры самого носителя и работают всегда:

- h2: одна TLS-запись на кадр. h2 IO клиента пробрасывает векторные записи,
  поэтому заголовок кадра и его тело уходят одной записью, а не двумя.
- h2: сообщения сервера помещаются в одну запись. На h2-носителях сервер
  держит каждое TCP downlink-сообщение (SS, VLESS, VLESS mux, replay при resume)
  в пределах одного кадра DATA не больше 16375 Б, поэтому кадр и его 9-байтный
  заголовок уходят одной TLS-записью (пар записей 16401 + 26 на больших
  загрузках больше нет). Ограничено само чтение из апстрима, поэтому мелкого
  остатка, который ушёл бы вместе со следующим полным кадром, не бывает.
  UDP-датаграммы и cover-кадры не режутся (они мелкие); диапазон паддинга, при
  котором на данные остаётся меньше 1 КиБ (`max_bytes` больше ~15 КиБ),
  отключает лимит.
- h2: uplink-сообщения клиента помещаются в одну запись. Зеркало серверного
  лимита: на `ws_h2` и XHTTP stream-one поверх h2 клиент режет uplink-сообщение
  (SS или VLESS, склеенное до 256 КиБ), которое не влезает в один кадр DATA
  не больше 16375 Б с учётом WS-заголовка и паддинга на максимальном паде, на
  равные куски, которые влезают. Поэтому и большие выгрузки не дают пар записей
  16401 + 26. Так же режется хвост большой первой записи, вышедший за байтовый
  бюджет окна нарезки. Не на h1, h3 и XHTTP packet-up (там каждая запись —
  отдельный POST со своей нарезкой на кадры DATA).
- Заголовок ответа VLESS вместе с первыми данными. Сервер ни на одном пути
  не шлёт 2-байтный заголовок ответа `[VERSION, 0x00]` (21 Б с паддингом)
  отдельным сообщением. Свежая TCP-сессия, resume без кадров управления,
  ретранслируемая сессия (edge кластера) и VLESS-UDP (свежий, возобновлённый,
  ретранслируемый) шлют его вместе с первыми байтами от апстрима или с первым
  ответным пакетом; сессия VLESS-mux — перед первым downlink-кадром mux,
  какое бы sub-соединение его ни отправило. Resume, запросивший кадры
  Ack-Prefix v1 / replay v2, шлёт заголовок в одном сообщении с этими кадрами
  (клиент ждёт их, прежде чем продолжить uplink, поэтому ждать данных от
  апстрима им нельзя). В кольцо replay v2 заголовок не попадает.
- Заголовок запроса SS2022 вместе с первыми данными. На носителях h1 / h2
  клиент придерживает заголовок до 50 мс (`SS2022_HEADER_HOLD`), чтобы он ушёл
  вместе с первыми данными. Не на h3 (там нет формы TLS-записи, которую нужно
  прятать, а задержка лишь тормозила бы протоколы, где первым говорит сервер) и
  не в пробах аплинков, которым она исказила бы замер задержки.

### Вне рамок

h3 (у QUIC своя пакетизация), UDP и тайминги: нарезка меняет только размеры, но
не задержки между сообщениями (кроме cover-кадров).

### Совместимость

Формат на проводе не меняется: части — обычные кадры паддинга (на пути без
паддинга — обычные сообщения `Binary`), а склеенные записи — обычный поток байт.
Старые пиры работают в обе стороны; свою сторону они не режут.

## Покрытые носители

Паддинг работает на уровне `Message`, общем для всех носителей WS / XHTTP,
поэтому один механизм покрывает их все:

- SS поверх WebSocket: h1, h2, h3 (WebSocket поверх HTTP/3, RFC 9220).
- SS поверх XHTTP: h1, h2, h3.
- SS-UDP поверх WebSocket / XHTTP: паддится по датаграмме (один кадр на один
  зашифрованный Shadowsocks-пакет); см. [UDP](#udp) ниже.
- VLESS поверх WebSocket: h1, h2, h3.
- VLESS поверх XHTTP: h1, h2, h3.
- VLESS-UDP поверх WebSocket: паддится по датаграмме (один кадр на один пакет);
  см. [UDP](#udp) ниже.

### UDP

Все UDP-носители паддятся одинаково, и SS-UDP, и VLESS-UDP. Каждая датаграмма
оборачивается ровно в один кадр (кодек никогда не разрезает пакет на несколько
датаграмм, поэтому границы пакетов сохраняются), а получатель прогоняет каждую
входящую датаграмму через потоковый декодер до парсинга SS / VLESS-слоем.
Cover-кадр (`real_len = 0`) на простаивающем downlink декодируется в пустоту и
отбрасывается.

Правило «одна датаграмма — один кадр» работает, только пока сам носитель
сохраняет границы пакетов: на WebSocket это так, на XHTTP — нет, там нагрузка —
байтовый HTTP-поток. Поэтому SS-UDP поверх XHTTP дополнительно оборачивает
датаграмму (паддированную или голую) в собственную запись с префиксом длины;
паддинг лежит внутри этой записи, и обе функции работают в любой комбинации.
См. [фрейминг записей SS-UDP поверх XHTTP](XHTTP-UDP-RECORDS.ru.md).

- VLESS-UDP мультиплексирует TCP и UDP на одном пути (различая их по
  command-байту внутри первого кадра), поэтому сервер не может отличить ноги
  до чтения данных. Значит, паддированный VLESS-путь обязан паддить и UDP-ногу.
- Split SS разводит TCP и UDP по разным эндпоинтам (`ws_ss_tcp` /
  `ws_ss_udp` либо `xhttp_ss_tcp` / `xhttp_ss_udp`). Поставьте `padded = true`
  на оба, чтобы паддить весь аплинк. Клиентский per-uplink переключатель
  работает по принципу «всё или ничего» (паддированный аплинк фреймит каждую
  отправляемую датаграмму), поэтому паддированный SS-аплинк ожидает, что оба его
  серверных эндпоинта, TCP и UDP, тоже паддятся.
- Combined SS (`ws_ss` / `xhttp_ss`) кладёт TCP и UDP на один эндпоинт,
  разделяя их по скрытому биту в токене (WS) / session id (XHTTP), который
  сервер декодирует на этапе upgrade. Обе ноги резолвят один эндпоинт, поэтому
  `padded = true` на combined-эндпоинте паддит обе ноги: UDP-нога
  `run_udp_relay` резолвит ту же per-path-схему, что и TCP-нога
  `run_tcp_relay`.

## Детект downstream-троттлинга (сервер → переключение uplink клиента)

Паддированный носитель может следить за собственной пропускной способностью и,
когда провайдер начинает шейпить путь к клиенту (например, VPS троттлит трафик в
сторону России), сообщить клиенту, что пора уйти на другой uplink. Покрываются
TCP- и UDP-носители обоих транспортов: VLESS и SS поверх WS / XHTTP. Для
QUIC-трафика (HTTP/3), например YouTube, который идёт по UDP-носителю, троттлинг
только по UDP детектится на UDP-носителе и переключает UDP-ногу того же uplink.
Непаддированный провод не мониторится.

Сервер измеряет для каждого носителя скорость, с которой тянет данные из
интернета (inbound, предназначенные клиенту), и скорость, с которой отдаёт их
носителю (outbound), а также наличие backlog отправки. Когда inbound опережает
outbound в `throttle_ratio_percent` (по умолчанию 200, то есть 2×) при наличии
backlog `throttle_sustain_windows` окон подряд, а inbound не ниже
`throttle_min_bytes_per_sec`, сервер шлёт один control cover-кадр — кадр
`real_len = 0`, pad которого начинается с magic-префикса `OCTL`. Пир, который не
реагирует на сигнал, отбрасывает его как обычный cover-кадр. Клиент с
`react_to_throttle = true` распознаёт сигнал, накладывает на текущий uplink
временный penalty и cooldown, и health-weighted selection уводит трафик на другой
uplink. Uplink возвращается в выбор, как только его проба снова проходит.

Поскольку сигнал едет на cover-кадре, получить его могут только ваши клиенты на
эндпоинте с `padded = true`; сторонние (непаддированные) SS-клиенты и
непаддированные эндпоинты никогда не мониторятся. И детект (сервер), и реакция
(клиент) по умолчанию выключены. Переключение uplink помогает, только если
другой uplink идёт по другому сетевому пути (другой сервер / VPS); это зависит
от раскладки аплинков оператора, а не от кода. Сервер не всегда может отличить
троттлинг провайдера от медленной последней мили клиента; пороги ratio, backlog,
sustain и минимальной скорости ограничивают ложные срабатывания, настраивайте их
под свой трафик.

## Конфигурация

### Сервер (`outline-ss-rust`)

```toml
# Пометьте эндпоинты, которые нужно паддить, — SS-TCP, SS-UDP, combined
# SS-эндпоинт и VLESS используют один и тот же атрибут `padded`; поставьте
# его и на SS-UDP-эндпоинт, чтобы западдить UDP-ногу единообразно.
[[endpoint]]
path = "/SECRET/tcp"
kind = "ws_ss_tcp"
padded = true

[[endpoint]]
path = "/SECRET/udp"
kind = "ws_ss_udp"
padded = true

[[endpoint]]
path = "/SECRET/vless"
kind = "ws_vless"
padded = true

# Только параметры — эндпоинт паддится, если у него самого стоит
# `padded = true` (выше), а не по ключу в этом блоке.
[padding]
min_bytes = 0                            # мин. pad на кадр
max_bytes = 256                          # макс. pad на кадр (0 = без фрейминга)
cover = false                            # idle pad-only cover-кадры (downlink)
cover_jitter_min_ms = 250                # нижняя граница idle-паузы перед cover
cover_jitter_max_ms = 1500               # верхняя граница

# Детект downstream-троттлинга (паддированные SS/VLESS, TCP+UDP, WS/XHTTP). По умолчанию выкл.
throttle_detect_enabled = false          # следить за throughput, толкать клиента сменить uplink
throttle_ratio_percent = 200             # сигнал когда inbound >= 2x outbound (200 = 2x)
throttle_window_secs = 1                 # окно семплирования
throttle_sustain_windows = 5             # сколько окон подряд над порогом до сигнала
throttle_min_bytes_per_sec = 1000000     # порог inbound (~8 Мбит/с); ниже — не actionable
throttle_signal_cooldown_secs = 30       # мин. пауза между сигналами на одном носителе
```

`max_bytes` меньше `min_bytes` поднимается до `min_bytes`, а
`cover_jitter_max_ms` меньше `cover_jitter_min_ms` — до минимума.

Устарело: `throttle_edge_min_bytes_per_sec` задавал порог stall-детектору на
edge кластера, а тот удалён вместе с v4-релеем mesh (см.
[`CLUSTER.ru.md`](CLUSTER.ru.md)). Ключ по-прежнему принимается и игнорируется:
секция `[padding]` отвергает незнакомые ключи, поэтому удаление ключа из схемы
не дало бы загрузиться конфигу, где он ещё прописан. Конфиг с этим ключом пишет
при старте `ignoring retired padding.throttle_edge_min_bytes_per_sec`. Удалите
ключ; само поле уйдёт в следующем релизе.

### Клиент (`outline-ws-rust`)

```toml
[padding]
enabled = false              # глобальный дефолт (per-uplink `padding` его переопределяет)
min_bytes = 0
max_bytes = 256              # макс. pad на кадр (0 = без фрейминга)
cover = false                # idle pad-only cover-кадры (uplink)
cover_jitter_min_ms = 250
cover_jitter_max_ms = 1500
react_to_throttle = false    # реагировать на сигнал троттлинга от сервера (penalty + смена uplink)

# Паддить только свой сервер, даже при выключенном глобальном дефолте:
[[outline.uplinks]]
name = "mine"
# … vless_ws_url / tcp_ws_url / и т.п. …
padding = true               # override: паддить дайлы этого аплинка

# Оставить сторонний VLESS-аплинк чистым, даже при включённом глобальном дефолте:
[[outline.uplinks]]
name = "thirdparty"
# … vless_ws_url на сервер xray / sing-box …
padding = false              # override: никогда не паддить этот аплинк
```

Блок `[padding]` задаёт параметры схемы и глобальный дефолт (`enabled`); ключ
`padding` каждого аплинка переопределяет on/off для этого аплинка (если ключа
нет, действует глобальный дефолт). С диапазоном по умолчанию `0..256` каждая
паддированная запись вырастает на 4-байтный заголовок плюс 0..256 байт паддинга.
Поднимите `max_bytes` для более широкого распределения размеров ценой большего
трафика. Включайте `cover` на обеих сторонах вместе, если важен анализ таймингов
простоя.

## Раскатка и накладные расходы

- Включайте паддинг на обеих сторонах одним изменением. Наполовину раскатанная
  пара (одна сторона паддит, другая нет) рвёт затронутые сессии, пока обе не
  совпадут.
- Паддинг добавляет 4-байтный заголовок плюс pad-хвост на запись. Он не меняет
  согласованный транспорт, ALPN и TLS-рукопожатие.
- Паддинг читается из стартового конфига. Изменение `[padding]` требует
  перезапуска затронутого бинаря: hot-reload не поддерживается.
