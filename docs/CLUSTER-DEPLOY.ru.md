# Runbook развёртывания кластера

*English version: [CLUSTER-DEPLOY.md](CLUSTER-DEPLOY.md)*

Как превратить два и более отдельных сервера `outline-ss-rust` в mesh-кластер,
в котором клиентская сессия переживает смену edge. Дизайн — в
[`CLUSTER.ru.md`](CLUSTER.ru.md).

## 0. Требования

- Два и более серверных узла. В кластере из одного узла релеить некуда. Обычно
  узлы в разных странах.
- Одна сборка на всех узлах. У mesh-протокола одна версия (`OPEN_VERSION = 5` в
  `server/cluster/mesh/frame.rs`); пиру, который её не знает, отказывают на
  установлении релея, до всяких данных. Поэтому смешанный парк теряет
  непрерывность сессий, а не трафик: такие сессии обслуживаются локально на edge
  вместо resume на своём home. Порядок обновления не важен, но надолго парк
  смешанным не оставляйте.
- UDP между узлами. Mesh — это QUIC поверх UDP (см. §4).

## 1. Топология и план shard'ов

Каждый узел одновременно edge (принимает клиентов) и home (владеет своими
сессиями и принимает релеи с других edge). Присвойте каждому узлу уникальный
`shard_id` в диапазоне `0..15`:

| Узел | shard_id | публичный вход (WS/H3/XHTTP) | mesh-адрес (узел-узел) |
| --- | --- | --- | --- |
| A (напр. DE) | 0 | без изменений | `<A_ip>:9443` |
| B (напр. NL) | 1 | без изменений | `<B_ip>:9443` |

`<A_ip>` и `<B_ip>` — IP-адреса, по которым узлы достают друг друга. Порт 9443 —
значение, принятое в этом runbook; значения по умолчанию нет.

## 2. Общий секрет

Сгенерируйте один секрет на весь кластер, одинаковый на каждом узле:

```bash
openssl rand -base64 32
```

Из него через BLAKE3 `derive_key` выводятся два независимых ключа: ключ
shard-обфускации session id и mesh-auth keypair. CA и сертификатов для раздачи
нет. Храните его как любой секрет, вне git. С утёкшим PSK можно выдать себя за
mesh-пира в будущих handshake'ах; записанный прошлый трафик защищён эфемерными
QUIC-ключами.

## 3. Серверный конфиг `[cluster]`

`peers` — полная карта shard → mesh-адрес всех узлов. Свою запись узел
пропускает, поэтому один и тот же блок `peers` можно копировать на все узлы.

Узел A (`shard_id = 0`):

```toml
[cluster]
enabled = true
shard_id = 0
cluster_psk = "<тот же base64 на каждом узле>"
mesh_listen = "[::]:9443"          # QUIC (UDP) слушатель входящих релеев
mesh_relay_budget_ms = 4000        # релей, стоящий дольше, рвём
peers = [
  { shard = 0, addr = "<A_ip>:9443" },   # свой shard, пропускается
  { shard = 1, addr = "<B_ip>:9443" },
]
```

Узел B: то же самое, но `shard_id = 1`.

Проверка на старте (`config/loader.rs`, `resolve_cluster`) прерывает запуск,
если: `shard_id` нет или `shard_id >= 16`; `cluster_psk` нет, он не base64 или
пустой; `mesh_listen` или `addr` пира — не адрес сокета (`IP:port`; имена хостов
не принимаются); в `peers` повторяется shard. При `enabled = false` или без
секции сервер работает standalone: обычные случайные session id, mesh-listener
не поднимается. Справочная таблица ключей — в
[`CLUSTER.ru.md` § Конфигурация](CLUSTER.ru.md#конфигурация).

### 3a. Пути и креды — свои у каждого узла; общие только имена пользователей

Крипту клиента терминирует edge и релеит plaintext, поэтому по релеимой сессии
на home ничего не резолвится: ни путь, ни таблица маршрутов, ни ключ
пользователя. Пути и креды поэтому у каждого узла свои. Узел A может
обслуживать `/tcp` там, где узел B обслуживает `/a1b2`, с разными `password` /
`method` / `vless_id` у каждого пользователя, и релеи между ними работают. Смена
кредов или путей узла не требует согласования с другими узлами.

Между узлами должно совпадать имя пользователя: по нему ключуются парковки.
Home сверяет имя, заверенное edge, с владельцем парковки, прежде чем отдать
сессию. Если `carol` на двух узлах означает разных людей, resume между ними
отвергается (`outline_ss_mesh_relay_rejected_total{reason="unknown_user"}`), и
это задуманное поведение. Прокси-протоколы совпадать не обязаны: парковка,
сделанная под SS, отдаётся VLESS-носителю той же учётки и наоборот. Это держит
сессии на аплинке, который перевыбирает активный wire на смешанном
SS/VLESS-наборе (`shuffle_wires`), и там идентичность несёт только имя
пользователя.

> Прежние версии (wire v4 и раньше, где расшифровывал home) требовали, чтобы
> пути и креды пользователей совпадали байт-в-байт на всех узлах; любая
> асимметрия давала молчаливую чёрную дыру — релей в маршрут без ключей. Этого
> требования больше нет, как и причины отказа `no_route`, которая о нём
> сообщала. Сверять конфиги между узлами больше не нужно.

Сервер сам проверяет одно: что имя способно пересечь mesh. Оно едет в кадре
`USER` с однобайтовой длиной, потолок — 64 байта (`MAX_USER_LEN`). При
`enabled = true` пустое имя или имя длиннее 64 байт прерывает старт с ошибкой,
в которой назван ключ.

Проверяется всё, что может попасть на провод: на mesh заверяется эффективная
учётная метка, поэтому ключ `[users.aliases]` становится именем на mesh, когда
исходный IP клиента попадает в подсеть алиаса. Проверяются и id из `[[users]]`,
и имена алиасов. Больше ничего в `[[users]]` не сверяется, а сервер без
`enabled = true` не проверяется вовсе.

После раскатки следите за
`outline_ss_mesh_relay_rejected_total{reason="unknown_user"}`. Ненулевая
скорость означает, что владелец парковки — не то имя, которое заверил edge.
Причины: имена пользователей в кластере расходятся; инцидент безопасности;
пользователь с `[users.aliases]`, подключившийся из подходящей подсети (SS-TCP
паркуется под базовым id, а mesh заверяет эффективную метку, и этот случай даёт
расхождение при корректном конфиге).

## 4. Сеть и firewall

- Откройте mesh-порт (в этом runbook — 9443/udp) между узлами. Это QUIC, то
  есть UDP, а не TCP.
- Ограничьте mesh-порт IP-адресами пиров. Mutual pin из PSK и так отсекает хосты
  без PSK; IP-фильтр не даёт им дойти даже до QUIC-handshake.
- Публичный вход (WS/H3/XHTTP) не меняется.

## 5. Клиент: подключение к кластеру

Правок кода клиенту не нужно, но от способа адресации кластера зависит,
выживут ли сессии. Клиент кэширует resume id по resume-scope; сессия переживает
смену edge, только если клиент предъявляет один и тот же resume id тому edge,
куда попал. Три способа, по убыванию предпочтения:

### 5a. Anycast

Один IP, анонсируемый по BGP со всех узлов. Клиент всегда подключается к одному
адресу, сеть направляет его на ближайший живой узел. Один scope, один resume id,
в клиентском конфиге ничего особого.

### 5b. Один DNS-hostname

Один hostname с несколькими A/AAAA-записями. Работает, если у клиента один
uplink-URL на этот hostname (scope — uplink, а не resolved IP). Ломается при
нестабильном резолвинге.

### 5c. Явные uplink'и с `shared_resume`

Для случая без anycast и без надёжного DNS. Пропишите каждый узел отдельным
uplink'ом и пометьте группу так, чтобы все uplink'и делили один resume-scope
(имя группы). На какой бы edge ни подключился клиентский балансировщик, он
предъявит один resume id, edge отрелеит сессию на её home, и сессия выживет.

Форма без именованных групп:

```toml
[[outline.uplinks]]
name = "edge-de"
transport = "ss"                   # или vless; см. UPLINK-CONFIGURATIONS.ru.md
# ...url / cipher / password / mode для узла A...

[[outline.uplinks]]
name = "edge-nl"
transport = "ss"
# ...то же для узла B...

[outline.load_balancing]
shared_resume = true               # все uplink'и выше делят один resume id
```

Секции `[[uplinks]]` / `[load_balancing]` на верхнем уровне файла по-прежнему
загружаются, но пишут предупреждение об устаревании (`config/compat.rs`). С
именованными группами (`[[uplink_group]]`) выставьте `shared_resume = true` на
группе, чьи uplink'и — edge'и кластера.

`shared_resume` по умолчанию `false`. Включайте его только для группы, чьи
uplink'и — edge'и одного mesh-кластера. В группе независимых серверов общий
resume id на чужих home всегда давал бы miss.

Общий scope охватывает и UDP, и TCP: при `shared_resume = true` сессии SS-UDP и
VLESS-UDP предъявляют групповой resume id с shard и мигрируют при смене edge так
же, как TCP (релеятся на свой home-shard). См. «Cross-node миграция UDP» в
[`UPLINK-CONFIGURATIONS.ru.md`](../bins/outline-ws-rust/docs/UPLINK-CONFIGURATIONS.ru.md).

## 6. Порядок раскатки

1. Сгенерируйте PSK и подготовьте блоки `[cluster]`.
2. Откройте mesh-порт между узлами.
3. Раскатайте новый бинарь и конфиг на все узлы, по одному узлу за раз. Узел на
   старом бинаре обслуживает своих клиентов standalone; его релеи отвергаются, и
   клиент получает свежую локальную сессию.
4. Направьте клиента на кластер (§5).
5. Выполните проверки из §7.

## 7. Проверка

- Старт: сервис `active`, в логе нет ошибок проверки конфига. Проверьте
  mesh-listener на каждом узле:

  ```bash
  sudo ss -lunp | grep 9443
  ```

  Узел, который не стартует с ошибкой про лимит mesh-имени пользователя, имеет
  пустое или длиннее 64 байт имя — id в `[[users]]` либо ключ в
  `[users.aliases]`; ошибка называет, какой именно (§3a). Исправляйте имя, а не
  конфиг кластера.
- Mesh-связность: с тестового клиента подключитесь к одному узлу с resume id,
  который декодируется в shard другого узла (при переходе клиента между edge
  это происходит само). Сессия обслуживается, upstream не пересоздаётся. Если
  home недоступен, edge выдаёт клиенту свежую сессию, не раскрывая топологию.
- Выживание: начните сессию с идущей загрузкой, принудительно переведите клиента
  на другой узел (при §5c — выключите или остановите активный uplink) и
  убедитесь, что загрузка продолжается.
- Метрики на `/metrics` каждого узла (и в Grafana-дашборде ss-rust, ряд
  Cluster Mesh):
  - Рост `outline_ss_mesh_relay_opened_total{outcome="ok"}`: edge'и релеят
    cross-shard-сессии на свои home. Рост `{outcome="fail"}`: OPEN не дошёл до
    home (нет пира для этого shard, не удался дозвон — пир лежит, mesh-UDP-порт
    закрыт или PSK не совпадает, — либо сам edge упёрся в свой исходящий лимит
    relay-стримов), и edge переходит на свежие локальные сессии.
    `{outcome="refused"}`: OPEN дошёл до home, но пригодного ответа не получил.
    Обычно это «нет парковки под этим id», но также home на лимите релеев или
    пир на отставной wire-версии, так что во время rolling upgrade всплеск здесь
    ожидаем.
  - `outline_ss_mesh_relay_outcome_total{outcome,close}` на home — первое, что
    надо смотреть: это ответ на вопрос «работает ли кластерный релей», которого
    одни байтовые счётчики не давали (на проде однажды из-за этого не заметили
    релей, не работавший вообще). Ненулевой `{outcome="hit"}` означает, что
    запаркованные сессии находятся и сплайсятся; полезное отношение —
    `hit`/`miss`. Исход записывается, когда splice закончился, а не когда его
    допустили, поэтому релеи в работе видны в `outline_ss_mesh_relay_active`, а
    обслуженные этим home стримы сходятся как
    `sum(outcome_total) + outline_ss_mesh_relay_active`. Метка `close` говорит,
    чем закончился hit: `client_done` (клиент edge закончил, upstream
    полузакрыт) или `carrier_ended` (edge только сменил носитель, сессия
    вернулась в реестр). Если `close` всегда `carrier_ended` и `client_done` нет
    совсем, edge'и не отправляют close-intent, и парковки висят до TTL.
    `{outcome="unusable"}` — сбой: парковка нашлась и была потреблена, но
    сплайснуть её не удалось, поэтому она уничтожена, а сессия клиента
    закончилась. Ожидаемое значение — ноль; парная причина в
    `outline_ss_mesh_relay_rejected_total` (`park_identity` или
    `park_incomplete`) называет форму. `{outcome="error"}` — установление
    сорвалось до того, как была найдена какая-либо парковка.
  - `outline_ss_mesh_relay_active` — сколько релеев home обслуживает сейчас.
    Ноль на простаивающем кластере — норма: mesh-стримы открываются по
    требованию. Смотрите также `outline_ss_orphan_resume_hit_total` на home: он
    растёт, когда home переподключает запаркованный upstream для клиента,
    пришедшего через другой edge.
  - Рост `outline_ss_mesh_relay_rejected_total{reason="capacity"}`: home упёрся
    в лимит 4096 одновременных релеимых сессий и отвергает новые relay-стримы;
    edge'и переходят на свежие локальные сессии. Ожидаемое значение — ноль;
    устойчивый рост означает, что на один home приходит больше одновременных
    релеимых сессий, чем позволяет лимит.
  - `outline_ss_mesh_relay_rejected_total{reason="no_session"}` — штатный
    отказ: у home нет парковки под этим resume id (истекла либо этот home её не
    выдавал), в том числе парковки, которая была на момент ack и истекла до
    прихода кадра `USER`. Edge'и считают то же событие как
    `outline_ss_mesh_relay_opened_total{outcome="refused"}`. У здорового
    кластера это ровная невысокая скорость; доля около 100% от открытий означает
    проблему до релея.
  - Рост `outline_ss_mesh_relay_rejected_total{reason="unknown_user"}`: владелец
    парковки под этим id — не то имя, которое заверил edge (§3a). Обычно имена
    пользователей в кластере расходятся; бывает и пользователь с
    `[users.aliases]` из подходящей подсети — расхождение при корректном
    конфиге. Ожидаемое значение — ноль. `reason="protocol_mismatch"` тоже
    должен быть нулём, но означает другое: байтовая парковка переходит между
    протоколами свободно, и под этой причиной остаются только датаграммные и
    mux-парковки, запрошенные под чужим протоколом. Проверка формы делает это
    недостижимым, так что ненулевое значение означает поддельного пира или узкое
    окно резервации.
  - `outline_ss_orphan_resume_cross_protocol_total{parked,resumed}` считает
    состоявшиеся переходы на узле-владельце парковки. Ненулевое значение
    нормально везде, где аплинк перевыбирает активный wire на смешанном
    SS/VLESS-наборе; серия показывает, какая доля непрерывности на этом
    держится.
  - `outline_ss_mesh_relay_rejected_total{reason="park_shape"}` — ожидаемое
    значение, не сбой: SS-UDP-парковка под VLESS-resume-id (и наоборот) — форма,
    которую релей запросить не может, поэтому релей отвергается без потребления
    парковки, а клиента обслуживают локально. VLESS-команда, которой нужна
    другая форма, чем у парковки, сюда не попадает: home называет форму в ack, и
    edge освобождает релей, ничего не потребив.
  - Остальные причины должны стоять на нуле, каждая означает свой сбой:
    `bad_setup` — непригодно само установление (OPEN, чьи framing и протокол не
    называют ни одной формы парковки, либо подтверждённый пир, чей кадр `USER`
    пришёл битым или не пришёл за 5 с), то есть старая сборка или поддельный
    пир; `framing_mismatch` — парковка под этим id не того вида, который нужен
    подтверждённой форме, это может дать только узкое окно резервации (парковку
    кладут обратно нетронутой, непрерывность клиента сохраняется);
    `park_identity` — у SS-UDP-парковки нет NAT-ключа пользователя, которого
    заверил edge, то есть нет идентичности, под которой маршрутизировать её
    датаграммы.
  - Трафик через mesh (сколько данных идёт, а не сколько релеев открыто):
    `outline_ss_mesh_bytes_total{role,direction,transport}` и
    `outline_ss_mesh_datagrams_total{role,direction}`. `role="edge"` — трафик,
    который узел отправляет в кластер; `role="home"` — который он обслуживает для
    чужих edge, та же релеимая сессия с другого конца. Ноль на обоих — через mesh
    трафик не идёт (все сессии локальны). Устойчивый `direction="up"` при
    `direction="down"`, стоящем на нуле, означает, что релеимый uplink доходит до
    home, который ничего не отвечает; проверьте upstream, к которому
    подключается home. Панели: Mesh Throughput — edge (into cluster), Mesh
    Throughput — home (from cluster), Mesh Datagram Rate (SS-UDP).
  - Удалены: `outline_ss_mesh_throttle_hints_received_total{outcome}`,
    `outline_ss_mesh_control_datagram_errors_total` и панель Mesh Throttle Hints
    & Control Errors. Throttle-детекция локальна для edge, а control-датаграмм
    mesh не носит. Если дашборд форкали, удалите панель и у себя.
  - На клиенте (дашборд ws-rust, ряд Cluster / Soft-switch):
    `outline_ws_soft_switch_total{outcome}` считает операторские
    soft-switch-миграции, на здоровом переключении в основном `migrated`;
    `outline_ws_resume_lookup_total{transport,scope,result}` с
    `scope="group",result="hit"` — cross-node-resume, предъявленный новому edge.
- Целостность на боевом трафике: тесты покрывают data-plane, но не боевой
  трафик. Скачайте большой файл через кластер и сверьте его sha256 с
  оригиналом; риск — тихая порча или переупорядочивание, как в TUN-pump. Первые
  дни держите `git revert` наготове.

## 8. Откат

- Выключить кластер: `enabled = false` в `[cluster]` (или удалить секцию) и
  рестарт. Узел снова standalone: обычные случайные session id, mesh-listener не
  поднимается. Клиенты продолжают работать и получают свежие сессии. На клиенте
  уберите `shared_resume` или направьте его на один узел.
- Удалить код: revert кластерных коммитов и пересборка. Для простого выключения
  не нужно: сервер без `[cluster] enabled = true` mesh-код не выполняет.

## 9. Известные ограничения

- RTT двойного хопа: хоп edge → home между странами добавляет задержку длинным
  bulk-передачам. Health-budget ловит зависания, а не медленность.
- Throttle-детекция: на старте держите `[padding] throttle_detect_enabled = false`.
  Она работает на edge, который видит последнюю милю клиента, но её пороги —
  эвристика (см. `CLUSTER.ru.md`).
- Мигрируют сессии всех видов, включая VLESS-UDP и VLESS-mux. Команда, которой
  нужна форма, которой у home нет, получает свежую локальную сессию на этом узле
  (без cross-edge resume для этого носителя), а home оставляет парковку
  нетронутой для носителя, который может её использовать.
  `reason="park_incomplete"` — отказ для mux: запаркованный набор без
  sub-connection отвергается целиком, а не сплайсится наполовину. Ожидаемое
  значение — ноль.
- Rolling upgrade стоит непрерывности, а не трафика. Wire-версия mesh одна, и
  узел на старой сборке получает отказ на установлении релея; такой edge
  обслуживает клиента свежей локальной сессией. Порядок обновления не важен, но
  пока парк смешанный, ожидайте всплеск
  `outline_ss_mesh_relay_opened_total{outcome="refused"}` на edge'ах.
