# Server mesh cluster (anycast ingress + shard relay to home)

*Русская версия: [CLUSTER.ru.md](CLUSTER.ru.md)*

This document describes how several `outline-ss-rust` servers act as one
cluster: an `outline-ws-rust` client may enter through any server, while a
session stays pinned to its home server. A server that is not the session's home
(the edge) terminates the client's crypto itself and forwards the application
plaintext to the home over a QUIC mesh link, routed by a shard id embedded in
the session id. If the home is unreachable or the mesh stalls, the client gets a
fresh session, which is what a standalone server does on a resume miss.

Scope: VLESS and combined-SS carriers. Split SS is not covered by the cluster.
Deployment steps are in [`CLUSTER-DEPLOY.md`](CLUSTER-DEPLOY.md).

## Why the session itself never moves

The parked state on a server is a live upstream connection: an established TCP
socket to the target with its kernel sequence numbers, source address and
connection state (`ParkedTcp`), or a bound `UdpSocket`
(`ParkedVlessUdpSingle`). None of that can be serialized and recreated on a
different machine. So the session stays on the home server, and the carrier
(the client-facing WebSocket / HTTP/3 transport) is what becomes anycast: it
may land on any edge, which relays the bytes back to home. To the client this
looks like "park on server A, unpark on server B"; physically the state lived
on home the whole time.

## Roles

- home — the server that owns a session: the upstream connection to the target
  (or its NAT entries) and the resumption parking (`OrphanRegistry`). Chosen
  once, at first connect, and fixed for the life of the session. It holds no
  crypto state for a relayed session, only for the clients it serves directly.
- edge — the server that terminated the client carrier, and with it the
  client's crypto. It may be the home (everything is local) or a different
  server (it relays to home).
- mesh — the QUIC link edge → home that carries the application plaintext
  inside a mutually authenticated TLS 1.3 connection.
- shard id — a 4-bit home identifier embedded in the session id.

## Shard id in the session id

A resumption `SessionId` is 16 bytes, generated by the home on the first
handshake and returned in `X-Outline-Session` (HTTP/WS) or VLESS addon `0x10`.
On a server without `[cluster] enabled = true` it is plain random bytes. A
clustered server encodes its shard into it
(`crates/outline-wire/src/cluster.rs`, `encode_session_id` /
`decode_shard`):

```
[ seed: 8 bytes (random, in the clear) | payload: 8 bytes (XOR keystream) ]
                                          payload[0] high nibble = shard id
keystream = BLAKE3-keyed(obfuscation_key, seed), truncated to 8 bytes
obfuscation_key = BLAKE3 derive_key("outline-proxy cluster shard-obfuscation v1", cluster_psk)
```

- 4 bits give up to 16 servers (`MAX_SHARDS`). The remaining entropy is 124
  bits: 64 in the seed plus 60 in the payload.
- The shard is a routing hint, not a secret: a forged shard only sends the edge
  to the wrong home, which answers with a resume miss. Its structure must still
  not be visible to a DPI observer, so the payload is XORed with a keystream
  under a key derived from the cluster-wide `cluster_psk`. Any cluster member
  re-derives the keystream from the seed and reads the shard in O(1); there is
  no shared routing table for ids.
- Any 16-byte input decodes to some shard, so a resume id from a non-clustered
  server or a client bug lands on some home and misses there.

The combined-SS `SsPathKind` (TCP vs UDP) bit lives in the XHTTP URL / WS
`/{token}` segment, not in the 16-byte resume id, so it does not use these bits.

## Routing decision on the edge

The edge must know the shard before any SS/VLESS payload. The shard comes in
carrier metadata that arrives ahead of the body:

| Carrier | Where the shard is | When visible |
| --- | --- | --- |
| WS / H3 / XHTTP resume | `X-Outline-Resume: <hex>` header | at upgrade, before body |
| First connect (no resume) | — | edge is home: handle locally, mint a session id with `shard = self` |

```
            client (ws-rust)
          resume? X-Outline-Resume
                      │ carrier (WS/H3)
                      ▼
                  ┌────────┐
                  │  EDGE  │  decode_shard(session_id)
                  └───┬────┘
        shard==self   │   shard!=self
        ┌─────────────┘└──────────────┐
        ▼                              ▼
  LOCAL (as today)            MESH RELAY to home[shard]
  accept→crypto→park          terminate carrier AND crypto,
  →upstream→target            stream plaintext over mesh QUIC
                                       │
                                       ▼
                              HOME[shard]
                              resume the park / re-park
                              upstream → target   (state lives only here)
```

First connect picks the home. A client with no resume id lands on some edge,
which handles it locally and returns a session id carrying its own shard. All
later resumes of that session, through any edge, point back to that home. The
home is therefore the server where the client first established the session.

## Mesh transport

There is one relay boundary, the same on every carrier: the edge terminates the
client's crypto and relays application plaintext. It holds the SS keys and
VLESS UUIDs of its own configuration, authenticates the client against them, and
hands the home only bytes. The home keeps the upstream socket (or the session's
NAT entries) and the park, and neither decrypts nor re-encrypts anything. This
is why a session survives a node switch without the two nodes sharing client
credentials. The plaintext crosses the network only inside the mesh QUIC
connection, which is mutually authenticated by the `cluster_psk` (see
[Link and authentication](#link-and-authentication)).

Two things about the body reach the home, both in the OPEN header: how it is
framed (a byte stream, or length-delimited datagrams) and which proxy protocol
the edge terminated (SS or VLESS). The framing selects the home's splice; the
protocol only keeps a park from being resumed across a protocol boundary, the
same rule the direct resume paths enforce. The header carries no request path
(routing and padding are local to the edge) and no carrier kind (WS vs XHTTP
never reaches the home).

An SS-UDP relay routes without a key as well. The identity (user, routing mark,
session scope) arrives once per stream in the setup exchange, and the target
rides inside each datagram, because a plaintext edge forwards the
SOCKS5-wrapped body (`TargetAddr || payload`) the SS-UDP packet already
contains. Responses take the mirror route: the home wraps the upstream datagram
and the edge seals it under the client's key. It has to be the edge, since an
SS-2022 response is sealed against the client session id that only the
terminating node sees. The response encoding is therefore stored on the NAT
entry's attachment rather than on the entry itself, so one upstream socket can
be served by a locally-decrypting carrier and by a relayed one in turn during a
session's life. The same attachment decides which node does the per-user
accounting.

The identity is also the access rule. A relayed datagram is otherwise
unattested content, so `user`, routing mark and session scope come from the
park, never from the datagram. A session reattaches the NAT entries it parked
with, may create entries for targets it has not reached before, and has no way
to address an entry of another session or user: a foreign entry lives under a
key the session cannot construct. Two sessions naming the same target (one DNS
resolver, many clients) get two entries, not a refusal.

### Per-user accounting

Per-user accounting stays with the node that terminates the client session. A
relayed session is counted on the edge, which sees the client's real protocol;
the home records the same traffic only on its `role="home"` mesh counters.
Counting on both nodes would double every relayed user's bytes and requests,
and on the home it would land under `protocol="http3"` (the mesh's own
protocol), where the duplicate is indistinguishable from direct H3 traffic and
cannot be subtracted.

The four splices make that split by three mechanisms:

- Byte stream and single-target VLESS-UDP: the home never touches the park's
  `user_counters`. They pass through the splice unchanged, so a later direct
  resume on the home keeps counting where it left off.
- SS-UDP: the decision travels into the NAT reader on the entry's
  `UdpResponseCoding::Plaintext` attachment, for which
  `terminates_client_session()` returns `false`. On that answer the home
  suppresses its own `user`-labelled `outline_ss_udp_*` request and byte series,
  with the exception below.
- VLESS-mux: the mux frame layer runs on the home, so its sub-connections would
  otherwise each count their payload. `MuxAccounting::OnTheEdge` switches those
  counters off; the edge has already counted the whole mux frame stream once as
  a VLESS byte stream.

Drops the home decided on itself stay counted on the home: an oversized
datagram or a relay-concurrency refusal is a node-local fact no other node
records. The oversized-datagram counter
(`outline_ss_udp_oversized_datagrams_dropped_total`) carries a `user` label, so
this one `user`-labelled `outline_ss_udp_*` series does appear on the home for a
relayed session.

### Park shape in the setup ack

The home names the park's shape in its setup ack. A VLESS carrier cannot name
it in the OPEN: one path multiplexes TCP, UDP and mux, and the command rides the
client's first frame, which the edge may read only after answering the upgrade,
which it may answer only after the OPEN is acked. So the ack answers what the
OPEN left open. It is `OPEN_ACK_ACCEPTED` for a Shadowsocks carrier, whose
framing already is its shape, and the park's shape for a VLESS one. The edge
then decides locally: a command that needs that shape attests the user and
splices; any other command releases the relay before the USER frame that would
make the home consume the park, and is served locally.

Both of the home's probes are non-consuming. Phase 1 asks "any VLESS shape?"
and reports what it found; phase 2 re-asks with the advertised shape
immediately before `take_for_resume`. A mismatch therefore never destroys a park
(`outline_ss_mesh_relay_rejected_total{reason="park_shape"}`). Two alternatives
were rejected: re-opening a second relay costs a mesh round trip before the
first payload byte, and naming the shape in phase 2 arrives after the edge has
upgraded its client and echoed the home's id, leaving a session it can only
fail. See the module doc in `server/cluster/mesh/frame.rs`.

### VLESS-UDP and VLESS-mux splices

Every VLESS shape has a home splice. A single-target VLESS-UDP park is one
connected socket, and the relay pumps length-framed datagrams to and from it, so
such a session survives an edge switch on the same source port. A VLESS-mux park
is a bundle: one sub-connection, with its own upstream, per multiplexed id. It
migrates the same way: the sockets stay on the home, which runs the mux frame
layer, while the edge forwards the client's mux frame stream verbatim as a byte
stream. No wire field was needed, because a mux frame carries its own length
prefixes and a UDP sub-connection's datagram boundary is a frame boundary.
Sub-connections opened inside a relayed mux are dialled from the home; a mux a
node establishes for itself dials its own, so sub-connections never straddle two
nodes. The bundle is admitted whole or refused whole
(`outline_ss_mesh_relay_rejected_total{reason="park_incomplete"}`): it is one
registry entry, and half of it on each node is a session neither node could park
again.

On a relayed mux the client sees frames coalesce and split. The direct path
emits one mux frame per binary WebSocket message; a relayed one forwards mesh
chunks, so one message may carry several frames or part of one. A
stream-oriented mux client (which mux.cool framing implies; `outline-ws-rust`
implements no mux at all) sees no difference. A third-party client that parses
one frame per message must buffer across messages to resume through a foreign
edge.

A relayed mux is not re-parked when the mesh downlink fails. The failure ends
the relay with the uplink cancelled wherever it stood, possibly inside a
sub-connection write or inside the dial of a `New` frame. A mux has neither an
acked uplink offset nor a downlink ring to replay that gap from, unlike the
byte-stream splice, which keeps its upstream across the same cancellation for
that reason. So the bundle is closed and the client re-establishes its mux
instead of resuming one with a silent gap in a sub-connection.

The carrier padding layer belongs to the edge along with the crypto above it:
the edge encodes and decodes padding for its own client and relays unpadded
plaintext, so the home never sees a padding frame on a relayed session.

### Link and authentication

- Link: long-lived QUIC connections between cluster members, one per peer pair,
  multiplexing many sessions. QUIC mandates a TLS 1.3 handshake (quinn on
  rustls with aws-lc-rs, the single crypto provider in the graph), which gives
  ephemeral ECDHE session keys with forward secrecy and an AEAD record layer.
  ALPN is `outline-mesh/1`, keep-alive 10 s, idle timeout 30 s
  (`server/cluster/mesh/tls.rs`).
- Authentication is PSK-derived, without an X.509 CA. Every node derives the
  same Ed25519 keypair from the shared `cluster_psk`
  (`BLAKE3 derive_key("outline-proxy cluster mesh-auth v1", psk)` → Ed25519
  seed) and builds the same fixed self-signed certificate from it. Every member
  therefore arrives at one certificate and pins peers by its SHA-256
  fingerprint, in both directions (mutual TLS). The pin helper is
  `bootstrap/cert_pin.rs` (`cert_fingerprint` / `CERT_PIN_LEN`); the mesh
  verifiers (`MeshServerVerifier`, `MeshClientVerifier`) delegate signature
  verification to the crypto provider and replace only path validation with a
  constant-time pin compare. rustls has no external-PSK API, so a certificate
  is the vehicle, but nothing about it has to be signed or distributed.
- Forward secrecy: a leaked PSK lets an attacker impersonate a peer in future
  handshakes, but recorded past traffic stays protected by the ephemeral ECDHE
  keys.
- One QUIC stream per session. Per-stream flow control gives backpressure and
  removes head-of-line blocking between sessions, the failure class that hit the
  TUN pump. A custom PSK+AEAD transport over raw UDP would also need its own
  nonces, rekeying and anti-replay, which TLS 1.3 already provides.

### Mesh stream layout

A stream is a fixed setup sequence followed by the relayed body
(`server/cluster/mesh/frame.rs`):

```
edge → home:  OPEN                     length-prefixed OpenHeader: version (5), framing tcp|udp,
                                       protocol ss|vless, session_id, client resume capabilities,
                                       optional peer address
home → edge:  ack (1 byte)             OPEN_ACK_ACCEPTED, or the park's shape when the OPEN
                                       committed to none (VLESS)
edge → home:  USER                     user name the edge authenticated (1-byte length, ≤ 64)
home → edge:  UPSTREAM-ACK (8 bytes)   only if the OPEN set the ack-prefix capability
home → edge:  downlink replay suffix   only if the OPEN set symmetric replay
both ways:    body                     plaintext: raw byte stream (framing tcp) or
                                       `u32 BE length | payload` per datagram (framing udp)
```

There is no per-chunk data frame. The stream ends with a QUIC `finish`
(graceful) or a `reset` whose error code is a `CloseReason`:

| `CloseReason` | Code | Meaning |
| --- | --- | --- |
| `Fin` | 0 | orderly end of stream |
| `Abort` | 1 | peer reset or upstream error |
| `Budget` | 2 | the edge tore the relay down on its health budget |
| `Capacity` | 3 | the home is at its relayed-session cap |
| `NoSession` | 5 | the home holds no park under this resume id, or its owner is not the attested user |

A peer on an older build maps `Capacity` and `NoSession` to `Abort`.

### Two-phase setup

The edge cannot name the user in its OPEN: it must decide what to send in the
client's `101` before it can read the client's first encrypted frame. So phase 1
asks a narrower question: is there a park under this resume id, of a shape this
OPEN can splice? The home answers with one ack byte or a `NoSession` reset. That
byte carries the park's shape when the OPEN could not name one, which a VLESS
edge needs before its first frame arrives. Phase 2, one round trip later, sends
the `USER` frame with the identity the edge authenticated; the home re-checks
the shape and the park owner before handing the park over. A home that gets no
`USER` frame within 5 s (`USER_FRAME_WAIT`) refuses the stream
(`reason="bad_setup"`) and releases its relay permit.

The edge waits for the phase-1 answer before it upgrades the client carrier.
This keeps a refusal recoverable: the edge can still serve the client a fresh
local session (`outline_ss_mesh_relay_opened_total{outcome="refused"}` on the
edge, `outline_ss_mesh_relay_rejected_total{reason="no_session"}` on the home).
A refusal is the ordinary answer for every expired park and every id this home
never minted, so only a refusal rate near 100% of opens is a symptom. The cost
is one mesh RTT per relayed session, paid once at setup.

There is one wire version, `OPEN_VERSION = 5`. The home parses only that: a
peer on an older build, including one still sending the retired v4 OPEN (where
the home did the decryption), is refused with a reset on both halves before any
ack. That edge then serves its client a fresh local session. Version skew costs
session continuity, not traffic.

## Per-node config, shared user names

Only `cluster_psk` and the peer table have to match across nodes. Paths and
credentials are per-node: the edge authenticates the client against its own
configuration and the home never decrypts, so nothing about a relayed session is
resolved on the home (no path lookup, no route table, no user key). A node can
serve `/tcp` where its peer serves `/a1b2`, with a different `password` /
`method` / `vless_id` per user, and relays between them work.

The user name must agree. A park is keyed by (session id, user), so the home
checks the name the edge attests against the park's owner before handing the
session over. If `carol` denotes different people on two nodes, a resume is
refused (`outline_ss_mesh_relay_rejected_total{reason="unknown_user"}`), which
is the intended outcome. On the byte-stream path the name is the only identity
signal: a park made under Shadowsocks is handed to a VLESS carrier of the same
account, and the reverse. So `[[users]].id` and every `[users.aliases]` name
must denote the same person on every node. See
`bins/outline-ss-rust/docs/SESSION-RESUMPTION.md` § Cross-protocol resume;
crossings are counted on
`outline_ss_orphan_resume_cross_protocol_total{parked,resumed}`.

The name is the only part of a node's user config the mesh constrains, and the
constraint comes from the wire: the name travels in a `USER` frame with a
one-byte length, capped at `MAX_USER_LEN` (64) in
`server/cluster/mesh/frame.rs`. An empty name or one longer than 64 bytes could
never authenticate a relayed session (the edge refuses to send it, the home's
parser refuses to read it), so a server with `[cluster] enabled = true` refuses
such a name at startup (`config/validation.rs`,
`validate_cluster_user_names`) instead of losing resumes at the first relay.
The check covers every string that can reach a `USER` frame: the attested name
is the effective accounting label, so a `[users.aliases]` key becomes the name
on the wire whenever the client's source IP falls inside that alias's subnet.
Both `[[users]]` ids and alias names are checked. A server without
`enabled = true` sends no `USER` frame and is not held to the limit.

A defect the mesh inherits: an SS-TCP park is keyed on the base user id, while
both the direct resume and the mesh attestation look it up by the effective
label. A user with `[users.aliases]` connecting from a matching subnet therefore
fails the owner check with a correct config, on the direct path as well as the
relayed one. This is a defect in the park key, not a cluster configuration
problem, so the relay's `unknown_user` log line reports what it observed and
does not point at node config.

The previous design (wire v4 and earlier, where the home decrypted) required the
relayed path and the relayed user's credentials to be identical fleet-wide. An
asymmetry produced a silent black hole: a relay onto a route holding no key, with
every packet failing authentication for the life of the session. Moving the
crypto to the edge removed the requirement and that failure mode.

## Home: accept loop and limits

The home's accept loop separates two failure scopes. A connection error (the
peer closed it, it timed out) ends the loop for that peer. A stream error (a
stream reset before its OPEN arrived, or an OPEN this build cannot parse, for
example from a peer mid rolling upgrade) drops only that stream, after refusing
it explicitly. The connection keeps carrying the relays already accepted on it.

The home holds one permit per in-flight relayed session:
`MESH_MAX_RELAYED_SESSIONS` = 4096 across all peers
(`server/cluster/mod.rs`), the inbound counterpart of the edge's outbound cap
`MESH_MAX_RELAY_STREAMS` = 4096. A stream arriving with no permit free is reset
with `CloseReason::Capacity` and counted in
`outline_ss_mesh_relay_rejected_total{reason="capacity"}`; the edge serves that
client locally.

For VLESS mux the whole multiplex parks atomically, and the relay carries it
over one mesh stream without splitting sub-connections across streams. The home
decides once, before it consumes the park, whether the bundle can be served;
re-attaching it cannot then partially fail, because every parked sub-connection
already holds both halves of its upstream.

For SS-UDP the body is not a byte stream. A datagram is atomic, so the relay
frames each one as `u32 length | payload` on the mesh stream and de-frames it on
the far side. A raw byte splice would let QUIC coalesce or split packets, and
the home routes per datagram, so a wrong boundary means a mis-routed packet.
(Before the crypto moved to the edge, the same coalescing broke the home's
per-packet AEAD open; that production incident is where this framing came
from.) The mesh QUIC stream is reliable and ordered, so the mesh hop drops no
packets; the client↔target UDP path stays best-effort over the last mile. On
the home each relayed SS-UDP session is pinned to its own NAT entry by a
per-session scope (its resume id). Two concurrent sessions to the same
`(user, target)` (a second edge relaying the same user, or a client warm-probe
next to real traffic) never share one upstream socket or last-writer-wins
response slot. A resume adopts the parked scope, so an edge switch reuses the
single entry (one source port to the target).

VLESS-UDP is framed the same way, but the decision comes later. Its OPEN is a
byte-stream one, because the edge cannot tell before the client's first frame
whether the session behind a VLESS resume id is TCP, UDP or mux. The shape comes
back in the home's ack, and the shape, not the OPEN's framing, says how the body
is delimited. A VLESS-UDP relay frames its datagrams as SS-UDP does: the
client's own `u16`-prefixed frames are de-framed on the edge, one mesh datagram
per packet, and sent whole into the one socket the park holds. A mux-shaped
park resolves to byte-stream framing, and the mux frames inside supply every
boundary.

### Health budget

Cluster members are in different countries, so the edge → home hop is long and
the mesh is treated as best-effort:

- The edge bounds each uplink write to the mesh by `mesh_relay_budget_ms`
  (default 4000). When the home stops draining (hung, or the interconnect
  stalls), the QUIC send window fills and the write blocks; exceeding the budget
  marks the relay as stalled.
- On a stall the edge resets the mesh stream (`CloseReason::Budget`) and closes
  the client carrier. The client starts a fresh session locally on the edge,
  which becomes the new home; the orphaned park on the slow home expires by TTL.
- The budget measures progress, not RTT. A high but flowing RTT keeps
  completing writes, so the budget fires only on a full stall and never on an
  idle session (an idle uplink blocks on a read, not a write). A pure-download
  stall with no uplink writes is left to the mesh QUIC idle timeout (30 s).

## Home: park and unpark

The `OrphanRegistry`, the `Parked` variants and the park/resume semantics are
the ones a direct carrier uses: a relayed resume is `take_for_resume(id, user)`
like any other, and a relayed carrier that ends re-parks the upstream under the
same id. The difference is that the home splices the park onto a mesh stream
carrying plaintext instead of re-running its accept path over a client socket,
so it runs no crypto and no route lookup for that session.

"Park on A, unpark on B" follows from this: the client leaves edge A (or edge A
dies), the home parks as it would on any carrier drop; the client arrives at
edge B with the same session id, edge B opens a new mesh stream to the home, and
the home unparks into that stream.

## Home is chosen once: sessions stratify across homes

The client's load balancer switches the edge (the entry point), never the home.
A home is assigned once, when a session is born, and never moves: a first
connect with no resume id is handled locally on whatever edge it landed on,
which mints a session id carrying its own shard and becomes that session's home.
A resume carries an existing home in its shard, so it points back at wherever
that session was first established.

When a client leaves a still-alive server A as its edge (A got a throttle or
health penalty, it did not die) and moves to B:

- existing sessions (born on A) keep A as their home; a resume through edge B
  relays back to home A over the mesh, so they survive;
- new sessions opened while B is the active edge are minted on B and get B as
  their home.

The client's sessions are then split across two homes: old ones on A, new ones
on B. Consequences:

- Correctness is unaffected. Sessions are independent; nothing requires a
  client's sessions to share a home.
- Path asymmetry. Old sessions take a double hop `client → B → A → target`. If A
  was abandoned because of a bad last mile (an `edge→client` throttle), the old
  sessions gain (their downlink is now `B→client`) at the cost of the `A→B`
  interconnect hop. If A was abandoned because of a bad upstream (`A→target`),
  the old sessions pinned to home A keep suffering; relaying through B does not
  change the `A→target` segment. Only new sessions on B avoid it.
- A cannot be drained instantly. While old sessions live, A stays their home
  (over the mesh from B, and directly for still-open flows). A sheds load only
  as its sessions close.
- The split does not grow without bound. Old sessions close, new ones are born
  on the active edge, and once A recovers and becomes the active edge again, new
  sessions land on A. The home distribution follows whichever edge is active,
  lagged by session lifetime.

There is no home migration: a live upstream socket cannot move between machines
(see the top of this document). The only planned mitigation is
[open risk 2](#open-risks): let the client dial the home directly when it is
reachable. That removes the double hop but not the split (the home is still
where the session was born). Anycast ingress (§5a in
[`CLUSTER-DEPLOY.md`](CLUSTER-DEPLOY.md)) reduces the split: one resume scope,
and the home is the network-nearest node rather than wherever the client
happened to be when it opened the session.

## Failure semantics

| Failure | Behaviour | Session |
| --- | --- | --- |
| edge dies | client fails over to another edge (existing uplink logic); same session id → same home → unpark | survives |
| mesh stalls | edge tears down on the health budget → fresh session on the edge | lost |
| home dies | shard points at a dead server; edge cannot reach it over the mesh → resume miss → fresh session | lost (same as standalone) |
| shard unknown (server decommissioned) | no peer for that shard → `outline_ss_mesh_relay_opened_total{outcome="fail"}` → fresh session | lost |
| home holds no park under the resume id (expired, or never minted there) | home refuses at setup (`no_session`); the edge has not upgraded the client yet → fresh session on the edge | lost (ordinary: parks expire) |
| the park is a shape no relay from this OPEN could ask for (an SS-UDP park under a VLESS resume id, or the reverse) | home refuses at setup (`park_shape`) without consuming the park → fresh session on the edge | lost on this carrier; the park survives for the next |
| a mux park holds no sub-connection left to re-attach | home refuses the whole bundle (`park_incomplete`) instead of splicing part of it → client reconnects | lost (the bundle was already empty) |
| the mesh downlink of a relayed mux fails or stalls mid-session | the relay ends with the uplink cancelled at an unknown point, so the home closes the bundle instead of re-parking it → client re-establishes its mux | lost on purpose (a re-park would hide a gap in a sub-connection) |
| the park's shape is not the one the client's VLESS command needs | home names the shape in its ack; the edge releases the relay before the USER frame, so nothing is consumed → local session on the edge | lost on this carrier; the park survives for the next |
| peer on a retired wire version | home refuses the OPEN before any ack → fresh session on the edge | lost (continuity only; traffic flows) |

## Interaction with downstream-throttle detection

The padding-based downstream-throttle detection (server `ThroughputMonitor` →
`OCTL` cover frame → client uplink switch) works with the cluster, with the
caveats below. It runs on both the TCP and the UDP padded WS/XHTTP carriers (SS
and VLESS); the unpadded wire is not monitored. In the cluster the UDP leg rides
its own carrier on the same uplink index, so it relays over its own mesh stream
to the same home and is subject to the same caveats: a detected UDP throttle
penalises the UDP leg and migrates only it.

- The signal is produced where the throttled segment is. The padding layer
  (including cover / `OCTL` frames) belongs to the node that terminates the
  client, the edge, so on a relayed session the edge both detects the stalled
  last mile and injects the `OCTL` frame into its own client's carrier. Nothing
  about the signal crosses the mesh.
- The client reaction does not depend on the cluster. The client receives
  `OCTL` over the carrier from the edge, penalises that uplink (the edge) and
  moves to another edge, which relays to the same home, so the session survives.
  No client-side change is needed.
- A detector on the home would measure the wrong segment, so a relayed session
  does not run one there. On the home, `out`/backlog reflect the home→mesh
  segment, not home→client. End-to-end backpressure (the client stalls → the
  edge stops draining the mesh stream → the QUIC window closes → the home sees
  backlog) propagates a client-side throttle, but the home cannot tell the
  segments apart:
  - throttle on `edge→client` (the last mile): switching edge helps;
  - throttle on `home→edge` (the cross-country interconnect): switching edge may
    help (a different mesh path);
  - throttle on `home→target` (upstream): switching edge does not help; the
    client flaps between edges, all go on cooldown, and it eventually moves to a
    new home and loses the park.
- False positives from a slow interconnect were the main problem of a home-side
  detector: a slow mesh between countries produces backlog on the home and a
  spurious `OCTL`. On the edge this cannot happen: the edge sees only the client
  mile, and a slow interconnect shows up there as a read stall on the mesh, not
  a client-facing write stall.
- It overlaps the health budget. Both react to a slow downstream: throttle
  detection is soft (keep the home, move traffic away), the health budget is
  hard (tear the carrier down, new home). Keep the budget a hard floor that
  fires only on a full stall, and make sure it fires later in wall-clock time
  than the throttle sustain window (`throttle_window_secs` ×
  `throttle_sustain_windows`, default 1 s × 5). Otherwise the budget tears the
  session down and loses the park before the soft migration can run.

Detection is local to the edge. The edge owns the client's crypto and its padded
writer, so the node that observes the throttled last mile is the node that acts
on it: it runs the `ThroughputMonitor` over its own client-facing carrier and
injects the `OCTL` cover frame directly. `home→edge` and `home→target` slowness
is left to the health budget. Detection is gated on the server
`[padding] throttle_detect_enabled` key (default `false`), read per node like
the rest of the padding config.

In wire v4, when the home did the decryption, the edge could not inject
anything and sent the home a `THROTTLE_HINT` mesh control datagram instead. Both
halves were removed with that wire version: the sender with the v4 edge
detector, and the home's receiver, its session registry and its two counters
(`outline_ss_mesh_throttle_hints_received_total`,
`outline_ss_mesh_control_datagram_errors_total`), because a pre-v5 peer's OPEN is
refused and never has a relayed session to send a hint about. The mesh does not
advertise QUIC datagram support (`datagram_receive_buffer_size(None)` in
`server/cluster/mesh/tls.rs`): an old peer that still tries to send a hint
fails locally on its own send instead of putting bytes on the wire.

## Security

- Mesh auth: mutual PSK-derived certificate pin between cluster members (see
  [Link and authentication](#link-and-authentication)). A host without the
  `cluster_psk` cannot derive the keypair and cannot open a relay stream.
- Topology is not revealed: on home-down or foreign owner the edge answers the
  client with an ordinary resume miss, the same silent answer as the existing
  owner-mismatch path. An observer cannot distinguish "no such shard" from
  "home is down".
- The shard is obfuscated under the cluster key, so the session id looks
  random to DPI.
- What an edge sees: on every carrier the edge terminates the client's crypto,
  so it sees that client's plaintext and holds the credentials its own
  configuration gives it. This is the same exposure any entry node has for the
  sessions it serves directly. It holds nothing for sessions it is not carrying,
  and the plaintext crosses the mesh only inside the mutually authenticated
  TLS 1.3 QUIC connection between nodes that hold the `cluster_psk`. The home
  holds no client key for a relayed session: of what it forwards it reads only
  the target address it routes on.

## Configuration

Server (`outline-ss-rust`):

```toml
[cluster]
enabled = true
shard_id = 7                       # 0..15, unique within the cluster
cluster_psk = "<base64>"           # one shared secret; derives the shard-obfuscation key and the mesh-auth keypair
mesh_listen = "[::]:9443"          # QUIC listener for inbound relays (PSK-derived mutual pin, no CA)
mesh_relay_budget_ms = 4000        # progress budget: stalled longer → tear down
peers = [
  { shard = 1, addr = "<shard1_ip>:9443" },
  { shard = 7, addr = "self" },    # own shard: skipped before addr is parsed
  # ...
]
```

`<shard1_ip>` is the IP address of the peer that owns shard 1.

| Key | Default | What it does | When to change |
| --- | --- | --- | --- |
| `enabled` | `false` | Master switch. Without `true` the rest of the section is ignored: plain random session ids, no mesh listener, no relay. | To turn the cluster on or off on a node. |
| `shard_id` | required when enabled | This node's shard, `0..15`. | Once, when the node joins; must be unique. |
| `cluster_psk` | required when enabled | Base64 of the shared secret; must decode to a non-empty value. | Never in a running cluster without changing it on every node: a node with a different PSK fails the mesh pin. |
| `mesh_listen` | required when enabled | Socket address (`IP:port`) the mesh QUIC listener binds. Parsed as `SocketAddr`, so a host name is rejected. | If 9443/udp is taken or the node should listen on one address only. |
| `mesh_relay_budget_ms` | `4000` (minimum 1) | Edge-side progress budget per mesh write. | Raise if long but flowing interconnect stalls tear relays down; keep it above the throttle sustain window. |
| `peers` | empty | Shard → mesh address of every node. Own shard is skipped; `addr` must be `IP:port`; a duplicate shard is an error. | When a node is added or removed. |

Validation (`config/loader.rs`, `resolve_cluster`) runs at startup and aborts
it on any error above. The listener is bound at startup in
`ClusterCtx::build` (called from `server/services.rs`). The server control API
(`PATCH /control/config`) writes `[cluster]` changes to `config.toml` and
answers `"requires_restart": true`; they take effect only after a restart.

The single `cluster_psk` is the only shared secret; there is no CA and no
certificate to distribute. It is split by BLAKE3 `derive_key` contexts
(`"outline-proxy cluster shard-obfuscation v1"` for the session id,
`"outline-proxy cluster mesh-auth v1"` for the interconnect keypair), so one key
is never used in two crypto contexts.

Client (`outline-ws-rust`): no code changes. The client already resumes to the
same uplink with the same session id, and the edge failover path exists. With
anycast ingress the relay is invisible to it. Without anycast and without
reliable DNS, list every node as its own uplink and set `shared_resume = true`
on the group (or on `[outline.load_balancing]`), so all uplinks share one resume
scope, the group name: whichever edge the client dials, it presents the same
resume id and the session survives the switch. Step-by-step deployment is in
[`CLUSTER-DEPLOY.md`](CLUSTER-DEPLOY.md).

## Bounded resources

Per the workspace "bounded resources" invariant, every long-lived mesh object
has a limit:

| Object | Limit | Where |
| --- | --- | --- |
| Outbound relay streams (edge) | 4096 per node across all peers (`MESH_MAX_RELAY_STREAMS`); over the cap the open fails and the client gets a local session | `server/cluster/mod.rs`, `mesh/peer_pool.rs` |
| Inbound relayed sessions (home) | 4096 per node across all peers (`MESH_MAX_RELAYED_SESSIONS`); over the cap the stream is reset with `Capacity` | `server/cluster/mod.rs` |
| Wait for the `USER` frame after the ack | 5 s (`USER_FRAME_WAIT`) | `server/transport/mesh_relay.rs` |
| Idle mesh connection | QUIC idle timeout 30 s, keep-alive 10 s | `server/cluster/mesh/tls.rs` |
| Parked session | the home's `[session_resumption]` TTL and caps | `[session_resumption]` |
| Stalled relay | `mesh_relay_budget_ms` | `[cluster]` |

There is no per-peer cap and no LRU eviction of relay streams.

## Open risks

1. Mesh data plane (the same silent-corruption class as the TUN pump). Covered
   by tests in `bins/outline-ss-rust/src/server/tests/resumption/cluster.rs`:
   `cluster_relay_streams_large_transfer_sha256` streams 16 MiB through the
   relay as a chunked SS-AEAD stream and checks it byte-exact with SHA-256 in
   both directions; `cluster_session_survives_edge_switch` covers park and
   reattach across an edge switch. Residual: confirm on production traffic (a
   SHA-256 check of a large transfer through a live cluster) and keep
   `git revert` ready.
2. The double hop across countries raises RTT for long bulk transfers; the
   health budget protects against hangs but not against slowness. A possible
   follow-up is letting the client dial the home directly when it is reachable,
   bypassing the edge relay. That is client-side routing on top of the mesh and
   a separate phase.
3. VLESS mux parks atomically and the relay carries the whole multiplex on one
   mesh stream. The residual risk is the frame layer running on the home: a mux
   frame stream that desynchronises there costs the whole bundle (it is not
   re-parked), where a byte-stream relay would only drop the carrier.
4. Downstream-throttle detection on relayed carriers runs entirely on the edge
   (see above), so the home no longer confuses the interconnect with the
   client's last mile. Residual: the edge cannot tell a real last-mile throttle
   from a client whose own link is that slow, so the detector's thresholds are a
   heuristic. The feature is off by default; keep the budget-vs-sustain ordering
   in mind when enabling it. The `[padding] throttle_edge_min_bytes_per_sec` key
   belonged to the retired mesh `THROTTLE_HINT` detector and has no effect. It
   is still accepted (`[padding]` rejects unknown keys, so removing the field
   would make configs that still set it fail to load) and logs a warning at
   startup. Remove it from configs; the field will be dropped in a later
   release.
